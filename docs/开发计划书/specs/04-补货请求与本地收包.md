# 补货请求与本地收包规格

- **计划版本**：`v0.1.0`，里程碑 M3—M4
- **优先级**：A
- **状态**：实施规格；2026-09-03 收缩为原生运输联调，2026-09-04 改用精确组件身份，T06／T07 受影响路径重新打开
- **前置依赖**：[个人缓存与持久化](01-个人缓存与持久化.md)、[供应链坠与网络绑定](02-供应链坠与网络绑定.md)、[物流格界面与五阶段](03-物流格界面与五阶段.md)
- **必需运行基线**：Java 21、Minecraft 1.21.1、NeoForge `21.1.219`、Create `6.0.10-280`、Curios `9.5.1+1.21.1`
- **兼容测试基线**：Create More: Package Couriers `2.3.0`、Create: Mobile Packages `1.21.1-0.7.7`。两者均不写入依赖声明，也不得成为核心类加载或补货请求前提；运输按各自原生方式运行
- **被依赖**：状态箭头、按格手动重置、五阶段缓存界面；后续退货另行定义载具发运接口，不得复用本规格的待收记录冒充退货签收

本规格只定义玩家本地的补货意图、Create 真实请求及专用包裹进入原版玩家物品栏后的处理。系统不跟踪载具坐标，不判断丢件，不超时赔付，也不创建另一套全图运输系统。外部运输事故仍按实物当前位置处理。

## 用户故事

> 作为佩戴有效供应链坠的玩家，我希望缓存低于最低数量时只向当前绑定的 Create 网络请求尚未覆盖的差额，并由纸飞机或运输蜂把真实包裹送进我的背包，避免重复点单和手动拆包。

> 作为同时安装两种运输模组的玩家，我希望一份缺口只产生一份 Create 请求；实际运输沿用我建设的路线和原模组规则，安装数量不改变请求次数。

> 作为遇到丢包或卡包的玩家，我希望能按物流格清除等待记账后重新采购，同时明确知道这不会撤销、删除或赔付旧包。

## 范围与非范围

### 本规格包含

1. 只在供应链坠有效佩戴、网络无冲突、饰品绑定有效、Create 网络可用并接受请求时提交补货；不额外探测配送模组或玩家运输资格。
2. 按精确物品变体汇总待收数量，按物流格执行手动重置。
3. 调用 Create 的真实库存查询及包裹请求，不直接向缓存生成物资。
4. 纸飞机原生派送与完整包裹交接的联调验收。
5. 运输蜂原生派送、成员条件与完整包裹交接的联调验收。
6. 两种运输模组同时存在时仍只发一次请求；核心不引用可选运输模组类。
7. `FMP@玩家名` 专用地址、部分入库、残包续收、迟到包与重复本地事件。

### 本规格不包含

- 跟踪、召回、取消或销毁已经发出的载具或包裹。
- 根据等待时间自动认定丢件、自动重置、赔付或免费重发。
- 扫描世界实体、其他玩家、末影箱或第三方背包；带插件背包访问属于后续功能。
- 接管普通地址包裹、预拆包后的散装物品或玩家背包中的同类散装材料。
- 退货、一次性蜂、退货站或远端仓库签收。
- 为补货登记／撤销外部目标、替代定位器、管理蜂成员、探测运输路线或截取打包机产物派出载具。

## 术语与逻辑字段

字段名是跨模块逻辑契约，不预设最终 Java 类名。

### `ItemVariantKey`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `itemId` | ResourceLocation | 非空；必须是该物流格允许存储的物品 |
| `components` | 完整持久化数据组件快照 | 数量规范化为 1；注册表感知编解码往返后身份不变；编码不超过 1,024 字节 |

`ItemVariantKey` 是过滤、待收、收据、Create 查询／请求和收包的统一物品身份。同一精确变体在一名玩家缓存中最多对应一个物流格；同一 `itemId` 的不同组件状态可分别占格。查询和请求使用由完整键产生的防御性 `ItemStack` 副本并精确同物同组件匹配，不能把裸 `itemId` 的所有变体合计，也不能把响应重建成默认实例。

### `RestockContext`

| 字段 | 类型 | 来源 |
| --- | --- | --- |
| `playerUuid` | UUID | 服务端当前玩家，不接受客户端指定他人 UUID |
| `cellIndex` | int | `0..unlockedCellCount-1` |
| `filterRevision` | long | 过滤建立或改变时递增，用于拒绝旧计划 |
| `itemKey` | ItemVariantKey | 当前物流格的完整精确过滤；不由客户端提交裸 ID 派生 |
| `onHand` | long | 当前缓存现货 `N` |
| `capacity` | long | 当前阶段单格实际容量 `C` |
| `minimumEnabled` | boolean | 最低端是否启用 |
| `minimum` | long | `0..capacity`；仅启用时参与计算 |
| `networkId` | nullable UUID | 本地访问可为 `null`；只有新请求门通过时必有值 |
| `localAccessState` | enum | 与终端快照一致：`INACTIVE`、`ACTIVE`、`MANAGEMENT_ONLY` |
| `requestAccessState` | enum | 与终端快照一致：`BLOCKED_NOT_WORN`、`BLOCKED_DISABLED`、`BLOCKED_UNBOUND`、`BLOCKED_CONFLICT`、`NETWORK_UNAVAILABLE` 或 `READY`；不追加外部运输资格门 |

### `PendingInboundRecord`

一条记录表示本地已经提交但尚未由本地专用包裹覆盖的请求量，不证明外部包裹仍在飞行。

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `requestId` | UUID | 服务端生成、玩家活动表内唯一 |
| `playerUuid` | UUID | 所属玩家 |
| `originSlotIndex` | int | 提交时物流格 |
| `filterRevision` | long | 提交时过滤版本 |
| `itemKey` | ItemVariantKey | 按精确变体聚合的请求身份 |
| `sourceNetworkId` | UUID | 提交请求所用网络；换饰品不改写记录 |
| `remainingCount` | long | 尚未被本地到货覆盖的正整数数量 |
| `submittedGameTime` | long | 诊断用；不得据此自动赔付或重置 |

有效待收量为同一玩家、同一 `itemKey` 与当前 `filterRevision` 下所有活动记录的 `remainingCount` 之和。每精确变体最多 4 条、全玩家最多 144 条；创建第 5 条前把同变体、同网络、同过滤版本的新承诺量合并进最新记录。记录归零或手动重置后从活动表删除，只写结构化日志，不持久化历史。

### `PackageReceipt`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `receiptId` | UUID | 专用包裹第一次被本模组观察时由服务端写入的本模组持久标记 |
| `ownerUuid` | UUID | 第一次处理时的实际背包所有者 |
| `address` | string | 必须精确等于当时的 `FMP@玩家名` |
| `firstSeenGameTime` | long | 诊断字段 |
| `arrivalCounts` | map<ItemVariantKey,long> | 第一次观察时包内各受支持精确变体的数量快照；结算时只分配给当时仍存在的同变体过滤及其当前修订，且只执行一次 |
| `allocatedCounts` | map<ItemVariantKey,long> | 已从同一精确变体活动待收记录中扣除的数量 |

包裹仍有余货时，收据标记随原包裹保存；后续续收入库只移动剩余实物，不再次扣减待收。包裹组件改写必须先通过 `SPK-PKG-01`，不能退化为“每次扫描都算一次到货”。

## 服务器状态机

### 需求状态

```text
INACTIVE
  -> NEEDS_STOCK            本地访问有效且 N < L，待收未覆盖缺口
  -> BLOCKED_REQUEST_GATE   未绑定、网络冲突或 Create 网络不可用
  -> BLOCKED_NO_STOCK       Create 可见库存为 0
  -> WAITING_LOCAL_DELIVERY 请求承诺已登记，remainingCount > 0
  -> RESIDUAL_REMAINS       包已到达但余物仍在真实包裹中
  -> SATISFIED              N 与有效待收已覆盖最低数量
```

第一次观察到真实包裹就按实际支持内容扣减待收；这表示物资已进入本地收包边界，不表示全部内容已进入缓存。未能装入缓存的内容由原包裹继续持有。

### 本地访问门与新请求门

**本地访问门**只要求：玩家在线且服务端身份有效、Curios 中至少一件供应链坠已启用、已启用坠子之间没有不同网络冲突。通过后允许查看与操作缓存、自动拆包及续收残包；全部坠子尚未绑定网络也不影响这些本地能力。佩戴变化不登记、撤销或修改外部运输目标。

**新请求门**在本地访问门之上再要求：已启用坠子归并出恰好一个随饰品携带的有效网络 ID、该 Create 网络仍可用并接受请求。只有通过新请求门才查询网络库存并广播补货请求。是否安装运输模组、是否有定位器、蜂成员关系和路线可达性不由 FMP 检查；原运输模组仍按自身条件决定是否实际派送。

已经发出的外部包裹不因任一门关闭而被修改。重新满足本地访问门时，处理顺序固定为：专用残包续收 → 首次到达的专用包裹 → 若新请求门也通过，再计算各格缺口。

## 补货计算与 Create 请求

对某物流格定义：

```text
N = 缓存现货
L = 启用的最低数量
P = 同一 ItemVariantKey 与当前 filterRevision 的有效待收量
D = max(0, L - N)
R = max(0, D - P)
```

1. 未启用最低数量、`N >= L` 或 `R = 0` 时不提交请求。
2. 先处理本地专用残包；处理后重新读取 `N`，不能先下单后续收。
3. 只有新请求门通过时，才用当前格完整 `ItemVariantKey` 生成数量为 1 的防御性模板，查询 Create 网络中同物同完整组件的可见数量 `A`。不能证明查询按组件精确匹配时进入 `ITEM_IDENTITY_UNSAFE`；`A <= 0` 时不调用请求入口、不创建 `PendingInboundRecord`，状态为 `BLOCKED_NO_STOCK`。
4. `A > 0` 时本次数量 `Q = min(R, A)`。查询不是库存预留；准备真实请求计划前必须再次校验佩戴、网络、过滤版本和当前 `R`。
5. 使用地址 `FMP@<服务端当前玩家名>` 准备一个包含 `Q` 个该精确变体的 Create 请求计划。请求结构必须原样保留组件；不得降级为裸 `itemId` 或默认实例，也不得为纸飞机、运输蜂各广播一次。没有可用打包机、分配量为零、打包机忙或计划超额时，在接触外部库存前拒绝，不创建待收。
6. Create 6.0.10 的实际派发入口没有可原子提交本模组待收记录的结果对象。为避免“外部已经部分抽料、随后抛错、本地却删除待收”造成重复发货，服务端须先持久化 `Q` 的**请求承诺**，再调用已经准备好的派发计划。派发正常返回后继续等待实体包；一旦开始调用派发，抛错或进程中断均保留该承诺并记为结果不确定，不自动回滚或重发，只允许玩家按格手动重置。UI 的在途状态仅表示“本地正在等待”，不证明载具已出发或包裹仍存在。
7. 缺货或暂不可用时不得每 tick 广播。Create 请求网关优先使用库存／链接失效通知；没有可靠通知时，对同一玩家和 `ItemVariantKey` 的重检频率不得高于每 100 个服务端 tick 一次。恢复可见库存后最迟在下一次该窗口内重算。
8. 一个 Create 请求可以由上游连续拆成多个标准包裹；待收量按物品数量结算，不按“见到第一个包裹”整单完成。

玩家换用另一网络绑定的饰品不会清除 `P`。只要旧记录仍覆盖缺口，就不向新网络重复购买；玩家可以按格手动重置后明确承担重新采购成本。

## 原生运输边界与联调

按 2026-09-03 用户明确的边界，首版不要求 `DeliveryProviderAdapter`，也不建立替代原生定位器、目标登记或蜂成员检查的兼容模块。核心只使用 Create 请求和完整包裹接口，不在类签名、数据文件或静态初始化中引用可选运输模组类。

- 一份缺口只提交一次 Create 请求，装几种运输模组都不改变这一点。
- 发运设施、定位工具、成员条件、返回方式和载具成本由玩家按原模组规则安排；FMP 不截包、不选路、不直接放出载具。
- 没安装两种运输模组也可按有效绑定和 Create 库存请求包裹。玩家可自行取得真实包裹；没有包裹进入本地时只维持待收，不由 FMP 猜测卡在哪一步。
- 联调用原生配置选择完整包模式，记录实际版本和设施，不在 FMP 内强制修改对方设置。预拆包模式产生的散装物品按原版背包物资处理；本模组不能从普通散装物反推出配送来源或伪造对应诊断。
- 当前本地实物满足地址、收据及缓存规则就可处理，不根据“由哪种载具送来”增加资格条件。
- T08／T09 的交付物是验证记录与必要的玩家使用说明，不预设新增运输适配代码。若证据显示 FMP 交接存在缺陷，先定位；修复核心缺陷不等于取得改写外部运输规则的许可。

上述收缩不改变后续退货：从玩家运输格使用纸飞机零件／运输蜂主动发运属于 `v0.2.0` 的另一个入口，届时再定义适配与失败处理。

## 本地收包事务

### 地址和身份检查

只处理同时满足以下条件的栈：

1. 是 Create 完整包裹物品。
2. 地址字符串精确为 `FMP@<该物品栏当前玩家名>`，大小写使用服务端真实玩家名。
3. 当前玩家通过本地访问门。
4. 包裹处于该玩家的原版主物品栏或快捷栏；光标、外部背包和地面实体不在首版自动扫描范围。
5. 包裹已有本模组收据时，`ownerUuid` 必须等于当前玩家，且收据保存的地址必须等于包裹当前地址；不匹配视为收据篡改或错误所有者，整包不动。

地址只用于选择本地包裹，不能选择他人缓存、创建饰品网络绑定或改写外部运输模组的权限。没有对应有效 `PendingInboundRecord` 的迟到包也照常处理；未标记、他人地址或普通地址包裹保持原样。

### 第一次观察与待收结算

先完整验证包裹槽数、每个栈的计数／原生上限、地址和组件可解码性；畸形包在写收据或改待收前整包拒绝。

1. 若合法包裹无 `receiptId`，生成并写入包裹，记录第一次观察时各受支持精确变体的数量快照。
2. 对每个 `ItemVariantKey`，只匹配当前仍存在的同变体过滤及其当前 `filterRevision`，再将到货数量按 `submittedGameTime` 从旧到新扣减仍有效的 `PendingInboundRecord.remainingCount`；归零记录立即删除。
3. 手动重置已删除的记录不会因迟到包重新创建。超过有效待收量的到货仍是合法实物，不丢弃、不赔付，也不产生负待收。
4. 若包裹已有 `receiptId`，不得再次执行到达分配；只尝试移动当前剩余内容。

### 部分入库

对包裹最多 9 个内容槽按原顺序处理：

1. 先验证包内最多 9 个槽，且每个非空栈的数量为 `1..该精确变体原生最大堆叠`；超槽、负数、零计数非空栈或非法超堆叠使整包进入 `PACKAGE_UNSUPPORTED`，不部分解释。合法栈规范化为 `ItemVariantKey` 并寻找完整相同的配置格；没有匹配格、模板超限、无法安全解码或其他不支持内容时原样留包。
2. 读取对应格当前空间 `space = capacity - onHand`，可转量 `move = min(stack.count, max(0, space))`。
3. `move > 0` 时，在同一服务端事务中减少包裹内容并增加缓存相同数量；不得先清包再写缓存。
4. 包裹所有内容均为空时才移除一个真实包裹栈；仍有任何内容时保留同一个包裹及其收据标记。
5. 完全没有空间时不修改包裹内容。最高数量不是容量，不参与 `space` 计算。
6. 缓存腾位后，先按原版物品栏槽序继续处理所有专用残包，再评估补货。

### 服务端提交与回滚点

事务准备阶段捕获：玩家身份与本地访问门、包裹槽及完整内容、包裹收据标记、涉及物流格的 `filterRevision/onHand/capacity`、相关 `PendingInboundRecord` 版本。

提交顺序：

1. 复核原包仍在同一服务端物品栏且内容未变。
2. 在内存事务中计算包裹新内容、缓存增量、收据与待收结算。
3. 校验每个物品守恒、容量及整数边界。
4. 原子应用本项目玩家数据与包裹栈变更，然后标记持久化与客户端同步。
5. 提交成功后才触发下一轮残包处理和补货评估。

在步骤 4 之前失败，所有对象保持原样；步骤 4 内任何写入失败，恢复准备阶段快照并返回 `RETRY_REQUIRED`。跨玩家附件与原版玩家物品栏的崩溃落盘顺序必须通过 `SPK-DATA-01`；未通过前不得宣称断电级原子性。

## 按格手动重置

输入为服务端当前玩家、`cellIndex` 与期望过滤修订，而不是客户端提交的物品或数量。服务端复核该格当前 `ItemVariantKey` 和修订，删除该变体／修订的全部活动 `PendingInboundRecord` 并写结构化重置日志；缓存、背包、包裹和外部运输均不改变。

重置完成后立即按当前 `N/L` 重新评估。若再次有真实可见库存，新请求必须重新消耗网络库存。旧包随后到达时照常按地址和容量处理；旧包不会因 demand ID 已重置而被销毁。

过滤变更要求缓存现货为零，并先执行清除过滤事务。该事务同步删除旧物品的本地待收记账，但不撤回、删除或改写任何真实包裹；随后才可设置新过滤。旧物品迟到而新格不再匹配时，实物留在原包，不写入其他格。

## 边界条件

- `minimum` 必须不大于实际容量；负数、溢出、未解锁格及失效 `filterRevision` 安全拒绝。
- 一个玩家同一 `ItemVariantKey` 只能有一个物流格；同 ID 不同组件可分别占格。活动待收每精确变体最多 4 条、总计最多 144 条，不保存完成或重置历史。
- 取出物资导致频繁缺口时，同一服务端 tick 内合并为一次评估；待收覆盖期间不重复请求。
- 多玩家竞争网络库存时，库存查询不视为预留；只按各自请求实际受理结果建立本地记录。
- 普通背包的散装同类物品永远不减少缺口，也不自动转入缓存。
- 玩家死亡、卸下、解绑或换网不清待收；未佩戴期间不处理新到包。仅解绑但仍有效佩戴时，本地访问继续有效，可处理迟到包但不能发新请求。
- 玩家改名后，旧名字地址的真实包裹不再精确匹配当前地址，本模组保持原包不动；待收只能由玩家手动重置，不做名字历史猜测。
- 玩家手拆、移出或耗尽残包后，从当前真实物品栏重建残包提示；不得保留固定槽号或永久“等待腾位”布尔值。
- 单个专用包裹含多种已配置物品时分别入格；某一格满不阻止其他可接收内容入库。
- 解码异常、提供者模组被移除或版本改变时保留原包裹数据，不把失败内容当空覆盖。

## 必须先完成的 Spike

### `SPK-CREATE-01`：Create 请求与实际受理边界

**问题：** 固定源码中的库存摘要和 `broadcastPackageRequest` 不是稳定公共收据；其成功值不能证明足量出库。

**通过门槛：** 锁定实际 Create 构建后，选取同一 `itemId` 的两个精确组件变体 A／B，在隔离网络中分别以 A 库存 0、40、128 请求 A 缺口 128，同时保留 B 库存。证明：查询与请求只计算／取走 A，B 不进入请求包；库存 0 不产生本地待收；可见 40 时至多提交 40；请求包中的 A 组件逐值不变；一次核心评估只调用一次真实请求入口；没有直接增加玩家缓存。若无法取得可靠“受理”边界，只能把返回限制为可手动重置的请求承诺；若无法保证组件精确身份，则 A 进入 `ITEM_IDENTITY_UNSAFE` 且不发单，不能用裸 ID 请求后把 B 卡在残包。

### `SPK-PLANE-01`：纸飞机原生运输与完整包裹交接

**问题：** 用原生设施与定位条件运输 `FMP@玩家名` 包裹，能否保持完整包交接；预拆模式不在缓存收包边界内。

**通过门槛：** 记录 Package Couriers 构建及原生定位／装配／发运条件；按原模组方式选择完整包模式，从真实 Create 网络送入玩家普通物品栏并收入缓存。卸下后 FMP 不收包，原生运输与目标登记不被修改；重新佩戴处理已有匹配包。预拆模式的散装物不被缓存扫描，也不伪装为缓存到货。先整理用户已有实测，只补未覆盖项，不为本项新增目标适配器。

### `SPK-BEE-01`：运输蜂完整包裹、成员资格与背包条件

**问题：** 原生路径检查网络成员并把整包放入普通背包；须从现有游戏记录核对构建、区块及满背包行为，只补未覆盖项。

**通过门槛：** 锁定 Mobile Packages 构建；网络成员能收到 `FMP@玩家名` 完整包裹，非成员不能借地址收货；背包有空间／全满、同维度／换维度、发货端区块加载／卸载分别记录真实结果；任何失败都不被 FMP 记为已入缓存。

### `SPK-PROVIDERS-01`：双提供者共存

**问题：** 两个模组共同安装时，原生目标与工厂路线是否正常共存，FMP 是否仍只发一次请求；这些结论须有具体组合记录。

**通过门槛：** 在同一实例分别跑纸飞机路线、蜂路线及两路线同时可用；对一次缺口捕获 Create 请求调用次数必须为 1；禁用或移除一个提供者后另一个仍可完成闭环；服务端日志和类加载无缺失可选类错误；普通地址包裹不被本模组处理。

### `SPK-INV-01`：玩家物品栏到包发现

**问题：** 已读源码未确认一个通用、稳定的“包裹刚插入玩家物品栏”事件，也未验证向包裹写入本模组持久收据标记的兼容性。

**通过门槛：** 采用架构规定的“玩家主物品栏变更 hook + 每 20 tick 后备扫描”，使两个提供者正常交付的包裹最迟下一服务端 tick 被处理；刻意绕过 hook 的加载残包最迟 20 tick 恢复。同一包裹重复发现 10 次只结算一次到达；手动移出／拆开后提示最迟 20 tick 消失；无 JEI、无任一运输模组时核心仍可启动。hook 只负责置脏，不直接改缓存，正确性仍由有界扫描和幂等事务保证。

### `SPK-PKG-01`：包裹部分改写与保存切点

**问题：** 包裹组件能否在保留地址／订单信息的同时安全部分改写；玩家缓存与原版玩家物品栏的落盘切点能否用收据和事务日志守住。

**通过门槛：** 覆盖 9 槽、多物品和残包重复扫描，证明一个整包事务只写一条覆盖全部物品的日志，且地址与第三方订单信息逐字段不变；在“PREPARED 后、包裹减少后、缓存增加后、COMMITTED 后”四个受控中断点重载隔离存档，每次 `包裹内实物 + 缓存现货` 都与事务前基线完全相等或与完整提交后的等量转移结果相等，既不增加也不减少，同一收据不二次结算。非终态日志只允许封锁并报告异常，不能靠猜测、默认清空或接受显式丢物通过；任一切点无法守恒即阻塞 M3。

## Given / When / Then 验收

1. **Given** 玩家缓存 96、最低 128、无待收且网络可见同物 100，**When** 补货评估提交成功，**Then** 只创建一笔 32 的真实 Create 请求和一条 32 的等待记录。
2. **Given** 上述格已有有效待收 20，**When** 再次评估，**Then** 只请求剩余 12；已有待收 32 时不再次广播。
3. **Given** 网络可见库存为 0，**When** 连续运行 200 tick，**Then** 缓存不增加、无等待记录、无每 tick 空单，显示灰色下箭头。
4. **Given** 缺口 128、网络可见 40，**When** 请求受理，**Then** 本次至多登记 40；收到 40 后若网络仍空，剩余缺口显示无库存而不是虚构 88 在途。
5. **Given** 纸飞机与运输蜂均安装并可用，**When** 同一格从 128 降到 96，**Then** 核心只广播一次 32 请求；分别沿两种工厂路线均可真实送达完整包裹。
6. **Given** 纸飞机按原生条件能定位当前玩家，**When** 玩家佩戴或卸下供应链坠，**Then** FMP 只切换自身缓存操作，不登记、撤销或改写原生目标；完整匹配包只有在本地访问有效时入库。
7. **Given** 运输蜂路线和非网络成员，**When** 使用相同地址尝试配送，**Then** 由原模组判断成员条件，FMP 不伪造成员、不因请求成功虚增缓存；若另经其他路径取得真实匹配包，仍按本地收包规则处理。
8. **Given** 当前玩家收到地址完全匹配、内含 32 个已配置普通物品的完整包，且格有 32 空间，**When** 本地收包事务提交，**Then** 包内容减少 32、缓存增加 32、包空后消耗，物资总量不变。
9. **Given** 包内有 64、格只剩 20 空间，**When** 收包，**Then** 缓存只增加 20，原包保留 44 和同一收据；重复事件不再次结算到达。
10. **Given** 残包 44、玩家从缓存取出 30，**When** 缓存变化触发处理，**Then** 先从残包转入 30，再计算补货；不会先请求 30。
11. **Given** 残包被玩家手动拆开或移出主物品栏，**When** 下一次有界重扫，**Then** 残包等待提示消失，散装物不自动计入缓存，也不重建原包。
12. **Given** 玩家按格重置 32 待收，**When** 重置完成，**Then** 缓存和世界实物均不变；随后新请求真实扣网络库存，旧包迟到仍按实际容量入库。
13. **Given** 已重置旧包在新请求后迟到，**When** 新旧两个包依次进入背包，**Then** 两个真实包均按内容处理，不因 demand ID 丢弃；等待数量不出现负值，缓存装不下的余量各留原包。
14. **Given** 同一专用包裹的插入、槽变化和周期扫描在一 tick 内都触发，**When** 服务端处理，**Then** 该包的第一次到达只结算一次，实际内容最多转移一次。
15. **Given** 玩家卸下饰品或出现多网冲突，**When** 专用包到达或旧菜单发送重置／收包操作，**Then** 不自动拆包、不改待收；解除冲突并重新佩戴后先处理现有包再检查补货。
16. **Given** 地址为普通地址、其他玩家地址或纸飞机预拆后的散装物，**When** 它进入背包，**Then** 本模组不修改、不扫描同类散装物补救。
17. **Given** 包中同时含已配置精确变体、同 ID 异组件变体、模板超限物品和没有过滤的物品，**When** 收包，**Then** 只移动完整匹配且可安全编码的部分，其余内容及组件原样保留。
18. **Given** 玩家换到绑定另一网络的饰品且旧待收仍覆盖缺口，**When** 恢复有效佩戴，**Then** 不向新网络重复采购；按格重置后才按新网络重新评估。
19. **Given** 一个或两个可选运输模组未安装，**When** 游戏启动且玩家具备有效网络绑定和 Create 库存，**Then** FMP 不加载运输模组类、不阻止真实请求；自行取得的完整匹配包仍能入缓存，未取得时维持待收而不猜测运输原因。
20. **Given** 玩家有效佩戴但所有供应链坠均未绑定，且背包中已有当前专用地址迟到包，**When** 本地扫描运行，**Then** 包按过滤与容量正常入库；系统不查询网络、不发新请求。
21. **Given** 网络同时有 40 个满气铜背罐和 1 个半气同 ID 背罐，**When** 满气变体过滤请求 32，**Then** 可见量与出包只使用满气变体且气量组件不变；若目标 Create API 无法区分组件，则返回 `ITEM_IDENTITY_UNSAFE`、不发单且两种实物均不改变。
22. **Given** 专用地址包裹被构造为超过 9 个内容槽、负数或高于物品原生堆叠上限，**When** 扫描到该包，**Then** 返回 `PACKAGE_UNSUPPORTED`，缓存、待收、收据和原包数据全部不变并写限频诊断。
23. **Given** 包裹已有归属 A 的收据，但实体位于 B 背包或收据地址与包裹当前地址不一致，**When** 扫描，**Then** 返回 `PACKAGE_RECEIPT_MISMATCH`，不把收据改成 B、不移动内容、不结算任何待收。
24. **Given** 玩家活动日志已达到任一上限，**When** 新专用包被发现，**Then** 返回 `JOURNAL_BACKPRESSURE` 且四类状态全不变；下一次成功保存清理终态日志后，同一原包可被正常重试一次。
25. **Given** 两格分别配置同 ID 的组件变体 A／B 且均有待收，**When** 只收到 A 包裹，**Then** 只结算 A 的待收并只增加 A 格；B 的数量、待收和过滤修订均不变。
