### 补货与运输的职责边界（2026-09-03）

**用户已明确：** 不涉及退货时，两种运输模组各按自己的原生方式派送，本模组不需要专门接管运输。供应链坠只负责向绑定的 Create 网络请求真实包裹，以及包裹到达玩家原版物品栏后的缓存处理；不会代替原模组定位器、登记／撤销其目标、管理蜂成员、从打包机截包或直接派出载具。玩家照原模组规则准备设施、定位工具、成员条件和运输材料。

**由此直接推出：** 是否安装某种运输模组、是否持有原生定位器、成员条件或路线是否可达，不再是 FMP 补货请求门；本模组不宣称能诊断这些外部状态。新请求仍严格校验有效佩戴、饰品网络绑定、Create 网络及库存／请求结果。已有待收仍只代表本地等待，不保证载具已经出发；没有送达时不自动重置、赔付或追踪。

T08／T09 改为纸飞机／运输蜂的原生运输联调与验收，保留双运输真实包裹测试，不以新增适配器作为完成条件。若出现可复现的本模组交接问题，执行者先报告实际失败位置；普通核心缺陷按已定规格修复，需扩张到外部运输行为时再讨论，不预先建设兼容层。JEI 的过滤与配方转移仍按原计划实现。只有后续退货才研究使用玩家运输格里的纸飞机零件／运输蜂主动发运，既定一次性蜂规则不变。

**证据边界：** 用户在[团队通信](团队通信.md)报告当前实测补货不需要专用适配；这是用户游玩反馈，不自动等同于 C0—C5 全矩阵已完成。执行者整理已有版本、搭建条件与测试记录，只补未覆盖项，不要求用户无理由重跑已通过流程。

## 0. 一句话定义

> 为 Create 玩家提供按上下限自动补给的个人物流缓存，通过饰品访问，以真实包裹运输。

## 1. 核心愿景

### 为什么做

工厂已有库存统计、打包和运输能力，玩家外出建造、合成时仍需反复点单、收包和整理。终端让玩家为缓存设置物品过滤、最低数量和最高数量：缓存不足时请求物资，后续在缓存过量时退货。

### 成功的样子

玩家首次使用终端建立个人缓存时，背包左侧的物流格为空；之后换用其他饰品，仍访问自己的已有库存与设置。把可安全编码的物品从背包拖进去，会以该实物的物品 ID 和完整持久化组件设置精确过滤，并存入这批真实物资；从 JEI 拖进去则只设置同一精确模板。组件状态不同就是不同变体，不在一个格里混存。悬停格子、点击角落的小点后，可展开 Create 风格的双端滑条设置最低／最高数量。新个人记录的两端初始都不活动，不会因为刚设过滤就自动发单。

绑定网络并启用最低数量后，缓存达到补货条件时，工厂生成真实包裹，运输交给已有模组。带有 `本模组指定的包裹地址@玩家名` 标记的完整包裹进入玩家物品栏／背包后，由终端立即解包到缓存；普通包裹不接管，终端不追踪运输途中去了哪里。玩家取出正常堆叠的物品即可施工，合成/开火或其他消耗物品的操作也能自动调用缓存原料。

格子角落用箭头显示待收、缺货等状态。包裹一直不到时，玩家可以手动重置在途记录，随后按正常缺口重新请求；系统不自行判断丢包或赔付。退货恢复研究，使用最高数量条件、运输物格与返回地址，不能出发时物资继续留缓存，不自建全局配送系统。上段“开火或其他消耗”按第 4.2 节逐项验收，不是全模组兼容承诺。

### 已确认的方向

- Minecraft 1.21.1 / NeoForge；名称使用本文件标题和中文名。
- 这是 Create 附属模组。DSP 只提供灵感，不要求完整复刻其界面、升级树或机制表达。
- 通过可穿戴物品访问个人物流缓存，并配置物流网络。装备时在背包左侧显示物流格，目标为两列布局；饰品本身不持有该玩家的物资与格子设置。
- 每件饰品只绑定一个网络，可以清除后重新绑定；不同饰品可以携带不同网络配置。换饰品只改变发单入口，不转移个人物资、格子、升级或已有待收记录。
- 首个可玩版本暂时必需 Create 与 Curios，只提供饰品 **供应链坠 / Supply Chain Pendant**。无 Curios 的 **供应链甲 / Supply Chainmail**、**供应链盔 / Supply Chain Helm**及装配／拆卸后置；名称均已确认，见第 4.5 节。
- 未佩戴有效饰品时，不显示物流界面、不能存取或自动取料、不启动补退货、不自动拆包或续收残包；仅携带饰品不激活。物资、设置及待收记录保留，重新佩戴先处理已有专用包裹，再检查补货。
- 每格可以设定物品过滤、最低数量和最高数量；补货与退货分别由两端控制。
- **只统计缓存内数量，不统计普通背包、快捷栏和副手。** 从缓存拿出去就扣减；存回来就增加。
- 数量规则为**不足时补回到最低数量，超额时退回到最高数量**。只补／退相应差额，不增加第三个目标量；恰好等于最低数量时不新增补货，恰好等于最高数量时不退货。
- 玩家首次建立个人缓存时格子为空；更换饰品不清空已有库存或配置。从背包拖入可安全编码的物品时，以服务端真实来源栈的完整组件设置过滤并存入真实物资；JEI 拖入只设置其提供的精确模板。
- 同一精确物品变体只允许设置一个物流格；同一物品 ID 的不同弹种、气量、耐久、附魔或其他组件状态属于不同变体，可以分别占格。所有入口都按完整身份检查重复。
- 允许带持久化组件的实物进入缓存；不再剥离额外 NBT／组件、不再二次确认改成默认模板。一个格内所有单位必须组件完全相同，组件改变后须进入对应变体格。无法完整往返编码或规范模板超过 1,024 字节时整体拒绝，来源不变。
- 悬停格子时角落出现小点，点击展开 Create 风格双端滑条；左端为最低数量，右端为最高数量。
- 两端初始分别位于最左／最右且不活动，即补货、退货默认分别关闭。
- 收货入口是玩家本地物品栏／背包中的完整实物包裹。只自动解包当前玩家的本模组专用地址包裹，内容存入独立缓存。`FMP@当前玩家名` 已通过两种运输源码的地址解析核查；原生目标、蜂成员条件及完整包交接的具体测试组合由联调记录说明，不要求 FMP 另行接管这些条件。
- 收货采用部分入库：只提取匹配格当前实际容量能容纳的数量，剩余内容留在原包裹中，不要求载具原路返回。缓存腾出空间后，自动优先从背包里的专用地址残包继续转入，再按更新后的缓存数量检查补货；普通散装物品仍不参与统计。
- 不判断包裹是否丢失，不按超时自动重置、赔付或重发；提供类似工厂仪表的手动重置在途功能。重置只清等待记账，真实旧包仍存在，后续补货仍消耗网络物资。
- 格子角落使用绿色下箭头、灰色下箭头、红色上箭头和灰色上箭头，含义见第 4.4 节。上箭头随当前退货研究处理，不能显示不存在的提货或签收状态。
- 格数、单格容量与插件槽按 **1—5 级**升级，依次为 **9／128／1、16／256／2、24／512／3、30／1,024／4、36／2,048／5**。等级归当前缓存：本件缓存随普通坠子，个人缓存随玩家；数值作为首轮实玩默认，后续平衡修改须另行记录。
- 库存和格子设置归玩家；饰品提供访问能力与本件网络配置，不持有个人缓存。卸下、丢出或更换饰品不会重置个人数据；他人拿到饰品只能访问自己的缓存，不会取得原佩戴者的物资。饰品遗失或销毁本身也不删除个人数据；死亡和重生同样不改变缓存物资与格子状态，不受世界“死亡不掉落”设置影响。
- 玩家直接用手放置／使用物品采用“先取出真实物品”的方案 1；自动取料的覆盖目标是其他物品消耗操作。已明确包含原版合成、标准投射物弹药链和 TaCZ 弹药；T12 接入共享协议而非弓弩物品 ID，第三方若绕开标准协议则以独立适配器接入统一消费服务，侵入式接入时先保原版。
- 背包页有一个自动取料优先级小开关，在“背包优先／缓存优先”间切换；首选来源不足时另一边补足。偏好归玩家保存，仅对已支持的自动取料生效，不改变补退货只统计缓存的口径。
- 先做补货；退货按新批注恢复研究，方向为运输物格、返回地址和出发前检查。运输蜂采用格内原蜂不消耗、派出一次性蜂的方向，不产出普通蜂；选站和回退先沿用原生行为，暂不专门防串网，待实际游玩观察后再决定是否适配。纸飞机单独适配，仍不自建全局配送系统、不默认新增退货站。
- 大量补退货沿用 Create 打包机的连续分包方式：每包最多 9 个物品槽，各槽遵守原生堆叠上限，不另造巨型包裹。

### 当前不扩展的方向

**已确认不做：** 从零开发纸飞机／运输蜂式全局配送系统；判断外部包裹是否丢失并自动恢复或赔付。退货当前研究以现有运输的随身发运入口为主，不把首轮审查的新增退货站、站内预留、全程回执自动当作当前架构。

其余保持讨论聚焦的建议边界如下，不是对未来功能的永久否定：

- 不重做 Create 的仓储和工厂生产系统，不为模仿 DSP 而重复添加配送站。
- 不承诺直接从虚拟格放置所有方块，也不承诺所有模组机器都能读取缓存。
- 不以瞬间从远方仓库扣料的方式代替包裹运输。
- 首个可玩版本不做退货、TaCZ、无 Curios 护甲入口、带插件背包访问、EMI、其他工作台全面取料或正式序列组装。退货紧随基础补货之后；其余按后续阶段处理。首版可以简化升级制造，不据此把简易合成当成正式工艺或取消既定后续方向。

## 2. 用户与场景

### 核心场景

玩家准备在基地外建设一条 Create 生产线。他首次通过终端建立个人缓存，将背包里的普通传动杆拖到一个空格，过滤与第一批库存同时建立；再从 JEI 拖入传送带图标设置另一个过滤，该格实际库存仍为零。绑定网络并通过滑条启用最低数量后，系统才根据缓存情况请求真实包裹。物流蜂或纸飞机按自身规则送达；完整的专用地址包裹进入玩家物品栏／背包时，终端将可接收内容解入当前玩家的个人缓存。

没有可用配送站或缺货时，格子显示灰色下箭头；存在本地待收记录时显示绿色下箭头。这不是对载具实时位置的保证。如果一直未收货，用户可手动清除在途记账，让后续补货检查重新处理缺口；旧包稍后到达仍按实际包裹与地址处理，不因记录已重置就丢弃。

施工时，玩家从缓存取一组物品到快捷栏，缓存数量立即减少，达到最低数量条件便触发补货检查，不必等到方块被放置。需要原版合成、用弓射箭或给弩装箭时，缓存也可以提供允许存储的原料／箭矢。只有真实取出或消费成功才扣缓存，查找原料、取消蓄力不能扣；已经从缓存装入弩的箭也不能在发射时再次扣缓存。背包页小开关决定先取普通背包还是缓存，首选不足时由另一边补足。

结束施工，把剩余物资放回缓存。退货实现后才按最高数量处理超额部分；当前规划版本只安全保留物资，不假装已经寄出。卸下终端后，个人库存、设置和升级仍保留；换用绑定另一网络的饰品，访问的仍是自己的数据，新请求改用该终端绑定的网络并重新校验 Create 网络。把已绑定饰品交给另一个玩家时，饰品携带的 Create 网络绑定一并转交；对方仍只访问自己的缓存，不继承原玩家的物资、格子、升级、偏好或待收。运输蜂成员资格等第三方身份条件由原模组按新佩戴者判断，FMP 不代查、不改写。

“只统计缓存”“补回最低、退回最高”、地址收包、按格手动重置及有效佩戴才启用整套系统已经确认。首个可玩版本包含 Curios 供应链坠、原版合成、JEI 原版配方填充、标准投射物弹药取用、五阶段，以及纸飞机／运输蜂分别验收。退货下一阶段实现；TaCZ、护甲入口和正式序列组装后置。

### 术语

| 术语 | 本项目中的含义 |
| --- | --- |
| 终端／饰品 | 提供当前玩家缓存访问能力，并携带本件单一网络绑定的可穿戴物品；不拥有玩家库存、格子设置或升级 |
| 个人物流缓存／幽灵物品栏 | 归玩家的独立真实库存，以虚拟计数表示；更换饰品不另建一份，不是无限物品来源 |
| 物流格／幽灵格 | 一个精确物品变体及其实际库存、最低／最高数量、容量和状态的界面单位；同一精确变体不重复设置 |
| 过滤物品 | 说明该格接受什么物品的模板；设置模板不等于投入或生成物资 |
| 最低数量 | 启用后，缓存不足时按差额补回此值；等于此值时缺口为零，不新增补货 |
| 最高数量 | 启用后，缓存超过此值时按差额退回此值；是物流策略阈值，不是物理容量 |
| 实际容量 | 格子能持有的真实物资上限，可升级；关闭最高数量不代表无限容量 |
| 在途数量 | 本地尚在等待的请求数量；用于防重复发单，不算缓存现货、不可用于合成，也不保证外部包裹仍在飞行 |
| 手动重置在途 | 用户主动清除等待记账；不增加物资、不撤回或销毁真实包裹，后续仍按正常缺口请求 |
| 精确物品变体 | 物品注册 ID＋完整持久化数据组件状态，数量不属于身份；同 ID 不同组件可分别占格，存取和物流均原样保留 |
| 专用包裹地址 | `v0.1.0` 固定使用 `FMP@玩家名` 作为本地拆包标记；不授予网络或其他玩家缓存的访问权限，若实测冲突则阻塞对应兼容并修订计划，不在运行时猜地址 |
| 原版背包 | 玩家普通物品栏，包括快捷栏；其中物资不纳入本终端的补退货统计 |
| 配送提供者 | 物流蜂、纸飞机等负责真实包裹运输的外部模组；补货不预设 FMP 专用兼容层 |
| 自动取料 | 为玩家的合成、武器等已支持操作补充缓存中的真实耗材来源；不代替操作本身，也不让世界中的所有机器自动抽取个人缓存 |
| 网络冲突 | 多件已佩戴且启用的终端具有不同网络绑定；全部暂停使用，保留手动禁用入口，同网多件不冲突也不叠加 |
| 运输物格 | 当前退货研究中的专用格，放现有载具／耗材，角落设置入口配置返回地址；不是新运输系统 |
| 访问插件 | 后续为带插件的背包增加访问本模组缓存的入口；初期不实现 |

## 3. 已有方案与差异

本节是针对已知候选的核查，不是“整个生态没有竞品”的结论。

| 已有内容 | 已核实的能力 | 与本项目的关系 |
| --- | --- | --- |
| Create 包裹物流 | 库存汇总、查询和包裹请求；源码有 `getSummaryOfNetwork`、`getStockOf`、`broadcastPackageRequest` | 作为库存与发单基础，不另造一套网络 [S1] |
| Create: Mobile Packages | 物流蜂、玩家地址、便携库存终端、退货槽；到货路径把完整包裹交给玩家背包 | 与纸飞机共同列入初期测试；本项目新增配额维护、缓存和自动取料 [S2]、[S3] |
| Create More: Package Couriers | 纸飞机长距离／跨维度运输；说明要求基地侧区块加载 | 用户偏好的初期配送测试对象，与蜂分别验收；具体行为受外部模组与服务器配置限制 [S4]、[S5] |

本项目的差异应体现在“缓存物品过滤与上下限 → 自动补差 → 包裹入缓存 → 取用与合成”的完整流程，而不只是新增一个便携库存终端。

### 4.1 普通取用：采用方案 1

解包后的到货物资留在缓存。玩家取出真实物品后，按原版行为放置和使用；也能把允许存储的普通物资存回缓存。支持真实取出与存回，以及采用原版物品栏鼠标习惯，均已确认。

**交互默认已确认：** 缓存与普通物品栏之间的取存遵循原版物品栏鼠标习惯，包括普通点击、右键拆分和 Shift 快速转移的对应语义；虚拟计数大于原生堆叠上限时，每次转出仍只形成合法原生堆叠，不能把整个千级计数塞进鼠标或普通槽位。

**已确认：** 转移成功时缓存数量就改变。从缓存取 64 个到快捷栏，缓存立即少 64；把 64 个存回来，缓存立即多 64。不再追踪取出物品在普通背包中的剩余数量，也不扫描玩家背包来抑制缓存补货。

### 4.2 自动取料：原版合成、JEI 原版配方填充与投射物弹药

**已确认目标：** 覆盖除玩家直接用手以外的物品消耗操作，明确包括原版合成、投射物弹药和 TaCZ 弹药。T12 不按弓／弩物品 ID 特判，而是接入 `LivingEntity#getProjectile` 与 `ProjectileWeaponItem` 的共享查询／消费协议；实际沿用该协议的第三方物品应无需逐物品登记即可获得缓存弹药，并以非原版测试子类验收。若第三方自写消费协议且适配需要侵入式修改，先保障原版，不为兼容重做对方系统。

**范围工作解释：** 这里针对玩家使用配方、武器等时本来会从随身物品中获取耗材的操作，不是让世界中的所有机器获得读取个人缓存的权限。手持方块放置、直接用手消耗物品仍先取出实物；耐久、能量和流体也不自动算作物品数量接口。

| 操作 | 当前交付范围 | 不改变的规则 |
| --- | --- | --- |
| 原版背包 2×2、工作台 3×3 合成 | 首版保障；原版合成范围的具体展开 | 配方、结果、余物与真实材料守恒；不从空白界面猜产物 |
| 标准投射物弹药供给 | 首版保障；原版弓弩及沿用标准链的其他玩家物品使用缓存允许存储的弹药 | 不按物品 ID 特判；不改变蓄力、装填、弹丸、附魔与创造模式原有规则 |
| TaCZ 的备弹取用 | 条件兼容目标，实施前通过版本与物品身份核查，原版主线优先 | 不把普通弹匣枪改成背包直读，不改枪包／服务器配置来假装兼容 |
| JEI 配方填充 | 首版包含向背包 2×2／工作台 3×3 的填料，接口仍需实现验证 | 与 JEI 拖入过滤分别验收；不包含所有 JEI 机器类别 |
| EMI、其他工作台或自写耗材工具 | 后续按具体消费协议扩展适配器 | 未核实的接口不宣称通用支持；不全局劫持 `ItemStack` 数量变化 |

带药效等额外数据的箭矢仍受缓存物品策略限制；不能为了弓弩支持而清除药效。它们在普通背包中的原有使用不受影响。弓、弩、枪械自身的附魔／状态不是放入缓存的耗材，不因缓存拒收特殊材料而被改写。

**已确认的配方入口：原版配方书或者 JEI。** 在原版 2×2／3×3 合成范围内，玩家选配方后可以使用缓存现货，不必先逐种搬进普通背包。手动已有布局及具体填料机制仍按真实转移、单次扣料和原版结果规则实现。JEI 配方填充与过滤拖入分别测试，原料来源顺序由背包页的小开关控制。

#### 背包页自动取料优先级开关：已确认

用户提出“可以在背包页留个小开关”，用于选择自动取料来源的优先顺序：

- **背包优先：** 先使用普通背包中的可用材料，不足部分从缓存补足。
- **缓存优先：** 先使用缓存中的可用材料，不足部分从普通背包补足。

这是取料优先级，不是“只准使用某一边”的锁定。两边总现货仍不足时不能透支，不把在途或基地库存当作可立即使用的材料。它作用于已支持的合成与弹药取用；TaCZ 等只有通过适配验证后才可列为可用功能。

来源优先级不授权替换材料或弹种：先满足配方／武器及玩家明确选择的物品条件，再决定从哪处取同一需求的材料。不能为了“缓存优先”把指定弹种改成别的弹种。

由既有个人数据与佩戴规则直接推出：偏好跟玩家保存，换饰品、卸下或死亡不重置；未佩戴时小开关随物流界面一起隐藏，不产生缓存访问。切换本身不搬动、退回或重新扣除任何物品，只影响后续取料顺序；它不控制快捷栏续栈，也不改变补退货的数量统计。

**界面与默认值：** 在背包页物流面板附近显示小开关，文字或悬停提示明确标出“取料：背包优先／缓存优先”。新玩家初始值确定为背包优先；最终位置和图标由 UI 方案落实，玩家选过后保留其偏好，不再反复重置。

#### 现货、取料与合成守恒

合成只使用已经在玩家普通库存或终端缓存中的现货。在途包裹和基地网络库存不能被当作可立即扣除的原料；不够时应提示不足，等待正常物流补给。

只有取自缓存的原料才会减少缓存数量并参与其补货检查；仅消耗普通背包中的原料不会直接改变缓存数量。这不妨碍合成界面把两处现货都作为取料来源。

首版机制已固定为“服务端把背包与缓存中的真实原料转入原版 2×2／3×3 合成格”。缓存原料在成功进入网格时扣减；关闭界面后的材料按原版菜单规则回到普通背包，不自动退回缓存。结果与配方余物继续由原版流程处理，不能同时在结果提交阶段第二次扣款。完整事务见[合成规格](开发计划书/specs/05-原版合成与JEI取料.md)。

验收必须覆盖：

- 普通库存与缓存共同提供原料，所得物品与剩余原料数量正确。
- 两种优先模式分别验证首选充足、首选不足、另一来源补足及总量不足；切换本身不改变两边库存。
- 批量操作中切换不能重复扣料；换饰品、死亡重生和保存重载保留偏好，未佩戴时不能通过旧界面使用缓存。
- 配方含桶、瓶或其他余物时，余物不丢失、不复制。
- 批量合成不会超出实际原料和结果容纳能力；不足时停止。
- 关闭界面、改变配方或中途卸下终端，不会吞物、复制或继续使用失效终端。
- 原料组件匹配遵循配方与物品语义，不能只按物品 ID 合并。

#### 投射物与枪械的取料时机

以下由“真实转移才扣缓存”和“只补充耗材来源”推导，作为实现必须验证的守恒条件：

- 查找可用箭矢、客户端预测、反复拉弓或取消蓄力不直接扣缓存。普通射击在实际消费提交时扣除来源；实际消费为零时不额外扣料。
- 弩从缓存成功装入箭矢时，物资已转移到武器，缓存相应减少；之后射出已装弹丸不能再扣一次。多重射击的扣料遵从原版逻辑，不按弹丸实体个数重复计费。
- 缓存取料不会取消装填时间、提升弹匣容量或绕过无弹检查。成功装入武器的物资已经离开缓存，之后卸下饰品不删除它，也不把它补回缓存。
- TaCZ 常规弹匣枪若得到支持，应在取出备弹并装填时处理缓存转移；只有枪械原本就是背包直读模式时才适配相应开火取料，不通过改枪包切换模式。
- 任何适配都须在服务端复核有效佩戴、材料身份与实际数量，不能用客户端显示的“有弹药”作为扣库或发射凭据。

**已核实的技术边界：** NeoForge 1.21.1 的 `LivingGetProjectileEvent` 提供共享查询入口，Minecraft 的 `ProjectileWeaponItem.draw/useAmmo` 提供共享消费链；T12 可按协议适配并让沿用该链的子类自动受益。事件本身仍不是完整库存事务，最终提交点须单独验证。`ItemStack.shrink/split/consume` 缺少消费者、需求与取消语义，不能作为全局自动补料入口。TaCZ 1.21.1 本次核到的是非官方移植，弹种通过 `CUSTOM_DATA` 中的 `AmmoId` 区分，备弹检查和提取有多个路径。这些是可研究入口，不代表已完成兼容。证据见[自动取料兼容边界核查](research/2026-08-29-自动取料兼容边界核查.md)与[T12 通用弹药消费入口核查](research/2026-09-02-T12通用弹药消费入口核查.md)。

**TaCZ 的后续闸门：** 精确组件变体已经解决缓存无法表示弹种身份的前置问题，但不等于完成 TaCZ 兼容。仍须锁定兼容的 1.21.1 NeoForge 构建，在不重写枪包、装填与射击流程的前提下验证弹种组件能稳定往返，并接入所有必要取弹、装填、弹匣和开火提交路径；不能清除 `AmmoId`、合并不同弹种或把“有一个 ItemHandler 接口”写成已经兼容。TaCZ 已明确后置，不再阻塞首个版本。

### 4.3 只统计缓存，按最低／最高数量触发

**已确认：缓存是独立容器，不是玩家全部随身物资的统计面板。** 原版背包、快捷栏与副手的数量均不参与缓存的补退货判断。之前建议的“缓存＋普通背包总量”已被用户否决，不再作为候选。

设 `N` 为缓存现货，`L` 为启用的最低数量，`U` 为启用的最高数量，`C` 为实际容量。

| 状态／条件 | 行为 |
| --- | --- |
| 还没有物品过滤 | 不生成物流请求 |
| 最低数量未启用 | 不自动补货，即使缓存为零 |
| 最低数量启用且 `N < L` | 核对在途订单后，按补回 `L` 的缺口发出请求 |
| 最低数量启用且 `N = L` | 缺口为零，不新增补货订单 |
| 最高数量未启用 | 不自动退货；实际容量 `C` 仍然有效 |
| 最高数量启用且 `N > U` | 按超出 `U` 的差额研究退货；只有运输可以出发并成功交接时才扣料，当前尚无运行实现 |
| 最高数量启用且 `N = U` | 没有超额物资，不退货 |
| 缓存在已启用的阈值条件之外 | 不因数量本身新增该方向的物流操作 |

补货检查不等于每次都发包；同一缺口已有订单时，不应重复发单。在途物资单独显示／记账，不能加进“缓存现货”数字，也不能借此把背包重新算回来。

**已确认的处理顺序：** 取用物资先实际扣减缓存；腾出的空间优先接收背包内专用地址残包的匹配物资，成功转入后再按更新的缓存现货核对缺口与在途，决定是否新发补货请求。这是先完成本地实物转移，不是把背包里的包裹或散装物资提前计入缓存。

**已确认：不足时补回最低数量，超额时退回最高数量。** 两端独立工作，无需第三个目标量。在对应端点启用、没有已覆盖该差额的物流操作时，补货缺口为 `max(0, L - N)`，退货差额为 `max(0, N - U)`。恰好等于最低数量时即使执行检查，缺口也是零，不发空订单；恰好等于最高数量时没有超额物资，不退货。

例如最低 128、最高 512，缓存有 96 且没有在途时请求 32；未来退货启用后，存回有 600 且没有待处理退货时退回 88。若已有相同缺口的有效在途 32，不再重复请求。**这些数字用于说明已确认规则，不代表预设值、容量或升级档位；退货当前不执行。** 已在途和已锁定的操作只用于防重复，不改变缓存现货数量。

在途记录仅维护本地待收数量。首版固定将 Create 请求入口成功接受的本次数量 `Q` 登记为请求承诺；这不等于载具已出发或网络已足量出库。第一次观察到真实专用包裹时，按其中受支持物资的实际数量从活动待收中结算一次；持久收据阻止同一包裹重复抵扣，未能入库的余货转为残包状态。请求失败不登记，用户按格重置可删除本地待收；不根据时间自动判断丢件。`SPK-CREATE-01` 只负责锁定目标 Create 版本的返回与调用语义，不能把接口验证改成免费补偿。缺货时保留过滤和缺口，不制造物资、不反复发空单。玩家存回物品后，迟到包裹可能使缓存超出退货阈值，须按实际库存与容量处理，不能静默丢弃内容。

#### 手动重置在途：已确认

- 提供类似工厂仪表的用户主动重置功能；不根据等待时长自动认定丢失、重置、赔付或重发。
- 重置按当前物流格执行，只清该物品的本地等待记账，不改缓存现货，不撤回或销毁已发出的真实包裹。首个可玩版本不提供全局清空全部待收；按钮放在该格设置入口内，具体像素由 UI 方案确定。
- 清除记录后，下一次正常检查按当前缓存缺口重新请求；新包仍由网络提供真实库存，不是给玩家补偿一份物资。
- 旧包迟到仍执行本地地址收包，不因没有未完成订单而拒绝或销毁。两次实际发货可能造成超额到货，但不会据此凭空生成或抹掉物资；未收下的内容要保留。
- 绿色下箭头依据尚未清除的待收记录，可能持续到收包或手动重置；它不承担判断载具仍在飞行的职责。

### 4.4 空格初始化、拖入过滤与双端滑条

#### 初始状态与拖入

玩家首次建立个人缓存时，左侧物流格没有过滤、库存为零，最低／最高端点都不活动。这是新个人记录的初始状态；已有数据的玩家换用新合成或转交来的饰品，不重置过滤、库存或端点状态。

| 操作 | 过滤 | 实际库存 |
| --- | --- | --- |
| 从背包把可安全编码的物品拖入空格 | 设为该实物的精确变体 | 转入实际存入的数量，来源同步扣除；构成第一批库存 |
| 从 JEI 拖入物品到空格 | 设为 JEI 栈的精确变体 | 仍为 0；JEI 提供模板，不提供物资 |
| 向已有匹配过滤的格子存回物品 | 保持过滤 | 仅完整组件相同才按成功存入量增加，并检查最高数量条件 |
| 尝试存入无法安全编码或模板超过 1,024 字节的物品 | 不设过滤，显示稳定拒绝原因 | 不接收实物；不降级为默认实例或剥离组件 |

JEI 拖入过滤与 JEI 向原版合成界面填料都是首版兼容目标，但必须分别实现与验收。JEI 不属于加载器依赖声明；缺失时仍通过背包实物设过滤和原版配方书取料，不自动扩展为 EMI 支持。

**格子唯一性已确认：同一精确物品变体只能设置一个格子。** 对已有完全相同过滤，从背包或 JEI 拖入另一空格时不能建立第二份过滤，界面定位并高亮已有格，来源实物保持原样；同一物品 ID 但组件不同的变体可以分别占格。用户主动存入已有精确匹配格时才转移库存。

刚设置过滤时仍不会自动补货，玩家需要启用最低数量并满足有效网络等发货条件。允许先配置过滤／数量再绑定网络；未绑定时显示原因，不删除配置。

#### 精确组件过滤

**已确认的最新规则：** 过滤模板保存物品注册 ID 与完整持久化数据组件，数量规范化为 1。背包来源由服务端读取真实菜单槽；设过滤与第一批实物转入同一事务提交。JEI 来源只提交有界 ghost 模板，不产生实物。任何路径都不得删除组件、忽略组件或把来源改成默认实例。

**可见语义：** 物流格按完整模板显示名称、图标、附魔光效和 tooltip；满气、半气与空铜背罐是不同过滤，组件发生变化后的实物只能存入对应变体格。首版不提供按组件范围或忽略字段的模糊过滤，也不把不同状态混在同一个 `long` 计数中。

**安全拒绝：** 模板必须使用注册表感知的物品栈编码完整往返，解码后仍与原栈同物同完整组件，规范化编码不得超过 1,024 字节。失败时显示“该物品数据无法安全存入物流缓存”或“物品数据过大”，来源、缓存和过滤全不变；不再存在“再次操作改为默认模板”的确认令牌。包裹外壳本来就携带地址和内容数据，必须先作为运输包装识别，再检查其中材料，不能作为普通材料过滤。

过滤设定、手动存入、Create 请求与包裹内容采用同一个 `ItemVariantKey` 和相等关系。无法接收的实物留在原包裹或手动存入的来源中，不能静默删除或转换后强行收下；部分入库规则见第 4.7 节。完整决策与 schema 迁移合同见[决策 0001](decisions/0001-精确组件物品身份.md)。

#### 格子角落的状态箭头

以下是用户确定的显示语义，不是对 DSP 或第三方模组接口已经验证的承诺：

| 显示 | 含义 | 当前边界 |
| --- | --- | --- |
| 绿色 ↓ | 有包裹在路上，等待补货到达 | 依据本地待收记录；不监控载具实际位置、不自动判丢失 |
| 灰色 ↓ | 需要补货，但配送范围内无可用配送站或站缺货 | 保留需求，等待可用；如何获得供应／可达信息待接口验证 |
| 红色 ↑ | 退货方向的运输活动 | 已恢复研究；随身发运时不能误称“载具来取货”或“基地已签收”，具体已知状态随适配验证 |
| 灰色 ↑ | 需要退货，但当前不能发运 | 研究覆盖缺载具、返回地址无效、目标不接收或提供者配置禁用；只显示实际知道的原因 |

“配送范围”与运输条件由原运输模组处理，不另做全图站点扫描系统，也不在补货 UI 中猜测路线、定位器或成员状态。`v0.1.0` 同格只显示一个主状态，优先级固定为：本地残包、已有待收、未绑定、异网冲突、网络不可见／缺货／忙碌／物品身份不安全、无缺口；tooltip 可同时列出本模组实际知道的次要诊断。设置小点、图标和文字的具体入口见[物流格界面与五阶段规格](开发计划书/specs/03-物流格界面与五阶段.md)。退货上箭头在 `v0.2.0` 实现前不显示为可用状态。

#### 已确认的数量设置方式

1. 鼠标移到每个物流格上时，格子角落出现一个小点。
2. 点击小点，展开 Create 风格的数量滑条。
3. 同一条滑条上有两个可拖动端点：左端为最低数量，右端为最高数量。
4. 两端初始分别位于最左与最右，并视为不活动；初始不补货、不退货。
5. 启用左端控制补货，启用右端控制退货；两方向可以分别保持关闭。

```text
新格默认：  ● 最低：关闭 ───────────────── 最高：关闭 ●
设置之后：  最低端点 = 补货条件          最高端点 = 退货条件
```

最高数量 `U` 是策略阈值，实际容量 `C` 是存储限制。必须允许在不超过 `C` 的前提下存到 `U` 以上，随后才有“超过最高数量就退货”的流程。存不下的剩余物资必须留在来源，不能因为滑条关闭就无限存储。

#### 已定交互与实现细节

- 最左／最右的不活动档分别规范化为最低 0／最高当前容量并明确显示“关闭”。有效的最低 0 和有效的最高容量均允许，但必须显示已启用标记，以启用开关而非位置区分活动与关闭。
- 活动数值遵守最低不高于最高；端点不互相穿越。数量的最大刻度随容量升级调整，但升级不应默默启用一个原先关闭的端点。
- 拖动时显示精确数值，并支持滚轮与直接数字输入，避免在千级容量上只能按像素猜数值。
- 设置点固定在格子右上：视觉 4×4、命中区 8×8，悬停显示“数量设置”；只有空光标且未拖拽时命中，携物拖入不被截走。键盘聚焦后 Enter／Space 打开，Esc 只关闭设置框。
- 缓存取空后保留过滤。物流格有真实库存时必须先取空，才能更换或清除过滤；不能直接覆盖、转换或吞掉原物资。

**非空格编辑已确认：** 有真实库存时先取空，才能更换／清除过滤；空格即使仍有旧在途也允许修改，不自动撤销真实旧包。晚到物资没有匹配的精确变体过滤时留在包裹中。精确变体唯一性与物资守恒规则不变。

### 4.5 个人缓存、饰品访问与身份

**已确认：物品设置与物资跟人走，具体网络绑定跟饰品走。** 格子过滤、最低／最高数量、启用状态、取料优先级与升级属于玩家个人记录；当前玩家使用饰品时读取自己的缓存。此前“库存随具体终端保留”及按终端永久 ID 组织库存的候选已被替代，不再给每件饰品建立独立库存或绑定原主人。最新的饰品网络绑定规则不改变个人物资归属。

由这一归属规则直接得到：

- 玩家 A 换另一件可用饰品，仍访问 A 原有的物资和设置；不能通过换饰品复制或清空库存。
- A 把饰品交给 B，B 访问的是 B 自己的缓存；A 的数据不随物品转移，也不会成为 B 的可用原料。若 B 从未建立个人记录，则 B 的初始格子为空。
- 卸下、丢弃、遗失或销毁饰品本身不删除个人数据；死亡和重生也不改变缓存物资与格子状态。重新获得访问能力后继续使用原有个人记录。
- 同一玩家的多件饰品共享个人库存、设置、升级和待收记录，不能对同一缺口重复发单。

#### 每件饰品的网络绑定

**已确认：** 一件饰品只能绑定一个网络；允许清除绑定，不同饰品可以绑定不同网络。因此“有且只有一个网络”按已绑定时恰好一个理解，清除后允许未绑定状态。网络配置归饰品，转交已绑定终端也转交其 Create 网络绑定；个人库存、格子、升级、偏好和待收归玩家，不随终端转交。Create 6.0.10 没有可复用的通用玩家 ACL，不能虚构“原绑定者个人授权”；运输蜂成员资格等提供者专属身份条件仍由原模组按当前佩戴者判断，不是 FMP 的新请求门。

| 场景 | 处理边界 |
| --- | --- |
| 玩家换成绑定另一网络的终端 | 个人缓存不变；新请求使用当前终端携带的网络绑定，并校验网络仍可用及 Create 请求入口接受 |
| 清除绑定 | 该终端不再发新网络请求；不清个人库存、不清旧在途，也不撤回已经生成的包裹 |
| 已有效佩戴但尚未绑定／网络不可用 | 由本地库存与网络请求分离直接推出：已有缓存仍可存取和供料，仅不能从不可用网络发单 |
| 旧网络包裹在换装／解绑后到达 | 有效佩戴时仍按玩家专用地址、允许物品、过滤与容量处理，不因来源网络已切换而吞包 |
| 饰品转交或原生运输条件改变 | 饰品的 Create 网络绑定随物品转交；接收者只访问自己的缓存，运输蜂成员资格等第三方条件由原模组按接收者判断；地址字符串或客户端 UUID 不能选择他人缓存或任意网络 |

**多终端冲突：已确认。** 同时佩戴并启用的终端若绑定不同网络，直接显示冲突，不能选择其中一件继续工作；须由玩家手动禁用某件，直到剩余启用终端不再包含不同网络。禁用不清绑定，不清个人缓存或待收记录。相同网络的多件不冲突，但仍只有一份个人库存和发单判断。

由“一个都用不了”直接推导：冲突期间暂停缓存存取、自动取料、收包及补退货；保留冲突列表和逐件禁用入口，避免无法解除冲突。若玩家把所有已佩戴坠子都禁用，缓存业务继续停用，但背包页保留只含终端列表和启用按钮的最小管理入口；没有佩戴任何坠子时才完全不显示本模组界面。未绑定终端不构成第二个网络；全部未绑定时仍按本地缓存可用、网络请求不可用处理。服务端必须执行同一规则，不能只在界面提示。

#### Curios 与后续护甲形态

**首个可玩版本已确认：** Create 与 Curios 为必需依赖，只实现 Curios 饰品入口。饰品正式名为 **供应链坠 / Supply Chain Pendant**；“便携物流终端”继续禁用为正式名。槽类型固定为 `necklace`，物品加入 `curios:necklace`，玩家槽数据位于 `data/create_feed_me_packages/curios/entities/player.json`；服务端只认实际 Curios 佩戴，普通背包携带不启用系统。

**后续名称与范围已确认：** 无 Curios 的胸甲和头盔形态分别为 **供应链甲 / Supply Chainmail**、**供应链盔 / Supply Chain Helm**，两者都保留为后续入口，不进入首个可玩版本。这些名称沿用 supply chain＋chainmail＋mail 双关，不重命名项目，也不预先限制基底材质。

**后续装配与拆卸规则：** 供应链坠与基底护甲合成后，仍访问玩家个人缓存，不另建护甲库存；原护甲数据和本件网络绑定须完整保留。引入护甲形态的同一阶段必须提供拆卸，返还当前护甲和供应链坠，保留拆卸时的耐久、附魔、绑定与禁用状态，不回滚旧快照、不转移个人缓存或升级。具体配方形式在该阶段的版本方案中确定。

**升级归属与数值：已确认。** 等级、格数、单格容量和插件槽都属于当前缓存。1—5 级依次为 9／128／1、16／256／2、24／512／3、30／1,024／4、36／2,048／5。普通供应链坠访问的本件缓存随坠子转交；供应链坠·私人定坠访问的个人缓存随玩家保留。永久升级使用 Create 序列组装，旧简化配方与手持右击行为已经废止。

由两种缓存归属直接推出：

- 普通坠子卸下或转交不会回退其本件缓存等级；坠子被真正毁坏时，整份本件缓存连同等级和插件永久失去。
- 私人定坠卸下、转交、丢失或毁坏不回退当前玩家个人缓存等级；重新取得访问入口后仍使用该玩家原等级。
- 多件坠子不叠加格数、容量、等级或插件槽；当前活动缓存由有效佩戴、禁用与异网冲突规则唯一确定。

**死亡独立性：已确认。** 用户明确“死亡不改变物资和缓存格子，这套系统是完全独立的，玩家无论是摘掉饰品还是死亡都不影响”。缓存内真实物资、格子过滤、最低／最高数量及开关状态均不因死亡或摘下而改变；不参与死亡掉落，不随世界“死亡不掉落”设置切换。此前“缓存物资跟随世界死亡掉落规则”的助手建议未被采纳，不作为当前需求。

死亡不等于手动重置，待收记录不自动清空，也不产生补偿物资。死亡重生后仍使用同一份个人记录，能否访问与运行自动物流继续按有效佩戴判断。该保留范围仅限个人缓存；已经取出的物品、饰品实体和缓存外包裹仍按原有规则处理，不因此获得保护。跨存档／跨服务器的数据转移不在这项死亡保留决定中。

**佩戴开关：已确认。** 用户明确“未佩戴时，对玩家来说这套系统就不存在”。首个可玩版本仅当玩家通过 Curios 有效佩戴供应链坠时，整套个人物流功能才生效；仅放在背包中不算佩戴。后续护甲入口实现时遵守同一有效佩戴规则。

- 未佩戴时不显示物流格、箭头或操作入口，不能存取、配置或手动重置缓存记录；合成等缓存自动取料也停用。原版背包、普通取用与合成仍按没有本系统介入时的行为运行。
- 不为该玩家新发补货或启动退货，不自动拆开进入背包的专用包裹，也不继续吸收残包。已有包裹仍按外部运输与物品原有规则处理，本模组不撤回、销毁或接管；这不替未来退货确定交接协议。
- 个人物资、格子设置及待收记录保留，卸下不等于清空数据或手动重置。重新有效佩戴后，先按过滤与容量从背包现有专用包裹及残包实际入库，再依据更新后的缓存与待收记录检查补货。
- 服务端须在操作生效前核对佩戴状态，旧界面、快捷键和延迟操作不能绕过停用。卸下瞬间的已提交取料与未提交操作仍须物资守恒，不凭停用重复扣料或补偿。

**技术载体已固定：** 服务端将个人缓存、格子设置、升级、偏好和待收保存在可序列化玩家 Data Attachment 中；饰品通过物品数据组件单独保存本件网络绑定。服务端不接受客户端指定他人缓存，也不从饰品旧来源读取他人物资。每格保存不可变 `ItemVariantKey`（数量为 1 的完整组件模板）加独立 `long` 计数，不将千级计数直接作为普通堆叠暴露。用户已授权 schema 1 → 2 无损迁移；旧 `itemId` 过滤及其待收／日志键迁为该物品的默认精确变体，其他字段原样保留。同步、保存恢复和事务日志见[架构设计](开发计划书/架构设计.md)与[决策 0001](decisions/0001-精确组件物品身份.md)。

**当前收口：** 1—5 级及每级格数、单格容量、插件槽，缓存归属、取料默认、按格重置、非空格编辑、供应链系列命名、Curios 入口、多网冲突与手动禁用均已确认。升级材料、序列步骤、概率和新物品 ID 仍待设计；旧测试简化配方不再有效。个人缓存归属本身不产生网络绑定；发单能力来自当前实际佩戴饰品所带的有效 Create 绑定，不额外绑定某种运输模组。

### 4.6 退货：运输物格与一次性蜂

**已确认触发与数量规则：** 只看缓存；玩家存回后超过启用的最高数量，就按超额差额退回最高数量。恰好等于最高数量时不退货；同一批已锁定退货物资不能重复派送。普通背包中有多少同类物资与这个判断无关。

**当前决定：恢复研究。** 用户在最新批注中要求仔细研究退货，并提出增加运输物格、放无人机／运输蜂，点击角落小点配置返回地址，运输无法出发时不打包。该指示替代之前整项搁置的状态；不自建全局配送系统的边界不变。研究不等于退货已实现，也不自动决定其必须进入 MVP。

**随后明确的蜂专属方向：** 检测到安装 Create: Mobile Packages 且运输物格内有运输蜂，满足出发条件时保留格中原蜂，派出一只一次性蜂运输真实退货包裹；运输交付后，或者出发后失去可用目标而终止，销毁这只临时蜂。这替代本模组“每包扣一只普通蜂并在蜂港回收”的研究候选，不改变第三方普通蜂，也不把同样规则自动套给纸飞机。

**最新范围决定：先不专门处理蜂串网。** 用户要求相信玩家的建设能力，先沿用运输蜂原生选站、换站和回退；固定目标、禁止跨网及改网即终止退出当前要求。实际游玩时观察串网是否发生、正常建设下的触发频率、货物最终去向及影响，再决定是否需要专项适配。不承诺永不串网，也不以消除此项原生风险作为当前版本的前置条件；这不取消一次性蜂、不改变格内蜂不消耗和物资守恒规则。

| 环节 | 一次性蜂的产品要求与边界 |
| --- | --- |
| 启用 | 运输模组存在、运输格内有蜂，并满足本模组有效佩戴、无网络冲突、饰品网络绑定、当前佩戴者的提供者资格和出发条件；不是只检测安装就无条件发运 |
| 发运 | 不扣格内蜂；真实货物成功交接到一次性蜂的包裹后才扣缓存，启动失败不造可取得的额外包裹 |
| 目的地 | 出发时仍检查返回地址、有效目标与当前提供者资格；途中选站及回退沿用运输模组，不额外锁定初始蜂港，不预设防串网 |
| 正常结束 | 先确认整包实际交付成功，再销毁临时蜂及其运输记录；不转成蜂港内的普通蜂物品 |
| 其他物品出口 | 临时蜂不得通过原生敲击回收、死亡等路径产出普通蜂；否则保留原蜂再产出新蜂会造成复制 |
| 丢失目标 | 原生逻辑仍有可用目标时允许重选，不因换站或改网额外终止；失去可用目标而终止时销毁临时蜂，原包当地掉落，不退缓存、不复制、不赔付 |
| 生命周期 | 一次性状态随运输记录保存，重载不变回普通蜂；玩家卸下／离线不改变已发运任务的终止规则，也不重新启用其缓存操作 |

**已确认的失败规则：** 一次性蜂失去可用目标而终止时，销毁蜂，未交付原包在失败位置掉落，不自动退回缓存、不复制、不赔付，不随蜂删除。依最新范围，原目标失效或改网不额外触发防串网终止，先允许原生选站与回退；接收端满、目标区块未加载也不能直接全部解释为永久失去目标。在未加载位置如何安全保留并落下包裹属于实现验证，不通过强制加载全图解决。

**本轮研究范围：** 使用现有载具从玩家处发送真实包裹，检查返回地址、载具、配置和目标当前接收条件；没有出发条件就让超额物资继续留缓存，不先打成一堆待发包裹。当前不新增退货站，不要求终端承诺整个网络未来有库容，也不重启首轮提出的全程回执系统。

**已核查的原生机制及适配差异：** 纸飞机有空零件与已装包飞机，零件不在送达后返还。普通运输蜂有携副手包裹出发的入口，受配置控制；入港及玩家敲击回收都会产出普通蜂物品，因此本模组的一次性模式必须单独阻断这些产物出口。普通蜂的目标有效性还要求蜂港能同时收包裹和蜂；一次性蜂不进入蜂库存，不能照搬这一容量条件。所查创建入口没有一次性模式参数，终止、回收和持久化仍须适配；防串网的目标锁定与回退拦截已移出当前要求，详见[双运输地址与退货核查](research/2026-08-29-双运输地址与退货入口核查.md)。

**成本与顺序：** 当前先缩减防串网范围，少做固定目的地与回退拦截；一次性蜂的交付／回收、失败落包和保存重载仍需实现与验证。上轮“纸飞机退货优先、蜂单独后置”只是助手建议，不作为当前已定顺序；不因尚未实测的串网风险强制后置蜂或扩大适配。双运输补货测试与补货先于退货的既定顺序不变，当前没有可靠工期或普遍兼容冲突的实测结论。

局部守恒要求不变：实物成功从缓存转入包裹时才扣对应数量，启动失败不能让物资消失，也不能凭外部运输超时把已转出的物资凭空加回来。交接事务在后续退货技术规格中落实，不再作为产品选择题。

**发运边界：** 拟采用“计算单包超额 → 检查载具与当前目标 → 服务端复核并提交真实交接”。受理失败不扣缓存、不耗载具、不遗留可拾取的额外包裹；一次性蜂受理成功也不扣格内原蜂。出发时有位置不保证到达时有位置：纸飞机按原生规则处理，蜂暂沿用原生选站与回退，不承诺必回最初蜂港；不能因为迟到或未知状态把已发出的货重复加回缓存。

**界面边界：** 不再把“首版永远禁用上限、不显示上箭头”当作定案；最高端点、运输物格及上箭头纳入退货研究。尚未具备实现的构建仍不得显示为可用；直接从玩家处发运时，红色上箭头应描述真实交接／发运，不能写成“配送机来取货”或“基地已签收”。

### 4.7 本地地址收包与标准分包

**已确认的收货流程，前提是有效佩戴：** 完整实物包裹进入玩家物品栏／背包 → 识别 `本模组指定的包裹地址@玩家名` → 校验当前玩家及有效佩戴状态 → 将允许存储的内容解入缓存。未佩戴时不执行这段自动处理，重新佩戴先处理已有专用包裹。终端不监视该包裹此前的运输路线、载具或世界持有者。

只处理专用地址标记，其他普通包裹保持原有行为。收包不以当前仍存在未完成订单为前提，因此手动重置后的迟到包，以及由其他路径取得的真实匹配包裹，仍可进入本地处理。解包目标是当前玩家的个人缓存，不由饰品原持有人决定。发单所需的饰品绑定和 Create 网络可用性与此分开；地址不能创建绑定或选择其他玩家缓存，收包也不另查运输载具来源。

#### 部分入库与剩余包裹：已确认

空间不足时，从包裹中提取匹配格能够接收的部分，最多填到该格的实际容量；剩余内容继续留在原包裹中，包裹仍在玩家本地物品栏／背包，不要求载具原路返回。

对一个匹配且允许存储的物品格，设缓存现货为 `N`、实际容量为 `C`、该包裹中对应物资数量为 `Q`，则本次最多接收 `A = min(Q, max(0, C - N))`。实际转移成功多少，缓存就增加多少，包裹就减少多少。`C` 不是退货最高数量 `U`，收货不能被 `U` 截断。

例如实际容量 1024、现货 1000、包裹带来 64：本次入库 24，缓存变为 1024，原包裹保留 40。若完全无空间则不提取，包裹内容保持原样；若可以全部收下则全部转入，不为填满容量凭空补足。数字仅用于说明规则，不是容量档位。

未接收的内容不得随外壳一起被消耗。不支持的物品、没有匹配格的内容也应留在原包裹，不自动建立新过滤或剥除物品数据。本地重复事件不能把同一份实物入库两次，保存重载后也须保留缓存与残余包裹的实际数量。这是本地库存转移要求，不要求在全世界封堵普通包裹的所有打开和转交路径。

#### 残包自动继续入库：已确认

缓存腾出空间后，优先从玩家背包内本模组专用地址的残留包裹继续转入匹配物资。每次仍受真实物品数量、允许范围、过滤与实际容量约束，没收下的内容继续留在原包裹。

顺序为：**缓存腾位 → 专用地址残包实际转入 → 按更新后的缓存数量检查网络补货。** 残包转入后已补足最低数量，就不为同一缺口新发单；仍不足时，核对在途后仅处理剩余缺口。普通背包散装物品、未标记包裹及尚未转入的包裹内容均不计为缓存现货。

这里是对已经到达玩家的实物继续本地解包，不是按超时重新下单。自动续收固定先于新补货判定；首次观察按实际支持内容结算待收一次，后续只移动残包实物。玩家主物品栏变化 hook 负责置脏，正常提供者到货最迟下一服务端 tick 处理，每 20 tick 的有界扫描负责恢复漏报；这些规则仍须实现后验证。

**残包被手动处理：已确认。** 玩家手动打开、移走或耗尽残包后，必须按当前实物清除“等待缓存腾位”状态，不能继续把不存在的包裹当成待收而卡住补货。手拆所得散装物品遵循原版物品栏规则，不自动算进缓存，不重新创建原包、不做补偿。一次到货记账由包裹持久收据负责，本地残包提示由当前主物品栏实物扫描结果负责；两者严格分离，续收、移动或手拆不得造成二次结算。

#### 标准分包

**已确认的分包方向：** 按 Create 打包机的方式持续生成标准包裹，每包最多 9 个物品槽，各槽遵守对应物品的原生堆叠上限。大量补退货用多个包裹完成，不把“9 组”一律算成 9×64，也不要求一个包裹容纳整格千级库存。标准包容量已在[首轮审查 C3](research/2026-08-28-物流系统对抗式审查.md)核对；连续发货和逐包入库总量仍需实际实现后验证。

本地识别固定为“目标版本的玩家主物品栏变化 hook 只置脏＋有效本地访问玩家每 20 tick 有界后备扫描”；置脏后最迟下一服务端 tick 扫描原版主物品栏与快捷栏，不扫描外部背包或世界实体。有效佩戴由服务端 Curios 枚举与异网冲突归并判定。多件饰品共享同一份个人库存与升级，不叠加格数或容量；不能再根据饰品 ID 选择另一份库存。这里不承诺本模组能够绕过外部运输模组的背包满检查，也不宣称尚未执行的投递路径已经联调通过。

### 4.8 1—5 级成长与首轮默认数值

**已确认：** 正式玩家等级为 1 级 → 2 级 → 3 级 → 4 级 → 5 级。“石／铁／安山／黄铜／坚固板”不再是等级名称，配方材料另行设计。每级同时增加物流格、单格容量和一个通用插件槽；等级归当前缓存，不是统一写在玩家身上的全局字段。

| 等级 | 格数 | 两列布局 | 单格容量 | 插件槽 | 全部装满时的总件数 |
| --- | ---: | --- | ---: | ---: | ---: |
| 1 级 | 9 | 2 列 × 5 行，末行 1 格 | 128 | 1 | 1,152 |
| 2 级 | 16 | 2 列 × 8 行 | 256 | 2 | 4,096 |
| 3 级 | 24 | 2 列 × 12 行 | 512 | 3 | 12,288 |
| 4 级 | 30 | 2 列 × 15 行 | 1,024 | 4 | 30,720 |
| 5 级 | 36 | 2 列 × 18 行 | 2,048 | 5 | 73,728 |

这些容量指缓存内部计数。即使格子可存数千件，取到背包、合成格或外部接口时仍分成合法原生堆叠。1 级末行只启用一个物流格；16 格以上及最终两列十八行使用滚动面板，在 GUI 缩放和窄窗口中仍保留全部已解锁格，不靠压缩、隐藏或改数值适配。

**获取规则：** 新缓存从 1 级开始，后续逐级提升。永久等级升级必须通过 Create 序列组装；每次成功只提升一级并新增空物流格、基础容量和一个空插件槽，不生成插件，也不另开互相独立的格数／容量研究树。具体中间产物、材料与概率尚待设计。

旧测试版的材料等级名、四种无序升级配方、手持右击行为和 `iron_cache_upgrade` 等注册 ID 全部失去产品效力。项目尚未正式发布，不为它们制作兼容别名、双格式解码或旧测试存档迁移器；新模型直接采用干净的等级与物品表。代理不得因此删除用户测试存档。

等级升级只扩容，不改变现货、已有过滤、插件或端点启用状态；已启用端点保留数值，关闭的最低／最高端分别重新贴合 0／新容量但继续关闭。普通缓存的等级随坠子转交，个人缓存的等级随玩家保留；不得把旧容量右端的“关闭”误转换成已启用退货阈值。

### plan-v1.0 固定的内部职责

| 职责 | 拥有的数据／操作 | 不能跨越的边界 |
| --- | --- | --- |
| 个人缓存 | 按玩家身份保存允许的物品身份、独立计数、唯一过滤、阈值、优先级和成长阶段 | 不按饰品建第二份缓存；不把千级计数传成非法原版堆叠 |

| 界面与操作 | 两列格、悬停小点、双端滑条、来源开关、状态、网络和原因提示 | 客户端提交意图，不决定物资数量；研究中的退货不能伪装为已实现 |

存取、填料和取箭统一按“模拟可行性 → 服务端提交真实转移 → 更新待收与界面”组织。模拟不是预先发放物品；实际提交时仍复核库存与佩戴。缓存数量发生变化后，先运行本地残包续收，再重新判断补货；同一 tick 的同物变化合并评估，避免多个调用各自发一单。

个人数据唯一权威已固定为 NeoForge 可序列化玩家 Data Attachment，并启用死亡复制；`SPK-DATA-01` 已通过正常保存、坏数据封锁和跨 JVM 压缩玩家文件回读。保存异常、重复网络操作和不完整客户端请求都必须安全拒绝，不能靠清空玩家库存恢复。完整结构见[架构设计](开发计划书/架构设计.md)。

上述职责边界属于已锁定架构；文档中的 Java 服务名用于表达责任，具体类的拆合可在不跨越边界、不改变协议与测试门槛的前提下于实现中调整。

### 已知源码入口与限制

- Create 的网络查询和请求方法已经存在，但位于其内部物流实现中；可调用不表示跨版本稳定 API。[S1]
- Mobile Packages 的 `BeePortBlockEntity.sendPackageToPlayer` 在所读快照中先检查普通背包空间，再把完整包裹插入背包。这与本轮确认的“完整包裹先到玩家、再本地拆包”入口相容，但仍是源码推断，尚未联调。原先建议的“必须在交付前截获，满背包仍能直接进缓存”不再作为当前要求。[S3]
- 两个固定运输快照都能解析 `FMP@当前玩家名`：蜂取最后一个 `@` 后缀，纸飞机取第一个 `@` 后缀。当前格式仅有一个 `@`，前缀解析不冲突，但蜂还检查网络成员，纸飞机还要求活动目标登记。完整交付、蜂成员资格及运行效果不能仅靠字符串推断，见[本轮核查](research/2026-08-29-双运输地址与退货入口核查.md)。
- Package Couriers 到达玩家后可能交付完整包裹，也可能按预拆包状态将内容逐项放入普通库存。后者已无完整包裹供本地按地址识别；后续需要验证完整包裹路径，不把普通散装物资一并搬入缓存。[S5]
- 之前检查的是提供者的到货源码，未见通用“投递到第三方库存”事件。plan-v1.0 已固定使用目标版本的玩家主物品栏变化 hook 置脏，并以每 20 tick 有界扫描守正确性；`SPK-INV-01` 负责锁定具体 hook 目标和事件顺序。若目标 hook 验证失败，必须阻塞 M3 并回到规格修订，不能改成全局背包替换、无界扫描或宣称全兼容。
- 2026-08-29 新增核查确认 NeoForge 1.21.1 源码有箭矢查询事件及原版耗箭补丁；它们为取箭提供入口，但不是“监听事件就自动守恒”的证明。必须分别处理查询、实际消耗与武器内已装物资。
- TaCZ 的本次 1.21.1 候选使用实体 `ItemHandler` 检查／提取备弹，弹种还依赖 `AmmoId` 数据。不能直接用原版弓弩监听覆盖 TaCZ，也不能以修改枪包配置、替换整个玩家库存能力或清除弹种数据绕过适配验证。以上是静态源码结论，详见[新增兼容核查](research/2026-08-29-自动取料兼容边界核查.md)。

### 第三方接入的成本边界

**用户已确认的退让条件：** 如果覆盖其他模组要做侵入式修改，就先保原版。为便于验收，本计划建议按以下标准评估，而不是把“用了某个技术名词”简单等同于可接受或不可接受：

- 优先使用已有事件、公开接口和隔离的适配层；未安装可选模组时基础功能仍可启动。
- 不要求玩家改枪包、改服务器游戏规则、关闭正常消耗、把弹匣枪改为背包直读，或安装修改过的第三方 JAR。
- 不全局拦截所有 `ItemStack` 的扣减，不替换全部玩家库存行为来伪装全兼容；局部注入是否必要以及对其他模组的影响必须在技术规格中说明。
- 同一版本是否携带 TaCZ 适配，取决于弹种身份、原有操作语义和多人守恒测试，而不是只看一个方法是否公开。未过闸门时交付原版范围并明确标注 TaCZ 尚未支持。

### 暂不采纳的路径

- 将每格的千级数量直接当作原版大堆叠物品传给所有容器。
- 用客户端面板或地址字符串直接决定真实库存与访问权限。
- 跳过实物包裹，在请求发出时直接给玩家增加物资。
- 扫描并搬走玩家普通散装物品或未标记包裹。完整专用地址包裹进入背包再本地解包已经是确认方向，不再列为被否决路径；识别触发方式另行验证。
- 为终端自建全局配送调度、监控包裹去向或按超时自动恢复物流。

## 6. 技术风险、开发顺序与验收计划

2026-08-28 完成[第一轮物流系统对抗式审查](research/2026-08-28-物流系统对抗式审查.md)，记录 24 类风险和 20 项未执行反例。它保留范围收窄前的分析，已标注后续用户决定；其中“特殊变体存储不纳入当前范围”的判断已被 2026-09-04 [决策 0001](decisions/0001-精确组件物品身份.md)替代。原有全程跟踪、以终端为库存归属和退货站协议仍不整套作为当前验收门槛。结论来自设计分析和静态源码核查，不是游戏内漏洞复现。

当前已确定不判丢包、只手动重置、精确组件变体可入缓存、四种箭头、本地地址收包及标准连续分包；自建全局配送被否决。以下仅登记当前边界内仍需验证的事项。后续只针对有实质取舍的未决事项讨论；直接推论合并处理，技术事实先查证，不重新扩大运输职责。

| 风险 | 影响 | 最小验证方式 |
| --- | --- | --- |
| 组件在存取或请求中被压缩、剥除或忽略 | 属性／内容丢失，弹种／气量串货，过滤与实物混淆 | 所有入口共用完整 `ItemVariantKey`；精确组件往返、同 ID 多变体和输出散列逐项验证，任何路径不得重建默认实例 |
| 组件模板过大或无法稳定编解码 | 网络包超限、存档膨胀、重载后身份改变 | 单模板上限 1,024 字节、C2S 8 KiB、全快照 64 KiB；编码→解码→再编码身份一致，失败在接收实物前整笔拒绝 |
| Create 查询按裸物品 ID 合并组件变体 | 请求到错误弹种、气量或内容，残包与待收长期卡住 | 查询和请求使用当前格的完整精确模板；目标 API 不能可靠区分时阻塞该变体自动补货，不降级发单 |
| 缺货或部分供货与待收记账不一致 | 等待状态误导、重复采购或空单风暴 | 0 库存、部分供货、多人竞争和手动重置；不把待收记录宣称为实时运输证据 |
| 重置在途误操作真实物资 | 凭空加货、删除旧包或拒绝迟到实物 | 重置前后实物不变，新请求真实扣库，旧包仍可按地址处理 |
| 千级数量未正确连续分包 | 漏装、余量丢失或重复记账 | 采用标准 9 格包裹，遵守各物品上限，逐包核对总量与剩余 |
| 提供者交付散装内容或未将完整包裹放进背包 | 没有地址可识别或本地入口不触发 | 验证完整包裹投递及本地处理；记录背包满时的实际行为，不承诺绕过上游限制 |
| 缓存口径被普通背包统计混入 | 取出不补货，违背用户规则 | 只改变背包数量不改变缓存判断；取出即扣缓存并重新检查 |
| JEI 模板被当成真实物品 | 凭空生成库存 | 空格拖入 JEI 图标后库存仍为零；背包拖入验证双向守恒 |
| 阈值与容量／关闭状态混淆 | 初始自动发单、无法存回超额物资 | 默认双端关闭、单端启用、等号边界、超过退货阈值但不超容量分别测试 |
| 状态箭头与本地记录不一致 | 玩家看不到缺货或误以为已收货 | 绿色／灰色下箭头、手动重置和部分到货；上箭头仅在未来真实退货流程中验证 |
| 重复本地事件或地址识别混淆 | 复制物资或误拆普通／他人包裹 | 同一实物重复事件不二次入库；不同玩家、未标记包裹、重置后迟到包分别测试 |
| 缓存满、过滤变化或包裹混入不支持物品 | 自动拆包吞掉未接收内容 | 按实际容量部分提取，缓存增加量等于包裹减少量，余货留原包；覆盖无空间、混合内容、重复事件与保存重载 |
| 腾位后先发新单再处理本地残包 | 已有实物尚未用完却重复采购 | 先真实续收入库再按缓存现货判断；残包足够时不为同一缺口新发单，不足时核对在途后只处理剩余缺口 |
| 合成取料与原版配方流程冲突 | 吞物、重复扣料、配方余物丢失 | 单次／批量、混合来源、桶等余物、关闭界面专项测试 |
| 个人缓存仍按饰品身份保存或选择 | 换饰品丢库存、转交泄露他人物资、重复库存或发单 | A 换饰品仍是 A 数据；同一饰品交给 B 只打开 B 数据；遗失／销毁饰品、重连与保存重载不清除个人记录 |
| 卸下只隐藏界面，后台或旧操作继续生效 | 无饰品仍取料、补货或拆包，违背整套系统停用 | 未佩戴及仅携带时所有缓存业务停用，原版背包操作不受影响；重装先收已有包再补货，反复穿脱不清在途、不重复发单；操作中卸下仍须守恒 |
| 死亡重生误清空、掉落或复制缓存 | 违反缓存独立保留，或重生得到重复物资 | 佩戴／未佩戴及世界死亡不掉落设置开／关分别验证；物资、格子配置和待收记录延续，连续重生与保存重载不产生第二份库存；缓存外物品保持原有规则 |
| 高计数或合法堆叠上限处理错误 | 数据损坏、转出非法堆叠 | 数千计数往返转移，分别验证原生上限为 1、16、64 的允许物品，不强行统一为 64 |
| GUI 左侧空间冲突或设置难点中 | 配方书遮挡、小点和滑条难操作 | 多 GUI 缩放、窄窗口、配方书展开、小点命中区域和精确数值测试 |
| 发货端区块未加载 | 有目标却不产生包裹 | 发货区块卸载时按可用信息反馈；不偷偷强加载全图，不为状态箭头新建全局调度 |
| 兼容模组更新 | Mixin 或请求协议失效 | 锁定验证组合，升级时重新检查到货与请求路径 |
| 每件网络被误写成玩家级唯一绑定 | 换饰品后网络错乱，违背本件配置规则 | 两件终端分别绑定 A/B；解绑其中一件不改另一件或个人缓存；转交携带该件 Create 绑定但不携带玩家附件数据，蜂成员资格重查 |
| 多件饰品或换网各自为同一缺口发单 | 重复采购、旧在途被遗忘 | 不同网络冲突后停用，手动禁用才能解除；同网共享防重，换网不清待收，迟到旧包仍按地址处理 |
| 重复过滤绕过精确变体单格 | 同一变体有冲突阈值或被多次请求 | 背包拖入、JEI 拖入、schema 迁移和保存重载均验证精确变体唯一；同 ID 不同组件允许各一格且不串单 |
| 投射物查询扣料或装填后再次扣料 | 取消射击丢弹药、多重射击过扣、复制弹药 | 查询／取消、实际射击、弩装填后换装与发射，以及非原版标准链子类分别核对库存及武器内物资 |
| TaCZ 弹种数据被忽略，或把组件缓存误报为枪械兼容 | 不同弹种混合、失去身份或扣料时机错误 | 精确变体先保真；另锁定 TaCZ 版本并验证备弹、装填、弹匣和开火提交点，未过闸门明确未支持 |
| 等级被写到错误所有者或只改部分结构值 | 转交后等级错乱、格数／容量／插件槽不同步 | 等级归当前缓存；1—5 级三项结构值原子变化，普通缓存随坠子、个人缓存随玩家 |
| 后续改装护甲配方改坏原装备 | 丢附魔、洗耐久、复制供应链坠或网络配置 | 不进入首个可玩版本；以后实现时各基底与附加数据转换守恒，无法安全保留时不接受输入 |
