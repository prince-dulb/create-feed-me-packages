## 2. 适配入口（发布二进制 `javap` 核对 + 源码确认）

### 2.1 目标登记——SPK-PLANE-01 的核心动作

- `CourierTarget.addOrUpdateTarget(CourierTarget)` 是**公开静态方法**；`new CourierTarget(String address, Entity entity)` 构造 ENTITY 目标。
- 参照实现 `LocationTransmitterItem.inventoryTick`（源码 79—85 行）：服务端每 tick，物品启用时 `addOrUpdateTarget(new CourierTarget(entity.getName().getString(), entity))`。**登记地址是裸玩家名**（不是 `FMP@玩家名`；`@` 前缀在 `addPlane` 解析时才剥离，见 2.2）。
- 目标表 `CourierTarget.activeTargets` 每 `ServerTickEvent.Post` 计数 +1，`TIMEOUT_TICKS = 20`，超时移除。**本模组适配器只需在有效佩戴期间每 tick 刷新；卸下／禁用／冲突时停止刷新，条目最迟 1 秒自然消失，且不会删除原版发信器等其他来源的目标**——与 SPK-PLANE-01"超时窗口内消失且不删除原模组发信器目标"逐字吻合。
- ENTITY 目标 equals = (address, entity 实例)。玩家重生／换维度产生新实例时，新登记成为新条目，旧条目因 `entity.isRemoved()` 置空并自然超时，无需本模组清理。
- `getActiveTarget` 用 `PackageItem.matchAddress` 匹配并**实体目标优先**；`addPlane` 解析 `FMP@玩家名` 时以 `playerOnly=true` 查询，不会被方块目标截胡。

### 2.2 起飞受理 `CardboardPlaneManager.addPlane(Level, Vec3, float, float, ItemStack, boolean unpack)`

受理链（源码 66—117 行，签名已用 javap 核对）：

1. 必须是 `PackageItem.isPackage`；客户端调用直接拒绝。
2. 地址解析：先取 `<…>` 尖括号内容，再取第一个 `@` 后缀并置 `playerOnly=true`。`FMP@玩家名` → 目标查询键 = 玩家名。
3. `getActiveTarget(address, true)` 为 null → 返回 false，**包裹不动、不生成飞机**——天然满足"不能出发就不打包／出发受理失败不扣物"。
4. 配置门：ENTITY 目标要求 `ServerConfig.planePlayerTargets`；跨维度额外要求 `planeCrossDimTransport`，关闭时目标维度不同直接拒绝。
5. BLOCK 目标还要求 `planeLocationTargets` 且目标方块实现 `CourierDestination` 且**当时有空位**。
6. 受理成功返回 true，创建非实体 `CardboardPlane` 加入飞行记录（渲染实体按区块加载情况按需生成）；LIFESPAN_TICKS = 400。

5 参重载固定 `unpack=false`。**本模组派出时必须走 `unpack=false`（完整包裹模式）**；`unpack=true` 到达后逐件散装 `placeItemBackInInventory`，本模组不扫描散装物，预拆路径只能诊断不支持。

### 2.3 配置默认值（`ServerConfig` 源码核对）

| 配置 | 默认 | 对本模组的影响 |
| --- | --- | --- |
| `enablePlanePlayerLogistics` | `true` | 关闭时 ENTITY 目标永不受理——适配器前置探测并诊断 |
| `enablePlaneLocationLogistics` | `true` | 方块目标门，与本模组玩家目标无直接关系 |
| `planeCrossDimTransport` | `true` | 关闭时只允许同维度派飞，适配器按维度诊断 |
| `enableShopAddressReplacement` / `atSignShopAddressReplacement` | `true` / `false` | 作用于地址书写替换路径，`FMP@` 直书地址不受影响（待游戏内确认） |

### 2.4 交付 `CardboardPlane.onReachedTarget`（源码 105—131 行）

- ENTITY 目标且玩家在线、`unpack=false`：**`player.getInventory().placeItemBackInInventory(整包)`**——完整包裹进入玩家普通物品栏，随后由 T07 已验证的有界扫描自动收包。补货闭环的收尾与现有收包侧无缝衔接。
- 玩家离线／实体消失：先检查目标坐标方块目的地，否则在飞机位置生成 `PackageEntity` 落地包裹——**包裹不消失**。
- 上游源码自注"destination is not loaded 时会怎样"是潜在问题（104 行注释）：到达时目标区块未加载的行为属未验证观察项。

## 3. 关键缺口：补货方向没有"自动上飞机"钩子

2.3.0 中 `addPlane` 的唯一外部调用方是 `CardboardPlaneItem.use`（玩家投掷已装包纸飞机，源码 107 行）。全模组 mixin 列表（Depot／Belt／Saw／Ejector／Sign）都是**接收端**目的地或纸飞机物品发射效果；`SendPackage`（便携行情器下单）最终也只调 Create 原生 `broadcastPackageRequest`，**没有任何代码把 Create 网络产出的包裹自动转为纸飞机**。

因此 T06 已验证的链路止步于"打包机产出 `FMP@玩家名` 真实包裹（`packager.heldBox`）"，物理运输的最后一公里（包裹 → 玩家普通物品栏）在纸飞机路线下必须由**本模组适配器**补上：T06 dispatch 成功后，适配器取到真实包裹并调用 `addPlane(..., unpack=false)` 派飞。这不违反架构职责表"适配器不负责重复广播 Create 请求"——不重复下单，只做真实运输派发；"出发受理失败不扣物"由 `addPlane` 的 false 返回值承接。

**T08 技术方案的第一课题**：派发时序。`performPackageRequests` 之后包裹何时出现在打包机（同 tick 或下一 tick）、多打包机并发时如何各取各包、取包与原生输出路径（青蛙港／传送带）的竞争，都需要在实现方案中给出设计并用隔离实例验证。候选形态：dispatch 后同 tick 检查 `PackagerBlockEntity.heldBox`、或订阅 Create 的打包产出事件（6.0.10 是否提供待查）、或在 T06 的 `PreparedRestockRequest.dispatch()` 内嵌派发。

## 4. T08 适配器前置条件清单（运行时探测，缺失即诊断降级，不阻断核心）

2. `ServerConfig.planePlayerTargets == true`（反射读静态字段或观察诊断）。
3. 跨维度按 `planeCrossDimTransport` 如实诊断，不谎报可达。
4. 玩家为有效佩戴（复用 `TerminalAccessService.resolve`），否则不登记目标。
5. 目标登记 20 tick 窗口内有效；`addPlane` 返回 false 时不扣任何物资、按格保留待收等待下次评估。

## 5. 对既有决定的符合性

- 只调用对方公开 API（`CourierTarget.addOrUpdateTarget`、`CardboardPlaneManager.addPlane`、`ServerConfig` 静态字段），不复制、不修改对方代码资产，不打 Mixin。

> **状态更新（同日，按[首轮技术审查](2026-09-03-首轮技术审查.md)）**：本节"同 tick 拦截 heldBox 直接派飞"方案已按审查要求**暂停**，未产生任何代码。审查指出的风险成立：该方案绕过载具成本（原生装包消耗纸飞机零件）、截走玩家的蛙港／传送带／运输蜂路线，且未处理延后产包（`queuedExitingPackages` 次 tick 才入 `heldBox`，同 tick 扫描会漏）。原生链路复核：装包仅玩家双手动作（零件+包裹），弹射器可自动化发射，载具为装包纸飞机物品本身。最小方案（目标登记＋完整包接收）无需此路径；直接派飞是否作为产品取舍提交用户，由主策划整理后决定。本节以下内容保留为时序事实，不作为已批准方案。

派发时序已按 Create 6.0.10 固定提交 `ac0c444d` 的 `PackagerBlockEntity` 源码核实并定稿：

- `heldBox` 是公开字段（源码 79 行）；`performPackageRequests` 装箱后在同 tick 写入 `heldBox` 并启动 20 tick 出箱动画（529 行）。T06 的 `t06CreateGatewayExtractsStockAndCreatesAddressedPackage` 已实证 dispatch 后同 tick 可读到 `heldBox`。
- 动画结束只调用 `wakeTheFrogs()`（195、571—574 行）唤醒青蛙港扫描；包裹由青蛙港经 `PackagerItemHandler` 异步拉走，不存在"同 tick 被原生弹出"的竞争。**同 tick 拦截无竞争，选定为派发机制。**
- 派发流程：核心侧在 `dispatch()` 成功后把"涉及打包机 + 收件地址"交给派发钩子（核心内默认空实现）；纸飞机兼容模块在模组存在且 `ServerConfig.planePlayerTargets` 为真时接管：对每个 `heldBox` 地址匹配的打包机，取 `heldBox` 调 `addPlane(level, pos, yaw, pitch, box, false)`——返回 true 则立即 `heldBox = EMPTY`（避免同一 ItemStack 双引用造成复制），返回 false 则**不动 heldBox**，包裹按 Create 原生路径继续弹出，待收保留等物理到达或按格手动重置。
- 目标登记按 §2.1 执行：有效佩戴期间每服务端 tick `addOrUpdateTarget(new CourierTarget(玩家名, player))`，停止刷新自然过期。
