# 2026-09-05 升级体系重构提案

## 1. 状态

- **状态**：部分已确认、工艺待细化。Scathiard 已确认旧升级体系废止、永久升级必须使用 Create 序列组装，并于 2026-09-05 接受 5.3 的一次性“待签收容量授权”方案；正式等级改为 1—5 级，具体序列、材料、概率和干净 schema 表示仍未定案，也未授权实现。旧测试注册 ID 与存档不要求兼容。
- **已确认前提**：普通供应链坠持有本件缓存；供应链坠·私人定坠访问玩家个人缓存；普通坠子可保留库存个人化，已有个人缓存时只允许全量原子迁移。
- **目标**：让玩家明确知道“升级的是哪份缓存”，同时保留 Create 的实体制造感、物资守恒和私人定坠的玩家身份语义。

## 2. 旧体系为什么失效

当前规格与实现是四种通用升级件：玩家佩戴任意有效坠子，手持正确的下一阶段升级件右击，代码直接升级 `PlayerCacheService` 中的玩家缓存。新模型下有四个根本问题：

1. 玩家可能拥有多枚普通坠子，每枚对应不同本件缓存；“对空气右击”没有明确目标。
2. 阶段现在应属于缓存，不能继续写在玩家身上，否则换普通坠子仍会共享容量。
3. 私人定坠的缓存确实随玩家，但它只是缓存所有权的一种形态，不能反过来证明所有升级都应直接作用玩家。
4. 普通坠子个人化会改变物品形态并合并缓存，和单纯扩容不是同一种操作。

因此须废止的是“玩家全局阶段＋手持升级件直接右击”的使用语义。项目尚未发布首个正式版本，现有四个材料命名注册 ID 也不保留为兼容入口；新实现直接使用 1—5 级语义与新 ID，不增加别名、旧行为代理或旧测试存档迁移器。

## 3. 缓存的规模与归属

| 轴 | 当前值 | 操作 | 不改变 |
| --- | --- | --- | --- |
| **缓存规模** | 1／2／3／4／5 级 | 通过 Create 序列组装把当前缓存提升一级 | 缓存所有权、网络绑定、已有物资与配置 |
| **缓存归属** | 本件／个人 | 用个人化组件把普通坠子的缓存转为或合并入玩家个人缓存 | 成功迁移的真实物资、最高阶段与可保留状态 |

任何一份缓存只有一个正式等级；等级是缓存记录的字段。本件缓存的等级随普通坠子转交，个人缓存的等级随玩家保留。私人定坠被毁后重新制作，只恢复访问，不重置个人缓存等级。

Scathiard 已确认任意等级都可个人化；已经个人化的缓存通过 5.3 的一次性待签收容量授权继续扩容，不能把同一高级私人定坠作为多人共享的永久升级钥匙。

上表描述缓存的两项属性，不再称为玩家成长的两条强化路线。Scathiard 已将总体成长定位为另一组更直观的双轴：**1—5 级是永久结构增强，插件是可逆构筑增强；5 级与针对目标的合法插件配置结合，才形成该目标的最高能力。**每级同时解锁一个通用插件槽，1—5 级依次为 1—5 槽；等级只提供装配结构，不生成插件效果。插件不能直接写入等级、增加槽位或跳过扩容链，等级也不替代插件带来的功能。详细规则见[插件系统领域草案](2026-09-05-插件系统领域草案.md)。

## 4. 扩容应用方式

### 4.1 已否决：面板内的链节安装口

此前建议玩家佩戴并启用唯一活动缓存后，在背包左侧面板阶段徽记旁放置小型链节安装口。Scathiard 已明确否决：升级若只在 GUI 中塞入组件，不能充分体现 Create 附属身份。以下交互只保留为被替代记录，不进入永久升级规格。插槽概念随后被重新提出用于**可拆换插件系统**；两者边界见[插件系统领域草案](2026-09-05-插件系统领域草案.md)：序列组装负责制造和永久阶段成长，插槽负责插件换装。

1. 点击阶段徽记，展开不超过一格高度的 Create 风格维护条；
2. 维护条显示当前阶段、下一阶段、格数与单格容量变化，以及一个输入口；
3. 玩家把正确的下一档扩容链节放入输入口；
4. 服务端按当前活动 `cacheKey` 模拟升级，成功才消费链节并更新缓存；失败时链节留在来源位置；
5. 多缓存冲突、全部终端禁用或未佩戴时不显示可用安装口，只保留解除冲突的终端管理入口。

这条路径同时适用于本件缓存和个人缓存，目标由当前面板决定，不依赖客户端提交任意缓存 ID。普通坠子和私人定坠都不必从 Curios 槽取下，也不会因背包已满而无处放回输出物。

阶段升级是单向且纯增益，放入正确链节即可提交，不另加大面积确认框。个人化会改变所有权并可能合并两份缓存，使用同一维护条但应显示迁移预览和明确的成功／拒绝结果，不能在普通扩容的无提示路径里悄悄发生。

### 4.2 当前建议：序列组装制造，确定性安装

每一档扩容至少包含一条 Create 序列组装路线：

1. 从“未完成的扩容链节”等中间产物开始，经机械手部署、机械压制等步骤循环加工；
2. 概率产出只作用于可重复制造的链节／中间产物；
3. 完成的扩容链节再通过机械手物品应用或序列的确定性收尾步骤装到目标坠子上；
4. 目标是普通供应链坠时，坠子携带的 `cacheId` 明确指出本件缓存，最终成功步骤原子提升该缓存阶段；
5. 整个加工链必须保留坠子的网络绑定、实例身份和缓存引用，预览、模拟、未完成步骤与配方查询不得提前改变缓存。

不建议让装有真实物资的坠子直接承担概率失败。若失败产物把坠子变成废料，就等于随机销毁数万件缓存；若失败后复制返回原坠子，又会形成复制窗口。因此建议把概率放在独立链节制造上，完成链节装坠的最后一步为 100% 成功。玩家仍须建设 Create 加工线，升级不是 GUI 消费。

私人定坠没有稳定的物品所有者：它转交后应访问新佩戴者自己的个人缓存。因此自动化设备可以加工私人定坠或制造升级凭证，但最终把阶段写入哪名玩家，必须等实际玩家认领，不能由传送带猜测。

### 4.3 其他方案

| 方案 | 优点 | 问题 | 当前判断 |
| --- | --- | --- | --- |
| 手持升级件右击 | 已有代码、操作短 | 目标含糊、发现性差、无法表达合并 | 废止 |
| 锻造台／铁砧组合 | 熟悉，输入物品明确 | 私人缓存仍需玩家提交时事务；预览不得改数据；Create 风格较弱 | 可作备选或无 GUI 降级方案 |
| 专用升级站方块 | 实体感强，能展示动画 | 为四次扩容新增方块、菜单和物流边界，首版成本高 | 后续候选 |
| 传送带／机械手直接加工普通坠子 | 目标 `cacheId` 明确，可全自动 | 必须完整保留数据，不能让概率失败毁掉缓存 | 可作确定性最终安装 |
| 传送带／机械手直接升级已认领私人缓存 | 很有 Create 味道 | 松散私人定坠无法说明升级哪名玩家 | 不直接写玩家缓存；须产生一次性待认领结果 |

## 5. 私人缓存的后续升级方案

### 5.1 方案一：只允许 5 级普通坠子私人化

- 普通坠子完成四次序列扩容后，才能进入私人定坠序列；
- 私人缓存诞生即为 5 级，以后不需要升级路径；
- 没有共享解锁、待认领状态或低级私人缓存。

优点是规则最少、实现最稳，私人缓存成为明确的终局奖励。代价是末影箱式的个人缓存直到最高阶段才出现，玩家早中期没有“本件／个人”的玩法选择；以后若增加第六阶段，又会重新遇到私人缓存如何升级的问题。

### 5.2 方案二原案：佩戴过的最高私人坠子永久解锁

按字面实现会使一枚高级私人定坠成为可无限复用的服务器升级钥匙：玩家甲佩戴解锁后交给乙、丙，每人佩戴一次都永久获得同级空间。把私人定坠改成不可转交或固定原主人，又会违反已经确认的“转交后访问新佩戴者自己的个人缓存”。因此不建议直接采用。

### 5.3 已确认：一次性“待签收容量授权”

允许任意阶段普通坠子私人化；私人缓存以后仍可通过序列组装升级，但高级私人定坠携带的是一次性待认领结果，而不是永久可传播的等级：

1. 玩家把一枚普通或已认领的私人定坠与下一档扩容链节送入对应 Create 加工流程；
2. 自动化只在物品上写入有界的 `pendingTier`／来源缓存引用，不直接猜玩家身份；输出显示为“待签收”的私人定坠并明确目标阶段；
3. 第一名满足阶段顺序且成功佩戴／认领的玩家，由服务端把目标阶段原子写入其个人缓存，并从坠子上永久清除这次授权；
4. 认领前转交物品等于转交一次升级机会；认领后再转交，只提供普通私人缓存访问，不再给下一名玩家升级；
5. 阶段不匹配、个人缓存迁移空间不足或事务失败时不清除授权、不改变缓存；不能为了通过升级丢弃库存；
6. 私人坠子被毁后，玩家已写入个人缓存的阶段仍保留；重制的普通私人定坠只恢复访问。

普通坠子首次私人化也可使用同一“待签收”事务：输出暂时保留源 `cacheId`，第一名认领者才执行已经确认的全量迁移／合并。这样自动化流程不需要在线玩家，同时一份普通缓存或一次扩容成本只能被一个玩家吸收一次。

这套方案比最高级门槛多一个短暂的待签收状态和一次性标记，但保留早期私人化、后续序列扩容、物品可转交和个人进度永久保存四个目标。

## 6. 扩容物品的命名方向

建议把四个笼统的“缓存升级件”改成链坠与供应链共同使用的**扩容链节**。显示名按目标等级命名，配方使用什么材料另行设计，不再把材料名冒充等级名：

| 目标等级 | 建议显示名 | 英文候选 | 建议新 ID |
| --- | --- | --- | --- |
| 2 级 | 2 级扩容链节 | Tier 2 Capacity Link | `tier_2_capacity_link` |
| 3 级 | 3 级扩容链节 | Tier 3 Capacity Link | `tier_3_capacity_link` |
| 4 级 | 4 级扩容链节 | Tier 4 Capacity Link | `tier_4_capacity_link` |
| 5 级 | 5 级扩容链节 | Tier 5 Capacity Link | `tier_5_capacity_link` |

“链节”既是链坠上安装的实体零件，也是供应链中的一环；“扩容”直接说明玩家收益。上表新 ID 仍是命名建议，须与最终序列和物品表一并确认；旧 `iron_cache_upgrade` 等测试 ID 无兼容义务。当前没有源码或 schema 实施授权。

个人化组件另用一套语义，候选名为**私人定坠订单**（*Made-to-Order Form*）：Create 序列组装可以自动制造空白订单，但把它应用到普通坠子并改变缓存所有权时，必须由实际玩家在自己的维护条内提交。

## 7. 五级数值与制造成本需要重新检查的部分

已确认过的 9／128、16／256、24／512、30／1,024、36／2,048 在数据结构上仍可使用，但所有权变化带来新的平衡条件：

- 旧模型每名玩家只有一份最多 73,728 件的缓存；新模型允许制作多枚普通坠子，每枚都可能达到 5 级与这个容量。
- 普通坠子与扩容链节若维持当前低成本无序配方，会成为可大量制造、可转交的超大便携仓库。
- 当前供应链坠本身需要黄铜板和精密构件，玩家得到 1 级终端时已经进入 Create 较后期；入口成本是否合适仍须随序列配方一起检查。
- “石／铁／安山／黄铜／坚固板”原本只是讨论用说法，现已被正式的 1—5 级替代。配方仍可使用其中部分材料，但材料选择不再定义等级身份或固定顺序。

因此数值可以作为基线保留待测，旧四个简化配方不应继续视为定案。正式序列组装仍适合制造扩容链节；概率只影响链节制造产率，不影响把已经制成的链节安装到缓存时是否成功。

## 8. 已有个人缓存的阶段合并

沿用已经确认的全量迁移规则：普通坠子个人化时，最终阶段取普通缓存与个人缓存中较高者，不相加。先用最终阶段的格数和单格容量模拟全部库存、配置与残包；完全容纳才提交，否则提示库存无法转移并保持两边不变。

这意味着高阶段空普通坠子可以作为对个人缓存的有效阶段投资，但输入坠子会在成功个人化时被消费／转形，不会复制出第二份高阶段缓存。

## 9. 建议的讨论顺序

1. 一次性待签收授权已经确认；将其与普通坠子首次私人化统一为一个认领事务。
2. 确认扩容链节的概率序列制造＋确定性装坠分工，不让真实缓存承担随机失败。
3. 决定 1—5 级数值是否先保留为实玩基线，并为每级重新设计材料与成本。
4. 设计每档序列步骤、中间产物、概率权重和私人定坠订单。
5. 把已定结果写回规格 01—03、物品注册、创造标签页、测试策略和干净 schema；取得实施授权后再交执行者替换旧测试模型，不编写兼容层。

## 10. 已确认选择与下一项决定

Scathiard 已确认：**允许任意等级私人化；后续更高级私人定坠只携带一次“待签收容量授权”，由第一名合格佩戴者吸收后永久清除，不能在全服循环解锁。**方案一“只允许 5 级私人化”和方案二原案“仅佩戴即可重复传播等级”均不采用。

下一步讨论扩容链节的实际序列流程与 1—5 级材料／成本。五级数值、每级材料、每档序列和个人化组件配方暂不随本次确认自动定案。
