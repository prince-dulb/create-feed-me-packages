# 2026-09-05 缓存归属、补货状态与收件口重构提案

## 1. 状态与边界

- **状态**：部分已确认、部分待技术验证。Scathiard 于 2026-09-05 已确认采用两种坠子、普通坠子的本件缓存随最后一个合法入口毁坏而永久失去、先试用一个面板可见残包槽，并确认个人型坠子应由普通坠子保留整份缓存升级而来；缓存冲突、缓存令牌、真实收件入口与干净数据表示仍未定案，也尚未授权实施。项目未正式发布，明确不为旧测试 schema／注册 ID设计兼容或迁移模块。
- **目的**：把“终端物品、真实缓存、请求记录、收件入口”拆成不同对象，避免只改界面表现后产生串库、复制、丢包或隐形仓库。
- **当前影响**：该方向会重新打开缓存归属、终端访问、补货、收包、UI、合成与弹药取料的部分设计。执行者在模型确认前不得重写缓存归属或数据 schema；与归属无关的 JEI 隔离和既有 UI 层级缺陷可以继续修复。旧测试世界不在兼容范围，但不得由代理删除。

## 2. 当前统一语言

| 名称 | 含义 | 不等于 |
| --- | --- | --- |
| **终端** | 玩家佩戴的供应链坠；保存网络绑定、启用状态和所访问的缓存类型 | 真实物资本身 |
| **本件缓存** | 由一件普通供应链坠的稳定 `cacheId` 标识；谁持有并有效佩戴该坠子，谁访问它 | 玩家 UUID 缓存 |
| **个人缓存** | 每名玩家持有一个个人缓存引用；只有个人型终端可按当前佩戴者解析该引用，换终端、死亡或终端遗失不改变它 | 任一普通坠子的内容物 |
| **已请求记录** | Create 已受理的请求承诺，用于防止同一缺口重复请求 | 对载具位置或包裹存活的追踪 |
| **收件口** | 满背包时仍可接收并立即处理本模组专用包的服务端入口 | 可自由存放普通物品的额外背包 |
| **残包槽** | 收件口无法完全拆空包裹时，保存一个真实剩余包裹的专用位置 | 隐形通用仓库 |

建议以后不再把 `pendingInbound` 对玩家统称为“在途包裹”。本模组不知道载具是否真的出发或是否灭失，用户可见词应为“已请求量／请求记录”。

## 3. 状态归属

“缓存跟物品”不能只移动数量；否则转交后会出现容量、过滤和待收仍属于原玩家的半套状态。建议按下表整体分界：

| 状态 | 归属 |
| --- | --- |
| 网络绑定、终端禁用状态、终端类型 | 终端物品 |
| 本件缓存的 `cacheId` | 普通终端物品；物品转交时随物品走 |
| 格数阶段、单格容量、过滤、最低／最高、现货、已请求记录、收包事务日志、残包槽 | 当前缓存；本件缓存由物品引用，个人缓存由玩家记录引用 |
| 背包优先／缓存优先 | 玩家偏好；换缓存不改变玩家的操作习惯 |
| 折叠、滚动、当前悬停等瞬时 UI 状态 | 客户端会话，不属于任何库存 |

这样转交普通坠子时，接收者得到完整的“便携箱子”：阶段、格子、物资和自动补货设置一起转交。个人型终端转交后，接收者看到自己的个人缓存，不会得到原主人的物资。

## 4. 已确认的两类缓存玩法

### 4.1 两个清楚的终端形态

1. **供应链坠**：默认形态，访问本件缓存。
2. **供应链坠·私人定坠**（*Supply Chain Pendant: Made to Order*）：访问当前佩戴者自己的个人缓存；内部物品 ID 使用直白稳定的 `personal_supply_chain_pendant`。

这比同一件坠子上的即时“本件／个人”开关更清楚，接近普通箱子与末影箱的关系。即时开关会产生隐藏库存、切换时未完成请求、两套阈值谁继续工作等额外问题。

两个形态都可各自绑定一个 Create 网络。普通坠子被转交时，网络绑定和本件缓存一起随物品走；个人型坠子被转交时，只转交该坠子的网络绑定，缓存仍按新佩戴者 UUID 选择。

两种坠子不是同一件物品上的即时切换。私人定坠由普通供应链坠升级而来，并保留其整份缓存；具体升级组件和正式序列组装可以稍后确定。

### 4.2 保留缓存的个人化升级

这里的“保留库存升级”不应实现为逐格复制。推荐把普通坠子当前引用的缓存记录从“本件所有”原子地改成“该玩家个人所有”，并让玩家的个人缓存引用指向同一个 `cacheId`：

- 库存、阶段、单格容量、过滤、最低／最高、已请求记录、收包事务日志与残包全部原样保留；
- 网络绑定和本件禁用状态仍属于正在升级的坠子，随输出的私人定坠保留；
- 缓存身份不变，因此指向该 `cacheId` 的旧请求与迟到包无需逐项改号；
- 缓存记录增加所有权类型；个人化后，创造／命令产生的旧普通坠子副本不得继续作为该个人缓存的访问钥匙；
- 升级失败时不消耗输入、不产生输出、不改变缓存所有权；配方预览、JEI 查询和自动化模拟都不得触发迁移；
- 私人定坠只按当前佩戴者解析其个人缓存，转交物品不会把升级者的缓存交给接收者；接收者只看到自己的个人缓存。

为了让正式 Create 工艺仍可自动化，序列组装更适合制造“个人化组件”，最后由玩家把组件应用到普通供应链坠；真正改变缓存所有权的提交点必须知道是哪名玩家取得结果。首版采用何种应用界面另行进入配方规格，不在普通 `assemble()`／预览调用中修改数据。

玩家已经拥有个人缓存时，Scathiard 确认允许自动迁移，但必须遵守**全量成功或完全不动**：服务端先模拟合并；若个人缓存能够容纳普通坠子的全部真实库存，才原子提交升级。任何物资无法放入时拒绝升级，提示“个人缓存空间不足，供应链坠库存无法转移”，输入坠子、输出槽与两份缓存均保持原样。

“能够容纳”不是只数空白图标格，而是按最终状态同时检查：

- 合并后的缓存阶段取两者较高阶段，再据此计算已解锁格数和单格容量；阶段不相加；
- 普通缓存中的精确变体若已在个人缓存设格，数量并入该格，合计不得超过最终单格容量，也不得另建重复物品格；
- 尚未设格的精确变体须占用一个最终已解锁空格，连同它的过滤、最低／最高与库存迁入；零库存但已有过滤／阈值的格仍算需要迁移的配置格；
- 同一精确变体在两边都有设置时，保留个人缓存现有过滤与阈值，只迁入普通缓存的真实数量和不能丢弃的请求／收包记录，升级不得悄悄改掉玩家原有个人配置；
- 残包先按最终缓存容量模拟续收；若仍有两个无法合并为一个的真实残包，而个人缓存只有一个残包槽，则不满足全量迁移，拒绝升级；
- 已请求记录、收据与事务日志不得为促成升级而清空。实现必须保留原请求 ID，或保留旧 `cacheId` 到个人缓存的安全重定向，使迟到包仍只结算一次；发给其他玩家的既有请求不能被偷偷改写收件人。

普通缓存为空时，私人定坠直接访问既有个人缓存；个人缓存尚不存在时，仍采用同一 `cacheId` 的整份所有权转换。首版不提供部分迁移、溢出掉落、自动退货或“先升级再让玩家处理”的中间状态。

### 4.3 多终端规则必须随之调整

当前“同网多件可合并”只适用于多件终端访问同一玩家缓存。改为本件缓存后，两件普通坠子即使同网也可能是两个完全不同的仓库。

建议规则：

- 同时只能有一个**不同缓存**处于活动状态；多件启用终端指向不同 `cacheKey` 时显示冲突，玩家通过现有禁用入口留下一个。
- 多件终端指向同一 `cacheKey` 时不叠加容量、不重复发单，可视为同一缓存的多个入口。
- 普通本件缓存与个人缓存同时启用必然冲突，不暗中选择其中一个。

这不是恢复旧“自动挑一个活动终端”，而是继续使用玩家手动禁用来解除歧义。

### 4.4 数据载体建议

不建议把 36 格完整模板、数量、请求和收包日志全部塞进 `ItemStack` 组件。建议由世界级缓存注册表按随机 `cacheId` 保存真实记录，普通坠子只持有这个引用：

- 转交物品即转交访问权；
- 创造复制、命令复制或第三方错误复制出相同 `cacheId` 时，多个副本访问同一份缓存，不会复制物资；
- 普通坠子掉落、转交或暂时遗失时缓存仍随该件物品存在；当最后一个合法入口被岩浆、仙人掌、虚空、实体自然消失等方式真正毁坏后，玩家永久失去这份缓存，**不提供找回、补偿或恢复玩法**；
- 底层是否暂存不可访问的孤立记录、使用墓碑或延迟清理，是为防止崩溃、复制和错误判定服务的技术选择，不得产生新的合法访问入口，也不得把“永久失去”改写成可恢复；若创造复制或命令复制出相同 `cacheId`，多个副本仍只能访问同一份缓存，销毁其中一份不能复制或误删其余副本仍可访问的库存；
- 个人缓存仍按玩家 UUID 建模，但不以读取旧 `test.N` 玩家缓存为设计目标；可以复用经过新不变量复核的代码结构，不能为旧数据格式保留兼容分支。

这会要求业务服务从“固定读取 `PlayerCacheAttachment`”改为“先解析 `CacheHandle`，再访问相同的缓存事务接口”。属于架构重构，不是简单改一个字段。

## 5. 补货箭头的新语义

### 5.1 数量公式

沿用既定口径，“实际数量”默认指**当前活动缓存格的 `storedCount`**，仍不统计普通背包、快捷栏或副手：

```text
shortage = max(0, minimum - storedCount)
requested = 当前物品、过滤版本和缓存对应的有效已请求量
uncovered = max(0, shortage - requested)
```

### 5.2 显示规则

| 条件 | 主状态 |
| --- | --- |
| `shortage == 0` | 不显示下箭头，即使后台仍有旧请求记录 |
| `shortage > 0 && requested > 0` | 绿色下箭头：“库存不足，已请求 X” |
| `shortage > 0 && requested == 0` | 灰色下箭头：“库存不足，尚未成功请求”，并显示本模组已知原因 |
| `requested > 0 && uncovered > 0` | 仍以绿色表示确有请求，tooltip 同时写“仍缺 Y”及后续请求状态 |

绿色箭头只证明本模组已向 Create 提交并登记请求，不证明纸飞机、蜂或包裹仍在路上。

### 5.3 显示消失不等于删账

当玩家手动存入物资，使 `storedCount >= minimum` 时，绿色箭头立即消失；但后台已请求记录不能因此删除。否则玩家再次消耗物资时会重复发单，而旧包仍可能迟到。

例：最低 100，缓存 0，已请求 100；玩家手动存入 100 后箭头消失。随后在旧包到达前消耗 80，缓存变 20，绿色箭头重新出现，因为那 100 的请求记录仍在；系统不会再为同一缺口重复请求。若旧包实际丢失，仍由玩家按格手动重置。

因此需要把 UI 状态和防重复账本彻底分开：箭头看“现在是否缺货”，账本看“系统已经承诺过多少”。设置面板可继续显示隐藏中的已请求量，避免它变成无法发现的陈年记录。

## 6. 满背包收货：推荐“收件口”，不扩展玩家物品栏

### 6.1 为什么不直接增加永久隐形槽

仅在玩家物品栏末尾伪造几个槽，会让原版菜单、存档、其他背包模组和运输模组对槽位数量产生不同理解；若这些槽可长期存包，还会变成没有界面、无法找回的额外仓库。外部运输也未必通过统一的槽位遍历投递，增加槽数本身不能保证纸飞机或运输蜂认得它。

建议实现专用**收件口**：匹配本模组地址与目标缓存的完整包裹尝试进入玩家物品栏时，服务端先模拟直接拆入缓存。只要事务能够安全接收，就在不占原版背包格的情况下完成收货。

### 6.2 接收规则

- 只接受本模组专用地址、目标 `cacheKey` 明确、包裹结构合法且玩家当前具备相应终端访问的完整 Create 包裹。
- 普通包裹、错误玩家、错误缓存、非包裹物品和不安全组件完全交回原路径。
- 先完整模拟，再提交；返回“投递成功”时，包裹减少量必须等于缓存增加量加残包保留量。
- 若整个包能拆空，收件口不保存任何物品，一个瞬时接收位即可连续处理多个包。
- 若只能部分接收，当前先为每个缓存保留 **1 个真实残包槽**。它不占原版背包，首轮在 FMP 面板显示包裹图标、内容摘要和阻塞原因，缓存腾位后优先继续拆。
- 残包槽已有包且新包不能完全拆空时，本模组拒绝接管；调用方必须保留原包、让载具继续持有或按原模组规则掉落，不能报告成功后吞包。
- 残包槽不能放普通物品，也不能由玩家把任意包拖入当隐形仓库。需要取出时，只能转入真实背包／光标；没有位置则不取出。

一个残包槽足以解决正常补货，因为与缺口匹配的包应在进入时立即拆空；更多槽主要扩大额外存储和故障面。**“在面板显示完整残包槽”是待实机验证的表现方案，不是永久 UI 承诺。**底层残包状态不得依赖槽位是否可见，这样实测若认为它干扰界面，可改为不可见收件位，只保留阻塞图标、摘要或取回入口，而不迁移或丢失残包。

本轮试玩重点记录：残包实际出现频率、玩家是否会误把它当额外仓库、一个槽是否经常阻塞新包、可见槽是否抢占主操作注意力，以及隐藏后是否仍有足够的故障可见性。

### 6.3 必须验证的真实入口

“收件口”是否能被使用取决于包裹进入玩家的实际代码路径，不能只写一个虚拟容器便宣称完成。后续实现研究至少覆盖：

1. 地面包裹实体被满背包玩家拾取；
2. 从打包机／容器手动拿取；
3. Package Couriers 纸飞机交付；
4. Create: Mobile Packages 运输蜂交付；
5. 两个运输模组是否在调用插入前先检查原版空槽。

若第三方在接触玩家库存前就因“无空槽”拒绝交付，需要最窄的运行时兼容入口；这会修订此前“补货不写运输适配器”的实现边界，但不意味着接管寻路、目标登记或运输权限。

## 7. 三项调整共同暴露的路由问题

现有 `FMP@玩家名` 只说明送给哪个玩家。当玩家可以持有多个本件缓存、切换普通／个人终端或在包裹途中转交坠子时，仅凭玩家名无法安全判断包应进入哪份缓存。

每次请求必须固定：

- 目标 `cacheKey`；
- 发单时接收玩家；
- 物品精确变体与过滤版本；
- 请求 ID 与请求量。

还需验证 Create 打包链是否能把 `cacheKey/requestId` 作为不影响纸飞机和运输蜂寻址的包裹数据一路保留。若只能靠地址字符串承载，就必须分别实测两种运输模组能否解析带缓存令牌的地址。无法证明目标缓存时，收件口应保留原包并给出诊断，不能按“当前恰好打开的缓存”猜测入库。

这是本件缓存重构的前置技术研究，也是虚拟收件口能否安全落地的关键。

## 8. 推荐收口顺序

1. 两个终端形态、正式名称、普通坠子永久失去语义、保留整份缓存的个人化升级、既有个人缓存的全量原子合并规则和单个可见残包槽试验方向均已确认。
2. 验证双运输对缓存令牌与满背包投递的真实入口，形成技术证据。
3. 再修订项目计划、规格 01—04、补货／收包规格、测试策略和干净 schema 边界。
4. 用户另行明确授权新 schema 实施；不编写 `test.10—12` 数据迁移或兼容读取，也不清空用户测试存档。
5. 执行者先抽象统一 `CacheHandle` 与仓储接口，再做本件缓存；之后改箭头派生状态和收件口，最后回归合成、弹药和多终端。

## 9. 已确认决定与尚待收口项

### 9.1 已确认

1. 采用两个明确终端形态：普通供应链坠访问本件缓存，个人型坠子访问玩家缓存，不在同一物品上即时切换。
2. 普通坠子的最后一个合法入口真正毁坏后，缓存对玩家永久失去，不设置昂贵找回或其他恢复玩法。
3. 满背包收件采用专用收件口；部分接收先试每缓存一个面板可见残包槽。可见性明确标记为待实机验证，未来可换成不可见表现。
4. 箭头所看“实际数量”继续只指当前活动缓存格现货，不把原版背包、快捷栏或副手重新算入最低值。
5. 个人型坠子正式名为**供应链坠·私人定坠**（*Supply Chain Pendant: Made to Order*），由普通供应链坠保留整份缓存升级而来，不另起一份空库存。
6. 玩家已有个人缓存时允许自动合并：先按最终较高阶段模拟，只有普通坠子的全部库存和必要状态均可迁移时才原子提交；否则拒绝升级并提示库存无法转移，不允许部分迁移或溢出掉落。

### 9.2 尚待收口

1. Create、纸飞机与运输蜂能否完整保留缓存令牌，以及满背包时各自在哪个真实入口决定投递成败。
2. 本件缓存的持久化表示、最后合法入口灭失的安全判定、孤立记录清理策略及复制边界。
3. 干净新 schema 如何表达本件缓存、个人缓存、认领状态与缓存令牌，以及何时授权实现；不再讨论旧测试数据如何迁入。
