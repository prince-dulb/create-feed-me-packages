- **结论**：T03 完成。个人缓存现已拥有唯一的玩家 Data Attachment、五阶段不可变记录、修订号事务内核、真实槽位存取／升级适配、默认组件过滤、待收和收包日志上限、成功保存后日志清理与只读审计。42/42 JUnit、10/10 必需 GameTest、跨 JVM 玩家文件回读、普通客户端和专服启动均通过。

## 1. 数据权威与坏档处理

`create_feed_me_packages:player_cache` 注册为可序列化玩家 Data Attachment，并启用 NeoForge `copyOnDeath`。附件有三种状态：

| 状态 | 含义 | 保存行为 |
| --- | --- | --- |
| `ABSENT` | 玩家从未获得有效访问 | 不写入附件；只读审计不会触发初始化 |
| `READY` | 记录通过结构、所有者和物品注册表校验 | 按严格 codec 保存 |
| `BLOCKED_CORRUPT` | 无法解码、所有者不符、物品已移除或任一不变量失败 | 禁止事务，保留原始 NBT 副本；再次保存原样写回 |

不能直接使用 `AttachmentType.serialize(PlayerCacheRecord.CODEC)`：NeoForge 21.1.219 在附件 serializer 抛异常时会记录错误并跳过该附件，之后调用 `getData` 可能建立空默认值。当前自定义 serializer 在失败时返回受控坏档包装，因此负库存、重复过滤、超容量、未知 schema、所有者不符和注册物品缺失都不会被截断、转成空气或覆盖为空记录。

首次初始化只能由服务端 `PlayerCacheService.initialize(ServerPlayer)` 显式执行，UUID 从当前 `ServerPlayer` 取得。`audit` 使用 `getExistingData`，不会因管理员查询而创建库存。附件没有通用客户端同步 handler；T05 仍须通过面向当前玩家的有界快照发送展示数据。

## 2. 记录和事务内核

### 2.1 持久化记录

`PlayerCacheRecord` 固定 schema 1，并实现以下边界：

- 阶段为石头 `9/128`、铁 `16/256`、安山 `24/512`、黄铜 `30/1024`、坚固板 `36/2048`；格列表长度必须与阶段完全相等，索引连续。
- 同一物品过滤全玩家唯一；无过滤格不得有现货或启用端点；关闭的最低／最高端必须规范化为 `0/当前容量`。
- 现货是 `long`，但严格限制在当前单格容量；普通背包和待收不计入现货。
- 待收请求 ID 唯一，每物品最多 4 条、每玩家最多 144 条；第五条只合并到同物品、同过滤修订、同网络的最新兼容记录，溢出或无法合并即拒绝。
- 整包日志操作 ID 唯一，单条最多 9 种物品；最多 256 条且未压缩 NBT 编码总量最多 256 KiB；四份摘要各固定 32 B。
- `PREPARED` 会封锁自动收包但不被猜测重放；`COMMITTED` 只有在原版 `PlayerDataStorage` 成功替换玩家文件并触发 `SaveToFile` 后才从内存清理。刚写成的耐久文件仍含该终态条目；若随后崩溃，重载后可以再次安全清理，而不会把未落盘状态当成已保存。

### 2.2 单一提交规则

`CacheTransactionEngine` 是不接触外部物品引用的纯计划层。所有操作先检查当前记录和 `expectedRevision`，成功时只返回一份经重新校验的新记录且修订号恰好加 1；失败、模拟和无变化返回原记录。现已覆盖：

- 存入：`min(请求量, 来源可取量, 容量余量)`；向空格存入时过滤和真实计数属于同一计划。
- 取出：`min(请求量, 缓存现货, 目标可接收量)`。
- 设置／更换／清除过滤、两端阈值规范化、按格重置待收和来源优先级。
- 逐级升级、旧格不重排、新格追加、关闭的最高端随新容量更新；生存消费 1 件升级凭证，`instabuild` 消费 0 件。
- 待收登记／兼容合并和 `PREPARED → COMMITTED` 单向日志转换。

`PlayerCacheService` 只在服务端线程提交计划。真实 `Slot` 存取先复制并模拟，再重新核对来源／目标，按实际提交量修改外部槽，最后替换不可变附件；意外提交异常会恢复外部槽。普通实物必须与服务端注册物品的默认实例满足 `ItemStack.isSameItemSameComponents`，且空气和 Create `PackageItem` 外壳不能成为过滤。附加名称、容器内容、附魔等额外组件不会被剥除后入库。
