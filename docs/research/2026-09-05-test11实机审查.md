## 2. 已验证事实

### 2.1 JEI 已加载，失败的是 FMP 插件注册

用户的 JEI `19.51.0.417` 已在 NeoForge `21.1.249` 上进入运行期。`latest.log` 两次记录 FMP 插件 `SupplyChainJeiPlugin` 注册失败：

```text
java.lang.IllegalArgumentException: you cannot add a ghost ingredient handler for:
[Screen, InventoryScreen, CreativeModeInventoryScreen]
```

对 `test.11` 二进制反汇编可见，它确实向 `InventoryScreen` 注册了 `IGhostIngredientHandler`；JEI `19.51.0.417` 的 `GuiHandlerRegistration` 又把 `InventoryScreen` 明确列入禁止清单。因此：

- “JEI 19.44+ 在用户平台无法加载”不是本次失败原因；
- 将开发基线降为 `19.21.0.246` 不能作为兼容修复；
- 编译 API 下限可以因本地开发运行条件单独选择，但 `v0.1.0` 的兼容验收仍须覆盖用户实际使用的 `19.51.0.417`，并按计划复测当时适用的 1.21.1 最新版；二者不得混称为支持上限。

当前工作区在 05:35 后出现了尚未交付的草稿：已移除 `InventoryScreen` 的禁止注册，并尝试通过 JEI runtime 读取鼠标下物品。方向可用，但仍须解决无 JEI 时的类加载隔离、`onRuntimeUnavailable` 清理以及最终交互规格，不能把工作区草稿当作已通过。

### 2.2 收包扫描在事务日志摘要阶段崩溃

`latest.log` 共记录 **365 次**同源失败，约每秒一次：

```text
Package receive scan failed for PRdulb
java.lang.IllegalStateException: Can't access registry ResourceKey[minecraft:root / minecraft:enchantment]
at ...PackageReceiveService.digestOfRecord(PackageReceiveService.java:345)
```

`test.11` 二进制使用带注册表组件的 `PlayerCacheRecord.codec(provider)`，却把记录直接编码到裸 `NbtOps.INSTANCE`；玩家缓存中只要已有附魔书等注册表组件，即使本次包裹装的是另一种普通物品，也会在生成事务摘要时失败。`digestOfPackage` 同样使用裸 `NbtOps`，组件包裹也有同类风险。

这证明收包失败与运输路线、目标地址改写无关；用户从打包机直接取包也会稳定触发。当前工作区 05:33 后把两个摘要改为注册表感知的 serialization context，方向正确，但必须补充下列回归后才能关闭：

1. 玩家记录中另一个格保存附魔书等注册表组件，本次收到普通物品包；
2. 包裹本身含附魔或其他注册表组件物品；
3. 两种情况都要验证包裹减少量等于缓存增加量、待收只结算一次、完整组件保持不变；
4. 同一持续异常不得再每秒输出完整堆栈，应按玩家／同类错误限频，同时保留首条可诊断证据。

### 2.3 UI 是明确的绘制层级错误

截图与录屏显示：鼠标携带栈的图标及数量 `64` 会盖在 FMP tooltip 上；携带附魔书时，图标又会盖住格下方的阈值滑条。`test.11` 的调用顺序是先在 `renderCachePanel` 内画 tooltip／设置面板，最后再调用 `renderCarriedAboveOverlay`，后者还额外抬高 Z 层重新绘制携带物。

所以这不是字体包导致的文本缺字，也不需要继续向用户询问字体。修复应建立单一、可说明的层级顺序：

1. 面板、物流格与滑条；
2. 必要时重绘鼠标携带物；
3. FMP tooltip、错误提示和模式提示最后绘制。

若携带物与 tooltip 同时存在，tooltip 必须处于最上层；打开某格滑条时，携带物不得盖住滑条的轨道、端点或数值。

### 2.4 创造目录物品只能建立零库存过滤

创造目录光标上的物品可能只存在于客户端，服务器菜单并没有相应来源栈；`test.11` 将它当成真实 `CARRIED_SLOT` 来源，所以服务端正确返回“来源物品已不存在”。

玩家看到的面板和点击动作仍应与生存模式一致，但服务端语义必须区分：

- 生存背包／创造模式“生存物品栏”中的真实栈：设置过滤并转入真实数量；
- 创造目录生成的光标栈：只按 JEI ghost 同类路径设置精确过滤，缓存数量保持 0；
- 两条路径都由服务端校验模板，不能把创造物品变成缓存现货。

这属于实现修复，不是“创造 UI 特殊化”的产品变更。

## 3. 产品问题分析

### 3.1 未绑定坠子

**建议维持现规格**：只要有效佩戴坠子，本地个人缓存、过滤和阈值设置都可用；未绑定只禁止向 Create 网络发新请求。原因是物资与设置归玩家，网络绑定归坠子。清除绑定或准备换网时，不应顺带锁住玩家自己的现货。

界面应把状态说清：`未绑定网络；本地缓存可用，补货暂停`，阈值旁可提示“绑定后按此数值补货”。这样玩家设置最低数量不会被误解为已经在发单。

### 3.2 手动拆包后待收箭头

本次箭头不消失是 2.2 的下游结果：收包扫描在真正提交前崩溃，当然没有结算待收。修好收包后，正常路径应在完整专用包进入本地物品栏时完成一次到货记账，玩家无需手拆。

**不建议**用“背包里出现同种散装物品”或“玩家手动存入同种物品”自动清待收。这些物品可能来自别处，无法证明原包已经抵达，会隐藏仍在路上的实物并破坏防重复发单语义。按格手动重置继续作为兜底。若修复后仍能稳定复现“FMP 包在扫描前被玩家打开”的竞态，再针对专用包的打开动作接管，不用散装物启发式猜测。

### 3.3 JEI 中键选品模式候选

JEI 禁止在 `InventoryScreen` 使用标准 ghost handler，因此建议把用户提出的中键方案做成**定点、一次性的选品模式**，避免全屏劫持鼠标：

1. 默认键为鼠标中键，并作为可改键位；只有中键点击一个**空的、已解锁物流格**时才进入模式，该格成为目标。
2. 目标格高亮，显示“从 JEI 选择物品；Esc／右键取消”。
3. 模式中单击 JEI 物品即可把其精确组件模板设到目标格；若技术上稳定，也接受从 JEI 拖动后释放，但不要求玩家再把物品拖回已经选定的格。
4. 成功后自动退出。Esc、右键目标格、再次中键目标格、关闭界面、失去有效佩戴／访问、目标格被占用或快照修订失效时取消。
5. 未进入模式时 JEI 的点击、查看配方、收藏和中键行为不受影响；没有安装 JEI 时该入口不崩溃，可提示“需要 JEI”或无操作。
6. 选品只建立零库存过滤，服务端继续执行 1,024 字节模板上限、精确变体唯一性和修订校验。

当前工作区草稿是“在界面任何位置按中键切换全局模式，再拖到任意格”，与这个候选不同，也会抢占 JEI／创造界面的中键；在用户确认前不得作为定案交付。

4. 带注册表组件的玩家记录和组件包裹均能自动收包；待收清零，组件原样，包裹与缓存守恒，日志不刷屏。

- UI 修复只有代码与自动构建结论，没有新截图证明携带普通 64 栈、携带附魔书、tooltip 和滑条的最终层级。它可以进入下一轮人工验收，但不能在验收前称为已关闭。

因此 `test.12` 可视为根因修复检查点，不作为四项问题的最终复测包。先收口第 3.3 节交互决定，再补齐隔离、测试和交付文档，减少用户对已知不完整构建的重复测试。
