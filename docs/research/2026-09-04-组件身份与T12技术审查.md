# 组件身份与 T12 技术审查

- 核查日期：2026-09-04
- 核查角色：@Planner／技术组长
- 当前状态：**Scathiard 已于 2026-09-04 确认精确组件身份并授权玩家缓存 schema 1→2 迁移；当前进入执行者实施队列。T12 扣料时机已确认违反现行规格，受影响路径须暂停完成声明并返工。**
- 证据边界：本轮只回读项目规格、当前源码与本地锁定的 Create 6.0.10 JAR；未修改源码、构建配置、玩家数据或冻结交付，未运行 Gradle、GameTest 或游戏内复测。

## 1. 结论

不应继续把所有带额外 NBT／数据组件的物品拒之门外，但也不能“允许 NBT”后仍只按物品 ID 计数，或在匹配时忽略组件。推荐把缓存的基本身份从 `itemId` 改为**精确物品变体**：

> 精确物品变体 = 物品注册 ID + 完整持久化数据组件；堆叠数量不属于身份。

这样才能让不同 TaCZ 弹种、不同气量的铜背罐、不同附魔或其他组件状态保持彼此独立。任何省略、清洗或模糊匹配都会把不同实物混成同一份抽象计数，最终不是串货，就是取出时无法还原原物。

## 2. 已固定的产品规则

1. 一个物流格保存一份权威的完整 `ItemStack` 模板，模板数量固定为 1；该格另用 `long` 保存真实件数。
2. 存入、取出、收包、残包续收、Create 库存查询、Create 请求、合成取料和弹药候选选择，都按“同物品且完整组件相同”匹配。实现语义应等价于 `ItemStack.isSameItemSameComponents`，不得退化为裸 `itemId`。
3. 同一个**精确变体**只允许设置一格；同一物品 ID 的不同组件变体允许各占一格。这会替代旧的“同一物品 ID 只能一格”。
4. 从缓存取出的实物必须逐字保留模板组件，并遵守该变体的原生最大堆叠数；不能按默认实例重建，也不能硬编码 64。
5. 从背包拖入带组件实物时，直接以该实物的完整组件设过滤并存入；不得先剥离组件。JEI 能提供具体子类型栈时保留其组件，只提供普通栈时才得到普通默认变体。Ghost 模板仍不生成物资。
6. 铜背罐按精确气量区分。例如满气、半气和空背罐是三个不同变体；首轮不提供“任意有气背罐”或“气量至少为 X”的范围过滤。
7. TaCZ 只有在锁定目标版本并证明弹种身份位于可稳定保存、比较和请求的持久化组件后，才算完成兼容。组件缓存是必要基础，不等于自动完成枪械取弹、装填和射击适配。
8. 无法完整编解码、超过服务端安全大小上限，或其组件引用外部库存／对象且复制语义无法证明安全的实物，应整体拒绝设置和存入，并给出原因；不得静默删组件后接收。具体大小上限和高风险组件判定由技术 Spike 依据 Minecraft／NeoForge 编解码与网络包上限固定。
9. 过滤、请求与收包必须使用同一份规范化编码和相等关系。不能出现“UI 看作一种、网络请求另一种、包裹接收又按第三种规则”的身份分裂。

## 3. 为什么不能只写“允许 NBT”

### 3.1 忽略组件会串货

若唯一键仍是 `itemId`，两个 TaCZ 弹种或两个不同气量背罐会共享格子、阈值和在途账。网络可能按裸 ID 请求到任意变体，缓存也无法知道应还原哪一份组件。

### 3.2 清洗组件会损坏物品语义

Create 6.0.10 的 `BacktankUtil#getAir` 从 `AllDataComponents.BACKTANK_AIR` 读取气量，`consumeAir` 再通过 `ItemStack.set` 改写该组件。因此“充了气的铜背罐”不是默认背罐的显示差异，而是行为所依赖的真实组件状态。把它转为默认模板会丢失用户想请求的气量身份。

### 3.3 全量放行仍需安全边界

一些带组件物品可能携带很大的嵌套数据、UUID、外部存储引用或第三方 capability 的序列化状态。缓存必须能证明完整往返编码、比较稳定和复制安全；否则“保存一个模板”本身就可能制造膨胀、复制外部库存或不可恢复数据。安全拒绝应发生在建格／存入前，不应等物资已经进入缓存后才发现无法输出。

## 4. 当前实现受影响范围

当前代码不是“已经支持组件但暂时拒绝”，而是从领域模型到网络协议都只保存 `itemId`：

- `FilterTemplate` 只有 `ResourceLocation itemId`（`src/main/java/dev/scathiard/feedmepackages/domain/cache/FilterTemplate.java:9-12`）。
- `PlayerCacheRecord` 当前为 schema 1，并按 `ResourceLocation` 检查重复过滤和汇总在途（同目录文件第 34、92—125、188—200 行）。
- `PendingInboundRecord`、`PackageJournalEntry`、`CacheSlotSnapshot` 与 `SetFilterPayload` 也以 `itemId` 为身份。
- T12 当前从过滤 ID 构造新的默认 `ItemStack`，因此即使 UI 允许带组件物品，弹药输出仍会丢掉组件。

这项改变会重新打开至少以下工程面：

1. T02 规范键 Codec、模板载荷、菜单快照与协议限额；
2. T03 玩家数据、迁移、事务与跨 JVM 回读；
3. T05 过滤建立、唯一性、同步快照、客户端渲染和安全拒绝；
4. T06 Create 精确查询、请求与在途键；
5. T07 包裹收据、部分收包、残包与日志键；
6. T10／T11 合成和 JEI 具体变体；
7. T12 弹药选择与实体组件保真；
8. T13—T15 回归、存档兼容与最终交付门。

### 4.1 已确认的 schema 2 迁移合同

该项属于存档 schema 变更；Scathiard 已于 2026-09-04 明确授权按以下合同实施：

- schema 1 的每个 `itemId` 过滤迁移为该物品的服务端默认完整变体；库存数量、阈值、启用状态、格位和玩家阶段不变；
- 旧待收记录迁移到同一默认变体，数量、请求 ID、网络、格位、过滤修订和提交时间不变；
- 包裹日志须转换为可区分变体且仍能阻止旧包重复结算的格式，迁移不得清空收据或把迟到包结算两次；
- 任一旧 ID 已不存在或默认实例无法安全编码时，整份玩家记录不得静默丢弃；须保留可诊断失败状态并停止该玩家的缓存事务；
- 升级后首次成功保存才写 schema 2，并保留可自动测试的 schema 1 夹具。

## 5. T12 高风险规格违例

本项与组件提议相互独立，已有直接源码证据，不等待 schema 决策。

### 5.1 已观察事实

- `ProjectileAmmoService.onGetProjectile` 在 `LivingGetProjectileEvent` 查询回调中直接调用 `withdraw`、提交玩家记录，随后才把箭交给事件（`src/main/java/dev/scathiard/feedmepackages/consumption/projectile/ProjectileAmmoService.java:30-68`）。
- 当前 GameTest 两次调用 `player.getProjectile` 就断言缓存从 8 降到 7、再降到 6；弩测试也只查询一次便断言扣 1（`src/gameTest/java/dev/scathiard/feedmepackages/ProjectileAmmoGameTests.java:35-49,76-85`）。这些测试把当前错误语义固化成了通过条件。
- 已确认规格明确要求：查询和取消不扣；弓在成功发射时扣；弩在成功写入 `CHARGED_PROJECTILES` 时扣，之后发射不再扣；连续查询 20 次而未释放时数量与修订均不变（`docs/开发计划书/specs/06-弓弩弹药取用.md:33,113-124,140,208-215`；`AGENTS.md:92,144`）。

因此 E-0014 的“T12 完成”和 test.9 弹药验收结论不能成立。反复查询或取消蓄力可能无声消耗缓存箭矢，61/61 GameTest 只证明代码符合错误测试，不能证明符合产品规格。

### 5.2 暂停边界与解除条件

- 暂停 T12 完成声明、test.9 的弹药验收结论以及依赖 T12 的 T15 最终交付；T10、T11 和其他无关路径不因此自动撤销。
- 执行者可自行选择满足事务守恒的最窄 hook，不由主策指定代码写法；但不能用纯查询扣料，也不能用“先扣后猜测是否成功”的补偿逻辑掩盖提交点缺失。
- 至少补齐真实流程测试：20 次查询不变、弓取消不变、弓成功发射扣 1、弩中断不变、弩成功装填扣 1 且发射不再扣、无限／创造／多重射击、中途卸下、组件弹药原样进入投射物或装填组件。
- 自动测试必须经过真实提交路径，不能只直接调用查询 API 后断言扣料。游戏内手测仍用于验证交互链，不能由服务层单测替代。
