# T12 通用弹药消费入口核查

- **核查日期**：2026-09-02
- **目标版本**：Minecraft 1.21.1、NeoForge 21.1.219
- **证据来源**：本地锁定构建的合并运行 JAR、官方 NeoForge sources JAR 与官方映射；没有进行游戏内兼容测试

## 结论

T12 不应按原版弓、弩物品 ID 写两个独立特例。目标版本已有共享的投射物查询与消费链，可以按协议接入：

1. `Player#getProjectile(ItemStack)` 先确认消费者是 `ProjectileWeaponItem`，再使用该物品提供的合法弹药谓词扫描双手和玩家物品栏。
2. 每次返回前都经过 NeoForge `CommonHooks.getProjectile`，触发 `LivingGetProjectileEvent`；事件公开消费者栈与当前投射物栈，并允许替换候选。
3. `ProjectileWeaponItem.draw` 调用共享的 `useAmmo`；后者根据创造、无限和附魔弹药消耗计算实际数量，再对来源执行 `split`。

因此，沿用 `LivingEntity#getProjectile` 和 `ProjectileWeaponItem.draw/useAmmo` 的第三方投射武器具备无需按物品注册适配的技术基础。是否完整兼容仍要用非原版测试子类及真实第三方物品验证，不能仅凭继承关系写成已通过。

## 为什么不全局拦截数量减少

`ItemStack.shrink`、`split` 和 `consume` 是最底层数量操作，食物、容器、机器、方块实体、配方和任意模组代码都会调用。到这一层时通常已经缺少：

- 哪个物品是消费者；
- 被需要物品的合法谓词和组件要求；
- 应当优先使用背包还是缓存；
- 当前调用只是模拟、查询、客户端预测，还是不可取消的服务端提交；
- 消费失败时如何回滚武器或机器的其他状态。

在这些方法上全局补缓存会把无关数量变化误判成弹药需求，并可能造成重复扣除、生成物品或破坏第三方事务。可行边界是建立统一缓存消费服务，再为具有明确查询和提交语义的消费协议增加适配器。

## T12 实现边界

- 共享查询：`LivingGetProjectileEvent`／`LivingEntity#getProjectile`。
- 共享提交候选：`ProjectileWeaponItem.draw/useAmmo`；最终注入点须在 `SPK-AMMO-01` 中验证取消事件与失败边界。
- 必测消费者：原版弓、原版弩、一个没有登记物品 ID 的非原版测试子类。
- 降级：自写背包扫描和扣料、未使用标准链且没有适配器的物品保持原行为，不访问缓存。
- 后续扩展：Create 土豆炮、枪械或其他“消费者物品”只有找到稳定的需求和提交入口后，才增加独立适配器；适配器复用同一缓存消费事务，不复制库存逻辑。
