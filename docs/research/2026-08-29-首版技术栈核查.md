## 1. 结论

首个可玩版本采用以下**开发与验收基线**：

| 项目 | 基线 | 装载关系 | 选择理由 |
| --- | --- | --- | --- |
| Java | 21，64 位 | 构建与运行必需 | NeoForge 对 Minecraft 1.20.5 及以上要求 Java 21 [N1] |
| Minecraft | 1.21.1 | 必需 | 用户已锁定的平台 |
| NeoForge | 21.1.219 | 必需 | Create 6.0.10、Mobile Packages `1.21.1-0.7.7`、Package Couriers 2.3.0 的源码构建基线一致 [C1] [M1] [P1] |
| Create | 6.0.10；开发坐标使用 `6.0.10-280` | 必需 | 该版本是 1.21.1 的正式发布；两个运输模组的固定源码都按此坐标开发 [C1]—[C3] [M1] [P1] |
| Curios | `9.5.1+1.21.1` | 必需 | 两个运输模组的固定源码共同采用此版本；首版只做供应链坠 [M1] [P1] |
| JEI | `19.21.0.247` | 可选兼容 | 两个运输模组与 Create 的固定构建共同采用；缺失时核心、原版配方书和背包实物设过滤仍可使用 [C1] [M1] [P1] |
| Create: Mobile Packages | `1.21.1-0.7.7` | 可选提供者，首版验收对象 | 已有正式 NeoForge 1.21.1 发布；源码快照与发布版本号一致 [M1] [M2] |
| Create More: Package Couriers | `2.3.0` | 可选提供者，首版验收对象 | 已有正式 NeoForge 1.21.1 发布；源码快照与发布版本号一致 [P1] [P2] |

这里的“可选提供者”是装载关系，不是验收降级：模组在两者都缺失时仍须安全启动，但首版发布门必须分别通过纸飞机、运输蜂以及二者共存的真实运输测试。

Create 的 `mc1.21.1/dev` 已继续演进到 6.0.11。首版不跟随移动分支静默升级；先用两个运输模组共同对齐的 6.0.10 建立可复现基线，再通过 `SPK-DEP-02` 单独验证 6.0.11。开发基线改变必须更新本文件、架构、测试矩阵和变更记录。

## 3. 已验证的 1.21.1 平台能力

### 3.1 玩家数据与饰品数据

NeoForge 1.21.1 Data Attachments 可把可序列化数据附着到实体；实体附件默认不随死亡复制，`copyOnDeath` 可明确开启。客户端同步需要模组自己发送包 [N2]。因此：

- 个人缓存、格子、升级、来源偏好和待收记录用一个玩家附件保存；注册时开启序列化与 `copyOnDeath`。
- 供应链坠的网络 UUID、逐件禁用状态与实例 ID 属于具体 `ItemStack`，使用 1.21.1 数据组件；数据组件可同时配置磁盘 `Codec` 和网络 `StreamCodec` [N3]。
- 玩家附件是服务端真相；客户端只收到界面需要的只读快照，不持有可提交的库存副本。

### 3.2 网络负载

NeoForge 1.21.1 通过 `RegisterPayloadHandlersEvent` 和 `PayloadRegistrar` 注册自定义负载，可区分发往服务端和客户端的 play payload。处理器默认在主线程执行；客户端发往服务端的负载上限低于 32 KiB [N4]。因此：

- 客户端只发送“操作意图”：格号、操作类型、期望修订号和必要参数；不上传整份玩家记录。
- 服务端在主线程重新读取佩戴状态、玩家身份、网络、格子和来源物品后提交事务。
- 快照按初始全量与后续增量分开；36 格数据必须在最坏组件模板下仍低于负载限制。

### 3.3 Curios 槽位

Curios 官方文档建议优先复用预设槽；`necklace` 用于项链或护符。预设槽类型不会自动加到玩家，物品通常通过对应 `curios:<identifier>` 物品标签获得插槽资格 [U2] [U3]。首版采用：

- 给玩家增加一个 `necklace` 槽的项目数据；与其他模组对相同槽的声明按 Curios 合并规则共存。
- 把供应链坠加入 `curios:necklace`，不创建项目专属槽。
- 服务端通过 Curios 物品栏查询实际装备的供应链坠；只放在普通背包中不激活。
- 多件已启用供应链坠的同网／异网判定由本模组执行，不依赖客户端槽位显示。

### 3.4 Create 请求与包裹

Create 6.0.10 的 `LogisticsManager` 提供网络汇总、单物库存查询和 `broadcastPackageRequest`。广播方法返回 `boolean`，但该返回值只覆盖“订单非空且相关打包机未被忙碌阈值拒绝”；源码中即使没有找到可供货请求，也可能走到 `true` [C5]。因此不能把这个布尔值解释为“足量物资已装包”或“包裹已起飞”。

Create 的包裹为 9 槽，地址和内容保存在数据组件中；`PackageItem` 提供地址匹配、地址读取和内容读取。部分入库可以在服务端构造剩余内容并重新写回同一包裹数据组件，但必须验证外部提供者是否依据订单数据或内容组件判断后续行为 [C6]。

首版采用的记账口径：

1. 请求前用服务端默认实例做同物同组件的准确库存摘要来计算本轮上限；裸 `itemId` 不能安全区分变体时不发单。
2. 只在广播未被忙碌拒绝时增加本地“已请求待收”数量。
3. 该数量是本模组发出的请求承诺，不是对外部包裹位置的追踪证明。
4. 当前 plan-v1.0 在真实专用包第一次被本地观察时，按其中与服务端默认实例匹配且当前有同物过滤的数量结算待收一次；未能入库的余货由同一包裹和收据继续持有，后续续收不重复结算。迟到或无对应待收的真实包仍按地址、过滤和容量处理。
5. 请求与实际装包之间的竞态由按格手动重置解决，不自动赔付或超时重发。

具体调用序列必须先通过 `SPK-CREATE-01`，尤其要验证缺货、部分库存、打包机忙碌和同 tick 竞争时的返回与扣库关系。

### 3.5 JEI 与测试工具

JEI 提供 ghost ingredient handler，适合把 JEI 中拖出的物品模板交给物流格；也提供 recipe transfer handler，用于控制向原版合成菜单填料 [J2] [J3]。二者是两条独立兼容路径，分别验收。

NeoForge Game Tests 可在游戏内结构模板中验证交互，并可用 `gradlew runGameTestServer` 运行专用测试服务器；需在 NeoGradle 配置中关闭该运行项的强制退出，才能让返回码正确反映失败数 [N5]。工程创建后把该命令写入 `AGENTS.md`，当前不伪造可运行脚本。

## 4. 依赖装载策略

| 模块 | 可以引用的依赖类型 | 装载条件 | 缺失行为 |
| --- | --- | --- | --- |
| `core`、`storage`、`network`、`client` | Minecraft、NeoForge、Create、Curios | 总是 | 任一必需依赖缺失，由加载器给出依赖错误 |
| `compat.jei` | JEI API | JEI 已安装且版本范围匹配 | 不注册 ghost／transfer handler；核心照常启动 |
| `compat.mobilepackages` | Mobile Packages `1.21.1-0.7.7` 类型 | 对方已安装且自检通过 | 蜂路线不可用，展示明确原因；不加载对方类 |
| `compat.packagecouriers` | Package Couriers 2.3.0 类型 | 对方已安装且自检通过 | 纸飞机路线不可用，展示明确原因；不加载对方类 |

可选兼容类必须隔离在自己的包与初始化入口中。核心接口只交换本项目定义的值对象，不在公共签名中暴露可选模组类型。缺少可选模组的专服启动测试是发布门，不允许通过捕获 `NoClassDefFoundError` 后继续运行来掩盖错误初始化。

Spike 不是产品问题，也不允许开发者自行改需求；每个 Spike 都有固定输出和失败处理。

| ID | 要回答的问题 | 最小实验 | 通过证据 | 失败处理 |
| --- | --- | --- | --- | --- |
| `SPK-DEP-01` | 上表基线能否解析并同时启动 | 创建隔离工程后解析依赖，启动客户端与专服 | 锁文件／依赖报告、启动日志和版本清单 | 不升级游戏版本；在 1.21.1 内选择共同可用构建并更新矩阵 |
| `SPK-DEP-02` | Create 6.0.11 是否可作为兼容上界 | 复制隔离实例，仅替换 Create，跑核心与双运输冒烟 | 对比 6.0.10 的编译、启动和运输结果 | 0.1.0 继续钉住 6.0.10，不阻塞发布 |
| `SPK-CREATE-01` | Create 请求 API 的真实受理量如何判定 | 对 0、部分、足量库存和忙碌队列调用查询与广播 | 网络扣库、出包量、返回值和本地记账逐项记录 | 将不可靠结果限制为可手动重置的请求承诺，不猜包裹状态 |
| `SPK-PKG-01` | 能否原子地部分改写包裹且保留地址／订单信息 | 对 9 槽、多物品、残包重复扫描做守恒测试 | 前后组件快照与物资总数一致 | 停止自动部分拆包，先实现安全的完整格转移，不吞余物 |
| `SPK-INV-01` | 哪个服务端入口能可靠发现进入玩家主物品栏的完整包 | 比较插入事件、槽变化与有界周期扫描 | 两个提供者所有到货路径均只触发一次处理 | 采用有界主物品栏扫描与包内容幂等提交，不接管第三方背包 |
| `SPK-JEI-01` | JEI `19.21.0.247` 的 ghost 与 recipe transfer 是否覆盖目标界面 | 对背包页、2×2、工作台 3×3 建最小插件 | 模板不生物资；混合来源转移守恒 | 保留原版配方书主线，JEI 不得阻塞核心 |
| `SPK-AMMO-01` | 弓与弩在哪个提交点真实扣箭 | 覆盖拉弓取消、无限、创造、弩装填、发射和多重射击 | 查询不扣、成功操作只扣一次 | 收窄到已证明的原版事件／注入点，不改武器规则 |
| `SPK-UI-01` | 左侧面板如何与配方书、JEI 和缩放共存 | 3 个 GUI 缩放档、4 个分辨率、JEI 开关组合 | 无遮挡、越界或不可达控件 | 启用滚动／折叠布局，不减少已确认功能 |
| `SPK-LIC-01` | 实现是否包含第三方受限材料 | 交付前审查依赖、JAR 内容、资源来源和声明 | 无第三方源码／资产／JAR 被打包；声明完整 | 移除该材料；若确需派生则停止并单独取得许可 |

## 6. 本轮没有验证的内容

- 没有证明依赖坐标能在当前机器解析。
- 没有证明 `FMP@玩家名` 已同时通过两个运输模组的地址、权限和完整包交付。
- 没有证明 Create 的请求布尔值与实际出包量一致；源码反而说明不能这样解释。
- 没有证明玩家物品栏存在覆盖所有外部插入路径的单一事件。
- 没有证明 JEI、Curios 或弓弩接入点在目标组合中无需局部注入。
- 没有执行许可证法律意见；本文件只据许可证原文约束工程行为。

这些未验证项都已转成有退出条件的 Spike，不留作实现者临场决定。
