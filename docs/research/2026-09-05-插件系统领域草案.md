# 2026-09-05 插件系统领域草案

## 1. 状态与边界

- **状态**：核心交互、计算规则与 1—5 级插件槽数量已确认；具体插件、首发版本和配方仍待讨论，尚未授权实现。
- **已确认方向**：供应链坠体系可以增加可安装插件。**功能类／数值类只是一套策划分析词汇，不是玩家可见分类，也不产生两类物品、两种槽位、两页界面或分类配额。**游戏内只有一种插件与一种通用插件槽，任意合法插件都能进入任意插件槽。Scathiard 提到的“死亡不掉落”“提高最大单格数量”只是说明两种效果算法的例子，不自动成为首批插件或完整范围。
- **与永久升级的边界**：1—5 级扩容由 Create 序列组装完成，是缓存的永久结构成长；插件是可装、可拆、可换的构筑强化。两者是并行的两套增强，互不取代；某一构筑目标的最高能力来自 5 级结构与对应插件配置的结合。
- **与第三方插件 API 的边界**：当前“插件”指玩家安装的模组内物品模块，不自动承诺首版公开 Java API，也不等于精妙背包等第三方背包兼容插件。

### 1.1 两套增强的定位

| 成长系统 | 提供什么 | 代价与性质 | 不负责什么 |
| --- | --- | --- | --- |
| **1—5 级结构成长** | 格数、基础单格容量，以及每级一个插件槽的结构底座 | Create 序列组装、逐级、永久、不可拆回 | 不生成插件，也不提供具体插件效果 |
| **插件构筑强化** | 离散功能与有界数值修正 | 占用有限通用槽、可拆换、可组合 | 不改写缓存阶段，不允许跳过永久扩容链 |

插件的派生数值以当前等级基础值为输入。5 级但不装插件，只获得最高结构底座；低等级装插件，也不会被视为已经完成高等级扩容。所谓“最大能力”是 5 级再加上针对某一目标的合法插件构筑，并不意味着互斥插件可以同时生效或玩家能够装下全部插件。

Scathiard 已确认正式等级只使用 **1—5 级**，每级解锁一个通用插件槽，依次为 1—5 槽。等级负责提供可装配结构，玩家仍须另行制造和选择插件才能获得构筑效果，因此两套增强仍不互相替代。同一插件集合用于更高等级时，其对应最终能力不得反而低于较低等级。“石／铁／安山／黄铜／坚固板”不再是玩家等级名，也不预先规定序列配方材料。

## 2. 策划分析用的两种效果算法

本节只帮助策划和实现者判断效果如何合成、冲突与验收。玩家只会看到插件自身的名称、效果、数值与限制，不会看到“功能类”“数值类”的分类标签。

### 2.1 功能类

功能类改变一条离散行为规则或提供一个新动作，例如生命周期处理、物流策略、交互入口或诊断能力。其特征是“有／无”或模式选择，而不是简单加减一个数值。

已确认规则：

- 同一种功能插件允许重复安装，每个实体插件都独立占用一个真实槽位；只要至少安装一件，该功能就视为生效，安装更多件不会重复执行或增强效果；
- 拆下一件重复功能插件时，只要仍有同功能插件留在插件舱，功能继续生效；每件插件仍可分别拆下并原样返还，不能因效果只计算一次而合并或吞掉实体物品；
- 互斥功能使用明确的冲突组，安装前给出原因，不按槽位顺序偷偷决定赢家；
- 功能插件不能绕过核心物资守恒、服务端鉴权、有效佩戴、精确物品身份和真实包裹边界；
- 可能消耗物资或改变掉落的功能必须单独定义事务与失败规则，不能只有一个通用回调便任意改库存。

### 2.2 数值类

数值类只修改一个有界参数，例如某种容量、数量上限、批次规模或其他可量化指标。其特征是能显示“基础值 → 插件修正 → 最终值”的完整计算过程。

已确认规则：

- 数值插件也允许重复安装，每一件都按其声明的目标参数、运算方式、数值与优先级参与一次计算，最终结果受硬上限约束；
- 统一计算顺序为基础阶段值 → 固定增量 → 比例修正 → 最终钳制，使用安全 `long` 运算并拒绝溢出；
- 插槽顺序不得在未说明时改变结果；同一组插件换位置后应得到相同数值；
- UI 必须显示最终值及来源分解，不能只显示一个无法解释的结果；
- 初期禁止“某插件增加插件槽位”这类自举修正，避免移除插件后连承载自己的槽都消失。

## 3. 效果作用域与存储归属

功能／数值回答“效果怎样合成”，作用域回答“效果改哪一个对象”。这些都是策划与实现元数据，玩家界面不按它们分类。

| 效果作用域 | 含义 | 适合的效果 | 风险 |
| --- | --- | --- | --- |
| **终端效果** | 只改变当前通过该缓存工作的有效终端 | 终端交互、网络或掉落行为 | 必须明确多终端时作用于哪一件，不能顺带保护背包里的其他坠子 |
| **缓存效果** | 改变插件所在缓存的能力 | 存储、补货、残包、参数等缓存行为 | 降值或卸载时必须检查缓存状态仍可合法表示 |

**已确认的存储归属**：所有已安装插件都存入当前缓存唯一的通用插件舱。普通缓存的插件随 `cacheId` 和普通坠子转交，个人缓存的插件随玩家保留；私人定坠遗失、毁坏或重制不会令个人缓存突然失去插件或缩容。终端效果／缓存效果只控制插件怎样生效，不创建第二套物理槽位，也不把终端效果插件塞进坠子的 `ItemStack`。

“死亡不掉落”之类的终端效果若以后获准制作，表达为：当前玩家通过装有该功能插件的活动缓存使用终端时，保护实际佩戴的那件终端；它不保护背包里其他坠子，也不改变普通缓存被手动丢入岩浆或虚空后的永久失去规则。

## 4. 插件槽与所有权

每份缓存记录拥有一个**通用插件舱**，其中只有一种槽位：

- 任意合法插件都能放入任意空插件槽；槽位不检查“功能／数值”策划标签；
- UI 不分功能区、数值区或分类页，也不使用分类专属颜色、图标、配额或解锁线；
- 所有插件都允许重复放入。同功能重复件逐件占槽但只产生一次功能效果；数值重复件逐件参与计算并受统一硬上限约束；
- “能进同一种槽”不代表可以绕过插件自身的互斥组、容量安全、有效佩戴或服务端校验。安装失败反馈具体规则原因，不能伪装成槽位类别不符。

插件槽数量随当前缓存等级固定增长：

| 缓存等级 | 通用插件槽总数 | 本次升级新增 |
| --- | ---: | ---: |
| 1 级 | 1 | 初始获得 1 槽 |
| 2 级 | 2 | +1 |
| 3 级 | 3 | +1 |
| 4 级 | 4 | +1 |
| 5 级 | 5 | +1 |

等级升级只解锁一个新的空槽，不生成、复制、移动或改写任何插件。槽位属于缓存，不因同时佩戴多枚坠子而叠加；插件也不能反向增加插件槽。等级单向成长，因此正常玩法不存在因降级而令已安装插件失去槽位的路径。

安装后的插件保存实际模块身份，而不是只记布尔值；拆卸应返还原模块物品及其持久化组件。普通缓存永久失去时，其中插件与物资一同失去；个人缓存则在私人定坠遗失、毁坏或重制后继续保留插件。

## 5. 安装、拆卸与降值安全

插件适合通过面板中的小型插槽安装，因为序列组装已经承担制造成本与 Create 表达；插槽在这里负责可逆换装，不再冒充永久阶段升级。

所有换装都采用服务端“模拟 → 验证 → 原子提交”：

1. 验证当前有效佩戴、唯一活动缓存、来源物品和目标槽；
2. 模拟安装／替换／拆卸后的插件多重集合与全部派生参数，保留每一件重复插件；
3. 校验现货、过滤、阈值、待收、残包和其他状态仍合法；
4. 成功时才移动真实插件物品并更新缓存，失败时来源和缓存均不变。

移除数值插件可能降低容量。首选规则是：若任何格现货、活动阈值或必须保留的残包在移除后超出新上限，拒绝拆卸，并列出第一个阻塞格及超出数量。不得截断、掉落、静默禁用物资或先移除后进入永久不可见状态。

如果模组更新后某插件 ID 缺失、数据损坏或第三方插件实现不可加载，缓存进入可诊断的降级状态：允许安全取出，不接受会扩大问题的新存入／请求；不因无法解析插件就删物、降容量或清配置。

## 6. 私人化与插件合并

普通坠子私人化时，插件也是“全部迁移”事务的一部分：

1. 先取两份缓存中较高阶段；
2. 模拟合并插件舱并计算最终派生数值；
3. 再用最终格数、单格容量和残包能力检查全部物资；
4. 插件槽不足、互斥功能冲突、数值硬上限冲突或任何物资无法容纳时，均拒绝私人化并保持两边不变；同功能重复件本身不构成冲突，只按真实件数占槽。

不能先借普通缓存中的容量插件把物资塞入个人缓存，再因插件无槽可迁移而丢掉容量来源。插件合并与容量检查必须是同一事务中的固定顺序。

## 7. 制造与 Create 身份

插件本体原则上通过 Create 加工获得：序列组装、中间产物、机械手应用、机械压制等步骤按插件主题组合。概率失败只能消耗或返回可再制造的中间产物；已安装插件、装有真实缓存的坠子和个人缓存记录不参与随机销毁。

不同插件不必强行复制同一条配方。离散功能效果可以突出其机械动作，数值修正效果可以共享“未完成插件基板”再使用不同材料分支；这只是配方设计方法，不形成玩家分类。首版若只实现少量内部插件，仍应让注册与计算模型可以继续加插件，而不是在缓存服务中散落物品 ID 特判。

## 8. 候选能力地图，不是内容清单

下表只用于检验分类是否够用，不代表决定制作：

| 能力方向 | 策划算法 | 效果作用域倾向 | 需要特别审查 |
| --- | --- | --- | --- |
| 死亡时保留当前终端 | 功能 | 缓存或终端 | Curios 掉落规则、诅咒、复制与死亡事务 |
| 提高最大单格数量 | 数值 | 缓存 | 拆卸降容、阈值、收包与网络载荷 |
| 改变残包处理策略 | 功能 | 缓存 | 真实包裹守恒、外部运输边界 |
| 增加某种有界处理数量 | 数值 | 缓存 | 服务器性能、硬上限与叠加顺序 |
| 增加诊断／预览能力 | 功能 | 缓存或终端 | 客户端只读、不能泄露他人缓存 |

任何后续想法在策划阶段先判断是离散能力还是数值修正，再决定效果作用域、冲突、重复安装结果、移除后果和制造路线；这些判断不改变玩家面对的通用插件与通用槽位，也不会因为示例出现在这里就自动进入 `v0.1.0`。

## 9. 首轮需要决定的问题

1. 插件系统进入哪个版本，首轮至少用哪两个真实插件验证，而不是只做没有内容的框架？
2. 每个首轮数值插件的具体修正量与硬上限是多少；不能只做一套没有平衡参数的通用计算器。
3. UI 是始终展示五个位置并锁住未解锁槽，还是只展示当前已解锁槽；这只影响表达，不改变 1—5 槽规则。
