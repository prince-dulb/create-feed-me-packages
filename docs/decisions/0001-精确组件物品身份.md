# 决策 0001：精确组件物品身份

- 日期：2026-09-04
- 状态：物品身份语义继续有效；schema 1 → 2 兼容部分已被 2026-09-05 预发布重构决定替代
- 决策人：Scathiard
- 影响版本：`v0.1.0` 及之后
- 技术审查：[组件身份与 T12 技术审查](../research/2026-09-04-组件身份与T12技术审查.md)

> **2026-09-05 后续决定：** 项目尚未发布首个正式版本，`test.N` 使用的 schema 与注册 ID 不构成存档兼容合同。下文“schema 1 → 2 迁移授权与合同”只记录已经发生的测试实现历史，不再约束重构后的首个正式版本。精确组件物品身份仍是现行产品决定；新缓存模型直接定义干净 schema，不提供旧测试 schema 的双格式解码、兼容别名或迁移模块，也不以兼容旧测试世界作为验收项。该决定不授权任何人删除用户测试存档。

## 决定

个人物流缓存允许保存带持久化数据组件的物品。项目不再把带额外 NBT／数据组件的实物统一转换为默认模板，也不再以裸物品 ID 作为缓存身份。

缓存中的基本身份改为**精确物品变体**：

> 精确物品变体 = 物品注册 ID + 完整持久化数据组件状态；堆叠数量不属于身份。

实现中统一使用不可变的 `ItemVariantKey` 值对象表达该身份。持久化以 Minecraft 注册表感知的 `ItemStack` 编解码为准，模板数量规范化为 1；运行时向外部接口提供的 `ItemStack` 必须是防御性副本。摘要或哈希只用于日志、定位和快速比较，不能代替完整身份做最终相等判断。

## 产品语义

1. 一个物流格只持有一种精确变体及其独立 `long` 数量；格内所有单位的物品与组件完全相同。
2. 同一精确变体在一名玩家的缓存中最多出现一格。同一物品 ID 的不同组件状态属于不同变体，可以分别占格并设置不同阈值。
3. 满气、半气和空铜背罐属于不同变体；半气背罐不能存进满气背罐格。不同 TaCZ 弹种只要持久化组件不同，也必须保持分离。
4. 背包存入、JEI ghost、Create 库存查询与请求、包裹接收、残包续收、合成取料、弹药选择和取出都使用同一精确相等关系。不得在任一路径降级为裸 `itemId`、忽略组件或重新构造默认实例。
5. 从真实背包／菜单槽设过滤时，服务端从实际来源栈取得完整模板，并把设过滤与真实转入作为同一事务。客户端提交的物品内容不是实物权威。
6. 从 JEI 设过滤时，JEI 提供具体子类型栈就保留其组件；只提供默认栈就建立默认变体。Ghost 只建立模板，库存仍为 0。服务端校验完整模板与大小，但不因此生成组件或物资。
7. 取出或消费时按模板生成组件完全相同的真实栈，并遵守该模板的原生最大堆叠数。缓存减少量必须等于目标实际接收或操作实际消费量。
8. 物品无法通过注册表感知编解码完整往返、解码后身份改变、为空气／包裹外壳，或规范模板编码超过 1,024 字节时，拒绝建格、存入和自动请求，来源保持不变并显示稳定原因。不得静默剥离组件。
9. 单次客户端模板意图仍须小于 8 KiB，完整缓存快照仍须小于 64 KiB；36 个满额模板也必须通过实际编码测试。若未来需要放宽单模板上限，应先分页或改变同步协议，不能直接突破现有包上限。
10. 组件在正常使用中发生改变后，该实物已经成为另一精确变体。只有已有对应格或另建新格时才能存入；首版不提供“忽略气量”“任意耐久”“至少某数值”等范围过滤，也不在一个计数格里混存异质状态。

## TaCZ 边界

此决策解决缓存保存和区分组件弹药的前置问题，不等于 TaCZ 已兼容。TaCZ 仍位于后续版本：执行前须锁定具体 1.21.1 NeoForge 构建，验证弹种身份能在持久化组件中稳定往返，并分别接入其真实备弹、装填、弹匣与开火提交点。不得修改枪包配置或清除弹种组件来伪造兼容。

## schema 1 → 2 迁移授权与合同

Scathiard 已于 2026-09-04 明确确认本决策，并授权玩家缓存数据从 schema 1 迁移到 schema 2。迁移必须满足：

- schema 2 的过滤、待收和包裹日志物品键均为 `ItemVariantKey`；客户端快照及相关意图同步使用同一身份。
- schema 1 的每个 `itemId` 过滤转换为该物品当时由服务端注册表构造的默认精确变体；库存数量、格位、阈值、启用状态、`filterRevision`、玩家阶段、取料偏好和总修订号不变。
- schema 1 的待收项转换到相同默认变体；请求 ID、数量、来源网络、原格、过滤修订和提交时间不变。
- schema 1 的包裹日志计数键转换到相同默认变体；收据、阶段和四类摘要不清空，不得让旧包重复结算。
- 解码器同时接受 schema 1 和 schema 2；新记录及成功迁移后的下一次保存写 schema 2。未知更高版本继续只读封锁。
- 任一旧物品 ID 已不存在、默认实例非法或迁移后不满足不变量时，整份玩家数据进入可诊断封锁；不得跳过该格、清空记录或用新空缓存覆盖。
- 迁移须用真实 schema 1 固定夹具验证跨 JVM 回读、重复加载幂等、死亡复制语义、待收／收据保持和失败原档不被空记录替代。实现不删除玩家文件，也不要求玩家手动清档。

## 被替代的规则

以下旧规则自本决策起失效：

- “同一物品 ID 只能设置一格”改为“同一精确变体只能设置一格”。
- “带额外组件实物不入库，二次确认后只建立默认模板”取消；相关二次确认状态和文案应移除。
- “缓存只保存 `itemId`，需要时构造默认实例”取消。
- “Create 只查询默认实例，特殊变体一律留包”改为“查询、请求和收包都按当前格的完整精确变体”。

## 未改变的规则

- 设置过滤不生成物资；JEI ghost 库存为 0。
- 缓存只统计自身现货，不统计普通背包、在途或远端库存。
- 非空格必须先取空才能更换或清除过滤。
- 包裹外壳与运输物格物品仍走各自专用校验，不作为普通材料过滤。
- 未佩戴、个人数据归属、网络绑定、阈值、容量、残包、手动重置、真实运输与物资守恒规则不变。
