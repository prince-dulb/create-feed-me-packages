## 1. 一句话定义

**Create: Feed Me Packages!** 为玩家提供一个可穿戴的个人物流终端：玩家在独立物流缓存中设定真实物资及补货阈值，Create 网络把物资打成真实包裹并由现有运输方式送来；缓存又能为已接入的合成与弹药消耗提供物资。

它不是无限物品模板、远程仓库瞬移器或新的全局运输系统。过滤、最低值和最高值只描述库存策略，不会凭空生成物资。

## 2. 产品原则

2026-09-06 test.16界面修订已确认：地址直接放在顶部横幅内、点击复制完整地址，长文本不能越框；等级成长优先横向扩列而非只拉长两列；真实残包存在时左上角以滑条角点同等大小的闪亮标记提示，无点击管理功能。具体显示列数与窄屏回退属参考实现选择，待实际体验。test.16按用户要求暂免自动测试，test.17恢复并补验，不以编译通过宣称游戏通过。

1. **真实物流**：补货必须从 Create 网络中的真实库存出发，经过真实打包与运输；本模组不直接在玩家端生成货物。
2. **物资守恒**：缓存持有真实物资。存入、取出、收包、合成、弹药和未来退货都只在成功提交时增减，任何失败不得复制、吞掉或补偿生成物品。
3. **终端决定访问，缓存决定归属**：普通供应链坠访问随物品转交的本件缓存；供应链坠·私人定坠访问当前玩家的个人缓存。
4. **未佩戴即不存在**：没有有效佩戴终端时，界面、存取、补货、收包、自动取料与未来退货均不出现也不运行，已有状态只被保留。
5. **精确物品身份**：物品注册 ID 与完整持久化数据组件共同决定物品变体；数量不属于身份。模组不再剥离 NBT／组件，也不把特殊物品静默降级成默认实例。
6. **服务端权威**：客户端只表达操作意图。缓存、网络请求、物品消费、升级、私人化与插件事务均由服务端重新读取真实状态并决定结果。
7. **Create 优先**：玩法表现、制造流程与交互语言服从 Create。DSP 只提供体验灵感，不要求复制 DSP 的设施或规则。
8. **低负担交互**：2026-09-06 用户明确要求尽量少文字、少层级，常规操作符合原版与 Create 的直觉。后台事务不能转化成要求玩家理解的管理面板或排障按钮；异常时仍须简短说明真实原因。当前先验证功能和操作，美术体系另作专题研究，不能未经许可复制第三方资产。

## 3. 玩家流程

### 3.1 建立普通供应链

1. 玩家制造 **供应链坠 / Supply Chain Pendant**。新坠子拥有自己的本件缓存引用，初始为 1 级、空物流格。
2. 玩家潜行右击一个能解析出 Create 物流网络的网络物件完成绑定；绑定入口不得写死为某一种方块。每件坠子只绑定一个网络，已绑定时显示附魔光效。绑定／清绑参考当前 Create 原生交互，不另设网络管理面板；地址复制使用紧凑入口。
3. 玩家把坠子佩戴到 Curios 项链槽。两类坠子合计最多佩戴一件，即使其他模组增加槽位也不能佩戴第二件。创造模式与生存模式使用同一套入口；只放在背包里不激活。
4. 背包左侧出现物流面板。玩家从普通背包拿起实物后，左键尽量存入当前堆栈，右键只存1个，同时为空格设置精确过滤。JEI ghost拖拽设过滤暂时停用；JEI查看配方与合成填充保留。
5. 玩家点击格子角落的小点，在该格下方展开 Create 风格双端滑条，分别设置最低值和最高值。两个端点初始关闭。
6. 启用最低值后，缓存不足时向坠子所绑定的网络提交真实包裹请求。纸飞机或运输蜂按各自原生规则送货。
7. 专用包裹抵达玩家时，模组把能容纳的内容转入目标缓存；缓存满时只保留真实余货，不要求载具原路返回。
8. 玩家从缓存取出实物，或让已支持的合成／弹药流程消费缓存现货。缓存数量在转出或消费成功的那一刻减少，并据此重新评估补货。

### 3.2 私人化

玩家可以把任意等级的普通供应链坠升级为 **供应链坠·私人定坠 / Supply Chain Pendant: Made to Order**。私人化保留普通坠子的整份缓存并转入「**锻造者**」的个人缓存，不新建一份空库存。

- **物主固定为锻造者**：私人化那次锻造的玩家就是这个私人定坠的唯一物主，`OWNER`（UUID）与物主名在锻造时写入坠子，永久归属。
- 若该玩家还没有个人缓存，锻造后普通坠子的缓存身份原子转为该玩家的个人缓存。若已有个人缓存，服务端先模拟完整合并；只有所有库存、格子配置、请求记录、收包状态、残包、等级和插件都能安全迁入时才提交。
- 无法全量迁移时拒绝私人化，两边状态和输入物品均不改变，提示：**“个人缓存空间不足，供应链坠库存无法转移”**。
- 私人定坠从此是**一把钥匙**：只有物主本人佩戴时才访问物主的个人缓存，并且同一物主锻造出的所有私人定坠共享同一个个人缓存（等级随之共享）。
- **非物主佩戴即退化**：其他玩家佩戴不属于自己的私人定坠时，该坠子立刻**退化成全新的普通供应链坠**（换成带新本件缓存的普通坠），无法访问物主的私人缓存；物主的缓存和其余钥匙不受影响。这代替旧「每人佩戴签收容量授权」的防刷机制。
- **物主直接升级**：物主本人可在锻造台用对应链节直接升级自己的私人定坠，一次提升物主个人缓存一级；不再需要「待签收容量授权／佩戴签收」流水，因此同一物主可以连续升级到 5 级。

## 4. 领域对象与状态归属

### 4.1 核心对象

| 对象 | 含义 |
| --- | --- |
| 终端 | 供应链坠或私人定坠；提供唯一佩戴入口并保存本件网络绑定和终端类型 |
| 本件缓存 | 由普通坠子的稳定 `cacheId` 引用；完整状态随该访问钥匙转交 |
| 个人缓存 | 按当前玩家身份解析；只由私人定坠访问，终端转交不转移缓存 |
| 物流格 | 一个精确物品变体的过滤、真实计数、最低／最高值、修订号和派生状态 |
| 请求记录 | Create 已接受或结果未知的本地承诺，用于防止同一缺口重复发单；不代表载具仍在路上 |
| 收包收据 | 防止同一个真实包裹因重复事件或扫描被重复结算 |
| 服务收件口 | 满背包时接管本模组专用包裹并立即尝试入库的服务端入口；不是额外普通背包 |
| 残包槽 | 每份缓存至多一个、只保存未能完全拆空的真实专用包裹的内部位置；不提供玩家管理入口 |
| 插件 | 放入当前缓存插件舱的可逆构筑物；每件占一个通用槽 |
| 物主 | 私人定坠的永久归属玩家；锻造时写入坠子的 UUID 与物主名，非物主佩戴会退化成全新普通坠 |
| 取料策略 | 当前固定背包优先，背包不足再用缓存；不存在玩家手动切换偏好 |

### 4.2 归属表

| 状态 | 归属与转交规则 |
| --- | --- |
| 网络绑定、终端类型 | 终端物品；随物品转交 |
| `cacheId` | 普通供应链坠；相同合法引用只访问同一缓存，不能复制库存 |
| 过滤、现货、阈值、请求记录、收据、残包、等级、插件 | 当前缓存；普通缓存随本件坠子，个人缓存随其物主（锻造者），非物主无法访问 |
| 自动取料优先级 | 当前统一为背包优先；未来插件若改变此规则须另行确认 |
| 面板滚动、悬停、展开格等瞬时状态 | 客户端会话；不写成库存事实 |

### 4.3 生命周期

- 普通供应链坠被丢出或转交时，本件缓存继续随坠子；死亡本身不删除缓存，坠子按正常物品规则掉落或保留。
- 当本件缓存的最后一个合法访问入口真正被岩浆、仙人掌、虚空、实体自然消失等方式毁坏后，该缓存对玩家永久失去；不提供找回、赔付或恢复玩法。
- 相同 `cacheId` 的异常副本只能访问同一份缓存，不能各自复制一份库存。销毁一个副本时不得误删仍有合法入口的缓存。
- 个人缓存不因死亡、卸下、丢失或毁坏私人定坠而改变。
- 未佩戴时保留缓存、设置、请求记录与残包，但不处理新业务。重新佩戴并解除冲突后，先续收已有残包／专用包，再检查补货。
- 底层可为崩溃保护保留不可访问的孤立记录，但这种记录不得形成玩家可用的恢复入口。

### 4.4 唯一佩戴入口

2026-09-06 用户修订了多终端玩法，下列规则替代旧“多件佩戴后管理冲突”方案：

- 每件终端只能绑定一个网络，绑定可清除；正常使用通过佩戴／卸下控制，不再提供逐件禁用开关。
- 有效佩戴但未绑定网络时，玩家仍可访问当前缓存并处理目标明确的迟到包，只是不能发起新补货请求；清绑或换网不清缓存、残包或既有请求记录。
- 两类坠子合计最多佩戴一件，在 Curios 接受第二件之前拒绝，不要求玩家进入终端管理页解决。
- 指令或异常接口绕过限制时，服务端拒绝缓存业务，不暗选缓存、不丢弃任何坠子；卸下多余坠子后恢复。异常提示保持简短，不为此保留常态管理页。
- 多件坠子仍可放在普通背包、转交或分别绑定不同网络，但不叠加等级、容量或请求次数。

因此 G-01 的正常玩家规则已经关闭；异常数据仍须服务端防御，不得把“正常无法佩戴两件”当成省略权限校验的理由。

## 5. 物流缓存与界面

### 5.1 精确物品变体

权威身份为：

```text
ItemVariantKey = 物品注册 ID + 数量归一为 1 的完整持久化数据组件
```

- 同一精确变体只能配置一个物流格。
- 同一物品 ID 的不同弹种、气量、耐久、附魔或其他组件状态是不同变体，可以分别占格。
- 存入、取出、保存重载、精确过滤、Create查询／请求、收包、合成和弹药候选均使用同一相等语义；未来恢复JEI ghost时也不得降级身份。
- 对外生成 `ItemStack` 时必须复制权威模板并按真实转出量设置数量，不能暴露可变内部引用。
- 无法完整编解码、往返后身份变化、属于禁止存储的包裹外壳，或规范模板超过 1,024 字节时，整次操作拒绝且来源不变。
- 首版不提供忽略气量、耐久或附魔的范围过滤。

### 5.2 格子操作

- 新缓存的已解锁物流格为空。
- 从背包拖入实物到空格：设置精确过滤，并按实际可容纳数量把真实物资转入缓存。
- 持物左键尽量存入当前堆栈；持物右键只存1个。未成功存入的物品仍在光标，容量不足或变体不符不改来源；空光标右键取出1个的规则不变。
- JEI ghost拖拽设过滤暂时停用，不能继续把拖拽成功作为首版必需入口。未来若恢复，仅设精确过滤、不生成库存；须先确定交互方案并重新验收。
- 已配置变体不能在其他格重复设置。
- 有现货的格必须先取空，才能清除或更换过滤；清除过滤同时只清该格旧修订的本地请求记录，不改变任何真实包裹。
- 取出时遵守物品自身合法堆叠上限。光标已有兼容物品时按可合并空间转出；没有合法落点时不扣缓存，不能把物品直接丢到世界。
- 存回时只接收精确相同变体，最多存到实际容量。无法存入的余量留在原来源。
- 最高数量是退货阈值，不是实际容量；关闭最高值不代表无限容量。

### 5.3 面板表现

- 面板位于原版背包左侧，创造模式和生存模式均可使用。
- 模组物品进入独立创造模式标签页；不能要求玩家依赖 `/give` 才取得坠子、升级中间产物或已开放插件。
- 面板显示由服务端生成的当前投递地址，复制交互参考当前 Create 原生做法，使用紧凑入口，不再使用大面积独立文字按钮。若必须改变可见地址格式，先修订规格，不能在运行时猜测。
- 物流格保持两列，格子尺寸和间距对齐原版物品栏；高级别使用滚动，不缩小格子或遮住已解锁格。1 级 9 格的末行只启用一个格。不常驻显示当前等级文字。
- 物品图标与数量、状态箭头和滑条小点使用不同绘制层与命中区，状态控件不能被物品图标遮住。
- 只有悬停某格时在格内显示角落小点；点击后只在该格下方展开紧凑的 Create 风格双端滑条，不靠扩大格距安放控件。
- 双端滑条支持拖动、滚轮和直接数字精调。左端是最低数量，右端是最高数量；各自最左／最右初始位置表示该方向未启用。
- 未佩戴时整个面板消失；不显示终端管理或取料优先级开关。
- 残包由后台自动处理，不显示残包取回按钮，不把缓存内部状态变成玩家必须管理的流程。
- 常态不弹出大段操作说明；保留原生物品提示，附加反馈只在相关操作或异常发生时简短出现。详细教程进入文档，不铺在每个悬停区域。
- 美术重做后续专题讨论；可以研究 Create 及附属的构图、控件和视觉惯例，复用具体资产前必须核对许可证与署名要求。
- 用户提出独立界面作为JEI交互的后续方向；入口、布局与是否恢复ghost尚未定案。本次暂停不自行替换当前背包左侧面板，也不新增一个未经讨论的物品选择器。

## 6. 补货、请求记录与箭头

### 6.1 数量口径

补退货只统计当前缓存中的真实现货，不统计普通背包、快捷栏、副手、请求记录或远端库存。

```text
shortage = max(0, minimum - storedCount)
requested = 当前缓存、精确变体与过滤修订下的有效已请求量
uncovered = max(0, shortage - requested)
```

启用最低值后，在 `storedCount <= minimum` 时可运行检查；只有 `shortage > 0` 才能产生非空请求。取出或消费使缓存减少时立即重新评估，玩家不必等到手中物品被放置或消耗。

### 6.2 请求规则

- 新请求只覆盖 `uncovered`，已有请求记录覆盖的部分不得重复发单。
- 网络只能提供部分物资时，只按真实接受量登记请求；库存为零或请求被拒绝时不创建虚假记录。
- 请求调用结果不确定时保留承诺，防止异常后自动重发造成复制；玩家可按格手动重置。
- 本模组不判断包裹是否丢失，不设超时重发、赔付或自动恢复。
- 按格重置只删除该物品与过滤修订的请求记录，不增加缓存、不撤回或销毁真实包裹。旧包迟到仍按真实内容处理。
- 大量物资沿用 Create 打包机连续分包：每包最多 9 个内容槽，各槽遵守物品原生堆叠上限，不制造超大包裹。

### 6.3 下箭头

| 当前状态 | 显示 |
| --- | --- |
| `shortage == 0` | 不显示下箭头，即使后台仍有旧请求记录 |
| `shortage > 0 && requested > 0` | 绿色下箭头：“库存不足，已请求 X” |
| `shortage > 0 && requested == 0` | 灰色下箭头：“库存不足，尚未成功请求”，并显示本模组已知原因 |
| 已请求一部分但仍有 `uncovered` | 仍以绿色为主，tooltip 同时显示仍缺数量与剩余请求状态 |

绿色只证明 FMP 登记过请求，不证明包裹仍存在、载具仍在飞行或远端一定会送达。玩家手动补足缓存后箭头立即消失，但请求记录不随之删除；再次消耗时仍用该记录防止重复采购。

红色／灰色上箭头属于退货版本：红色表示超额且已有发运动作，灰色表示超额但当前不能发运。未实现退货时不显示可用的上箭头。

## 7. 收件口、包裹与残包

### 7.1 路由身份

仅凭 `FMP@玩家名` 不能区分同一玩家的多份本件缓存。每个补货请求还必须固定：

- 目标缓存键；
- 发单时接收玩家；
- 请求 ID 与请求量；
- 精确物品变体和过滤修订。

用户可见地址仍以 `FMP@玩家名` 为基础，但目标缓存令牌／请求标识的实际承载方式必须先通过 Create、纸飞机与运输蜂的完整链路验证。无法证明目标缓存时保留原包并提示诊断，绝不按当前打开或当前佩戴的缓存猜测。

### 7.2 服务收件口

满背包时采用专用服务收件口，不给玩家永久增加若干不可见普通物品格。

- 只接管地址、目标缓存、包裹结构和访问条件都合法的完整 Create 包裹。
- 普通包裹、错误玩家、错误缓存、散装物品或不安全内容完全交还原路径。
- 若内容可全部进入缓存，包裹立即拆空，收件口不保存任何物品。
- 若只能部分接收，只转入恰好能容纳的数量，剩余内容保留在同一个真实包裹。
- 每个物品格提供一个专用残包位，只能容纳针对该格过滤变体、未能完全拆空的真实包裹。某格已有残包且新包无法完全拆空时，FMP 拒绝接管该格的第二个包；不同物品格的残包互不占用、互不阻塞，调用方对拒绝的包保留原包或执行原模组失败规则。
- 残包位不能存普通物品，也不能作为额外仓库；不提供手动取回按钮。后台负责正常续收和不能继续入缓存时的安全处置，任何转出必须有真实合法落点，没有空间则保留原物。
- 缓存腾位后先续收残包，再检查补货。
- 背包中的真实余包被玩家手动拆开或移走后，不保留不存在的等待状态；散装所得不自动计入缓存。后台不能因用户看不到残包而静默销毁、复制或无限增加内部槽位。

### 7.3 到货结算

- 第一次观察合法包裹时写入本模组收据并按实际支持内容结算请求记录一次。
- 重复插入事件、槽位变化与后备扫描不能让同一包裹二次结算或二次入库。
- 实际转入量必须等于包裹减少量；只在包裹所有内容为空时移除包裹外壳。
- 没有现存请求记录的迟到包仍可按目标、地址、过滤和容量处理；手动重置不是丢弃真实包裹的理由。
- 组件不匹配、没有过滤、容量不足或不支持的内容均原样留包，不能清洗后强行收入缓存。

## 8. 终端成长

### 8.1 1—5 级永久结构

正式等级只称 **1—5 级**。石头、铁、安山、黄铜、坚固板是已废止的讨论简称，不是等级名，也不绑定配方材料。

缓存有五级，但扩容只有四次。玩家可见的扩容链节编号为 **1—4**，依次用于 **1→2、2→3、3→4、4→5**；这是升级步骤编号，不是目标缓存等级。私人化链节不属于这四种扩容链节。

| 等级 | 物流格 | 单格容量 | 通用插件槽权益 |
| ---: | ---: | ---: | ---: |
| 1 | 9 | 128 | 1 |
| 2 | 16 | 256 | 2 |
| 3 | 24 | 512 | 3 |
| 4 | 30 | 1,024 | 4 |
| 5 | 36 | 2,048 | 5 |

- 等级属于缓存：普通缓存等级随普通坠子，个人缓存等级随玩家。
- 多枚终端不能叠加等级、格数、单格容量或插件槽。
- 每次升级只提高一级并新增一个空插件槽权益，不生成插件。
- 等级与插件是两套并行增强：等级提供永久结构底座，插件提供可逆构筑；特定方向的最大能力来自 5 级与合法插件组合。
- 插件不能提高插件槽数量、改写等级或跳过升级链。

### 8.2 序列组装

永久升级必须体现 Create 序列组装与中间产物，不能再使用旧测试版的普通合成升级件、手持右击或面板插槽。

- **已确认（2026-09-06）**：Create序列组装制造链节，锻造台完成坠子升级与私人化。坠子在制造菜单中时允许最终装配；这项制造例外不开放未佩戴时的缓存面板、存取、补货、收包或自动取料。
- **已确认的成长成本方向**：五级投入应呈指数式陡增，主要通过关键材料的获取难度和加工复杂度体现。高等级需要更深的材料加工链、更多前置工艺与产线配合；不能把同种材料等比堆量、同一工序反复循环、降低成功率或强制计时当作主要难度。
- 工厂建设和自动化可以降低重复劳动与实际等待；不为制造“更费时间”而绕过机械动力产能提升的价值。具体材料、数量和工艺是参考配方选择，实机核对递进是否成立，不能把未测的游玩时间写成精确倍数。
- 装有真实缓存的坠子不能进入随机损毁或概率失败的步骤。
- 若采用概率产出，只能作用于可重新制造的链节／中间产物。
- 配方预览、JEI 查询与自动化模拟不得升级缓存、转移所有权或改变物主。
- 最终提交必须明确目标缓存，并在服务端验证当前等级、输入身份、输出和事务版本。
- 各级材料、步骤和概率是首版进入实现前必须完成的产品配方门，见第 12 节。

## 9. 插件系统

插件属于后续构筑版本，但其核心模型已经确认，首版数据模型不得堵死该方向。

- 游戏内只有一个通用插件舱和一种通用插件槽；玩家看不到“功能／数值”分类，也没有分类页、分类颜色或分类配额。
- 任意合法插件均可进入任意槽。
- 所有插件都允许重复安装，每个实体都占一个槽并须逐件保存、返还。
- 同功能重复件按“至少一件即生效”计算，重复件不会让布尔功能执行多次；拆下一件而仍有同功能件时，效果继续。
- 数值插件的每个副本都进入该插件固定的组合公式，并受硬上限约束。公式由插件定义，不能临时依 UI 顺序变化。
- 不同插件可以定义互斥组；不合法组合在提交前拒绝。
- 插件实体属于当前缓存：普通缓存插件随 `cacheId`，个人缓存插件随玩家。
- 安装、拆卸和私人化合并均先在服务端模拟，再原子提交。
- 移除会降低容量的插件时，如果现货、配置或残包无法在新上限下保持，拒绝拆卸；不得截断、掉落或静默删除。
- 私人化时先合并插件多重集，再校验最终槽数、冲突和容量；任一失败使整个私人化事务回滚。

首批插件、数值、硬上限、互斥关系、制造配方和界面细节尚未由用户决定，因此不进入`v0.1.0`或`v0.2.0`。1—5级的槽位权益在首版数据模型中保留，插件舱等到`v0.3.0`有实际内容后开放，前两个版本不显示占位内容。

## 10. 取用、合成与弹药

### 10.1 玩家直接取用

玩家直接用手放置或使用物品时，先从缓存取出一份遵守该物品原生堆叠上限的真实物品，再按原版方式操作。首版不做快捷栏堆栈的自动无缝续补。

### 10.2 自动取料原则

长期目标是覆盖“某个操作消费另一种物品”的通用消费行为，而不是只为弓和弩写物品 ID 特判。

- 首版保障原版背包 2×2、工作台 3×3、配方书、JEI 向这两类界面的配方填充，以及原版标准投射物消费链。
- 标准投射物采用共享查询／实际消费入口；未登记物品 ID、但遵循同一协议的其他投射物武器也应能使用缓存。
- TaCZ 弹药是明确后续目标。精确组件模型只解决弹种保存前提，仍须单独验证装填、弹匣、开火和不消耗规则。
- JEI ghost过滤与JEI recipe transfer是两项独立能力。2026-09-06用户暂停前者，后者与配方查看继续保留和验收；JEI不成为硬依赖。
- 首版不据此承诺 EMI、所有模组工作台或所有自定义武器兼容。

### 10.3 消费事务

- 查询候选、配方预览、取消拉弓或失败操作不得扣缓存。
- 箭矢实际被消费、弩成功装填或适配器确认真实消费时才扣缓存。2026-09-06 用户确认合成改用可撤销预留：准备配方不形成消耗或补货缺口，实际合成或玩家手动拿走预留原料才提交；取消释放未消费预留。玩家直接从缓存取物仍立即扣量，普通背包不计入补货库存。
- 弩装填后发射不能再次扣箭；无限、创造、多重射击和配方余物遵循原规则。
- 背包和缓存可以混合补足，当前固定背包优先，不足时由缓存补足。
- 不显示或提供优先级切换开关；仅隐藏按钮不够，旧网络意图和旧偏好也不能继续改写实际策略。未来改变优先级的插件仅为候选，仍须通过插件产品门，且不恢复此开关。
- 普通背包现货不参与最低／最高数量统计；从背包主动存入缓存后才成为缓存现货。

## 11. 运输边界与退货方向

### 11.1 补货运输

- FMP 只向 Create 提交真实请求并接收本模组专用完整包裹，不另写一套全局运输。
- Create More: Package Couriers 的纸飞机与 Create: Mobile Packages 的运输蜂都必须进入真实联调；用户更偏好纸飞机，不能只测蜂。
- 两种运输模组按各自原生定位、成员、路线和成本规则工作。FMP 不代替定位器、不修改成员资格、不接管寻路，也不把运输模组存在性当作 Create 发单前置条件。
- 补货阶段若满背包投递在外部模组进入玩家物品栏前就失败，只允许增加最窄的运行时交接适配；这不授权接管运输系统。
- 两种运输模组和 JEI 均通过运行时存在性探测隔离，缺失时核心模组仍须加载。

### 11.2 退货

2026-09-06用户调整顺序：退货在基础补货稳定后于`v0.2.0`实现，插件构筑后移至`v0.3.0`。退货不等待插件系统，也不把运输物格做成必须先安装的插件：

- 当缓存实际数量大于已启用最高值时，超出部分才有资格退货；恰好等于最高值不发运。
- 面板提供专用运输物格；格子角落的小点切换为返回地址设置入口。
- 发运前必须证明当前有效佩戴、目标缓存、网络、返回地址、载具和接收条件均可用。无法出发时不打包、不扣缓存、不消耗载具。
- 纸飞机与运输蜂分别适配，不把一方规则自动套给另一方。
- 运输蜂格内的实物蜂不消耗，只作为派出资格；每次派出一只带真实包裹的一次性临时蜂。
- 临时蜂进行真实运输，不瞬移。成功交付后销毁；出发后失去可用目标并终止时也销毁，未交付原包在失败位置掉落。
- 临时蜂不得通过入港、敲击、死亡或保存重载变成可取得的普通蜂物品。
- 原生逻辑可以重选目标；首轮不专门防“串网”，先在实际游玩中记录发生频率与后果。
- 不新增退货站，不自建全局配送系统，不判断途中包裹丢失，也不自动赔付。

加载器依赖声明只保留 Minecraft／NeoForge、Create 与 Curios。JEI、Package Couriers、Mobile Packages 和其他兼容目标不写 required 或 optional 依赖；实现兼容时使用隔离模块与运行时存在性探测。

### 13.2 干净架构边界

- 所有业务先由有效佩戴门解析活动终端，再得到 `CacheHandle`，最后进入统一缓存事务；业务代码不能重新假设“缓存永远是玩家附件”。
- 世界级缓存注册表保存本件缓存的真实状态；私人缓存通过玩家身份解析其缓存引用。
- `ItemVariantKey` 是过滤、库存、请求、收据、合成和弹药的统一物品键。
- 请求与包裹路由固定目标缓存，不能只靠玩家名或界面当前状态。
- 服务收件口是包裹交接能力，不是扩展 `Inventory` 长度的隐形仓库。
- 单次客户端意图最多 8 KiB，完整同步快照最多 64 KiB，单模板最多 1,024 字节；超过上限安全拒绝。
- 项目目录中的 `!` 会破坏当前 SecureJar／union URI 发现链，Gradle 输出继续写入相邻的 `../.fmp-build-safe/`。
- 新模型直接建立当前 schema 与新注册 ID。不得添加旧测试格式迁移器、兼容别名或双格式解码；当前 schema 的首次创建、保存重载和坏数据拒绝仍必须完整测试。

## 14. 版本级验收原则

任何版本只有同时满足对应路线图与下列原则，才能成为本地版本交付：

1. **守恒**：缓存、背包、包裹、网络和世界掉落的总物资变化能由真实操作解释；失败、重试、保存重载和重复事件不复制、不静默丢失。
2. **身份**：同 ID 不同组件不串格、不串单、不串包；组件往返完全保真。
3. **归属**：普通缓存随本件坠子，个人缓存随玩家；转交、死亡、卸下、销毁、异常副本和私人化均符合第 4 节。
4. **访问控制**：未佩戴、第二件佩戴尝试、异常多件、旧菜单包和伪造客户端意图均不能绕过服务端。
5. **请求正确性**：缺口、已请求量、部分库存、失败、结果未知、手动重置和迟到包不会重复采购或凭空消账。
6. **收件正确性**：背包有空间与全满、完整／部分包、重复发现、残包手拆和多个缓存都不会猜路由或吞包。
7. **操作正确性**：取出不丢物；持物右键只存1个；JEI ghost停用时不改过滤／库存且不影响配方查看与填充；合成余物有安全去处；弹药查询不扣、实际消费只扣一次。
8. **界面可用性**：生存／创造、不同 GUI 缩放、配方书与 JEI 共存时控件不遮挡，失效状态有恢复入口。
9. **依赖隔离**：没有 JEI 或任一运输模组时核心仍加载；声明的真实兼容组合分别经过客户端、专服和游戏内闭环。
10. **证据分层**：编译、单测、GameTest、客户端观察、专服启动和第三方联调分别记录，任何一层不能冒充另一层。

`release/vX.Y.Z-test.N/` 只用于阶段测试；达到整个版本完成门后才生成 `release/vX.Y.Z/`。本地交付不等于允许 Git push、打标签或公开发布。

## 15. 明确不做与后续方向

### 当前不做

- 自研纸飞机／运输蜂式全局配送系统；
- 远程瞬移扣库或直接生成货物；
- 自动判断包裹丢失、超时赔付或自动重发；
- 用普通隐形背包槽解决满包收件；
- 忽略组件的宽松过滤；
- 为未发布 `test.N` 世界开发兼容或迁移模块；
- 在插件内容尚未决定前注册占位插件。

### 已登记后续

- 统一插件构筑；
- 纸飞机／一次性蜂退货；
- TaCZ 弹药；
- 供应链甲／供应链盔无 Curios 入口及无损拆装；
- 精妙背包、Create 存储背包等插件式访问；
- EMI 与更多合成／消费适配；
- 运输蜂串网的实际观察，只有出现值得处理的真实问题才设计专门适配。
