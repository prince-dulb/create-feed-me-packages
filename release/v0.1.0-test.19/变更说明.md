# 变更说明 — v0.1.0-test.19

基于 test.18 修复三项问题，其中最关键一项为容量模型纠正。

## A. 容量模型纠正（用户明确指定）

test.18 误将 `CacheLevel.capacity()` 理解为组数，导致 1 级单格实际容量 = 128 × 64 = 8192 个。用户明确纠正：**容量仍以物品数计**（1 级 = 128 个），组容量 = 容量 / 堆叠上限（木板 128/64 = 2 组，而非 128 组）。

修改清单：
- `CacheState`：容量校验改回 `amount ≤ capacity`（物品口径）；阈值校验改用 `groupCapacity = capacity / filter.stackSize()`
- `CacheEdit.insert()`：插入空间 = `capacity - amount`（移除 `capacity * stackSize` 乘法）
- `CacheEdit.thresholds()`：阈值上限校验改用 `groupCapacity`
- `CacheMerge`：NO_SPACE 检查改回 `amount > capacity`（两处）
- `Cell.shortage()`：不变（`minimum * filter.stackSize() - amount`，阈值按组、数量按物品）

## B. MaterialHints 崩溃修复

旧版 `MaterialHints.Message` 构造器的 `amount > 2048` 校验在错误容量模型下被超出（8192+），触发 `IllegalArgumentException: Invalid material hints` 崩溃。容量模型回退后自然修复；另将上限提至 4096 留安全余量。

## C. 滑条范围与单位

- 滑条范围改用 `groupCapacity = capacity / stackSize`（滚轮、拖动、数字输入、提交均按此上限）
- 滑条标签显示 "N组" 而非裸数字
- stock tooltip 双行：第一行物品数与容量，第二行组数与组容量（仅堆叠 > 1 时显示）

## D. Schema 4 与迁移

- `CacheLedger.SCHEMA` 升至 4
- schema 3 为错误实现标记，整记录拒绝载入
- schema 2→4 迁移：旧物品阈值 `min`/`max` 除以 `filter.stackSize()` 转为组数（`< 0` 保持 `-1`）
- 新存档请使用新世界；旧 schema 3 测试世界自然失效

## E. GameTest 阈值换算

所有 `thresholds(slot, itemValue, max)` 调用按 level 与 stackSize 换算为组数：

| 旧值（物品） | 新值（组） | 依据 |
|--------------|-----------|------|
| 128 | 2 | 1 级 capacity=128, stackSize=64, 128/64=2 |
| 120 | 2 | ⌈120/64⌉=2 |
| 100 | 2 | ⌈100/64⌉=2 |
| 37 | 1 | ⌈37/64⌉=1 |
| 32 | 2 | 1 级 groupCapacity=2（上限边界） |
| 16 | 16 | 5 级 capacity=2048, stackSize=64, 2048/64=32, 16≤32 |

## 请复测

1. 设最低 1 组后大量补货——不再触发 `Invalid material hints` 崩溃
2. 不同堆叠上限物品（如 64 堆叠木板 vs 16 堆叠末影珍珠）各自按组容量独立占格，不共享同一物品上限
3. 滑条拖动/滚轮步进以 1 组为最小分辨率，标签显示 "N组"
4. 旧存档（schema 2）自动迁移，阈值从物品数转为组数；schema 3 存档拒绝载入
